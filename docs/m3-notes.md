# M3 记录：工具与副作用

M3 拆成两段（设计文档第 12 节，rev 262）：M3a 副作用协议和 GitHub 写工具，M3b 只读 git MCP。

## M3a：副作用协议和 GitHub 写工具（2026-10-18）

验收 T2、T3、T15、T16 通过，GitHub 用本地模拟的。真实测试仓库上的那次 T2 放在 M3b 收尾。

### 做了什么

- **数据目录锁**：agentd 启动后第一件事是对数据目录加排他锁（`agentd.lock`，flock），拿不到就退出，账本和 socket 都不碰。以前第二个 agentd 会删掉并抢走 Control socket（Linux 上还有 Runtime socket），而且在绑定端口之前就执行 `SettleOpen`，把第一个 agentd 还在途的模型预留按全额结算，还会启动 gateway worker 领活动任务。锁随进程走，kill -9 也会释放。
- **副作用协议**（`internal/gateway/effects.go`，迁移 `00007_effect_claims.sql`）。一次写分四步：
  1. 渲染载荷：工具的 Prepare 生成外部系统将收到的全部内容，同一个请求每次渲染结果相同。
  2. 记录：载荷存成 blob，哈希存进 `payload_sha256`。
  3. 领取：按 `version` 比较并交换，记下 `claimed_by`（本进程的标识）和 `claimed_at`。领取在同一个事务里检查任务没被取消，所以 CancelRun 落库之后任何尝试都领不到。
  4. 发送，记结果。

  重试时重新渲染，载荷和记录的不一致就不执行（`PayloadChanged`）。M4 的审批绑定的就是这份载荷。
- **发送的结果分四种**：
  - 成功：SUCCEEDED。
  - 没发出去（`ErrNotSent`）或对方要求稍后再试（限流）：交还领取，返回可重试错误，下次尝试再领。
  - 对方明确拒绝（4xx）：FAILED，不可重试。
  - 同名资源已存在但内容不同：UNKNOWN，等人核对，不覆盖。

  其余情况（5xx、超时、连接断开）结果未知，当场按类别恢复。
- **按类别恢复**：
  - 适用于两种记录：被已经不在的进程领取的；被本进程领取、但当前没有执行在跑的。
  - 规则：
    - idempotent：同键重发。
    - lookup：先查。查不到就等到“最后一个可见请求发出的时间 + Settle”，再查一次，仍没有才重发；查询本身出错就转人工核对。
    - unsafe：记 UNKNOWN，返回 needs_reconcile。
    - 已取消的任务：只查，不发；查不到记 ABANDONED。
  - agentd 启动时还有两件事：
    - 已取消任务里没领取过的记录直接记 ABANDONED。
    - 上个进程领取的记录在后台恢复，和工作流重试走同一个 singleflight 键，谁先到谁做，另一个等结果。启动时的恢复只查不发：查不到就交还，由任务的下一次调用发出。任务已经结束的，不会再有下一次调用，也就不会再发。
  - 本进程领取、执行还在跑的记录，同时到的另一个执行者返回可重试的 `EffectBusy`，不会再发一次。
- **核对**：
  - `ListPending` 列出 UNKNOWN 的记录，包括当时要发的载荷全文。
  - `ResolveReconciliation` 有两个出口：
    - 已执行：结果由人给出（按工具的结果 schema 校验），或者 `--lookup` 让 agentd 去查，记录改成 SUCCEEDED。
    - 未执行：记录改回 PENDING，下次调用用原幂等键重发；任务已取消或已结束则改成 ABANDONED。lookup 工具在最后一个请求发出后的 Settle 时间之内，不接受“未执行”。
  - 并发和重复提交的处理：
    - 按 `version` 防并发，`resolve_key` 防重复提交。
    - 同一个 key 再发一次，返回同样的结果。
    - 换一个 key 再处理，报“已不在待核对状态”。
  - 处理完直接给工作流发门铃（outbox 留到 M4）。
  - 命令行：`agentctl reconcile list | show | resolve`。
- **工具注册表**（`internal/tools`）：
  - 每个工具在代码里声明三样东西：类别、参数 schema（`additionalProperties: false`）、写工具的结果 schema。
  - 写工具实现 Prepare、Execute 和 DryRun；lookup 类工具另外实现 Find 和 Settle。
  - 策略文件里的 `effect` 改为可选。要写，只能写工具自己声明的类别，或者对写工具写 unsafe。
  - agentd 启动时检查：策略写了更弱的类别，或者列出 agentd 没有的工具，都拒绝启动。
  - 网关只给工具补它声明了的范围参数；schema 拒收未知参数。由此堵上两个口子：Scope 只管列出的参数名（m1-notes），以及塞无关字段绕过同参数计数（m2-notes）。
- **GitHub 写工具**（`internal/githubtool`，go-github v92）：
  - `github.open_draft_pr`：
    1. 检查补丁，应用到镜像里的原文件。
    2. 经 Git Data API 建 tree、建提交（作者和时间固定）、建分支。分支已存在时，比较 tree 和父提交，不比较提交哈希。
    3. 按 head 分支查 PR（state=all），查不到才开草稿 PR；遇到 422 再查一次。
    4. PR 正文里没有模型写的文字。
  - `github.comment_commit`：
    - 按模板从 report_ref 渲染。
    - 模型和工作流给的文字全部放进代码围栏，围栏比其中最长的一串反引号还长。
    - 围栏外只有 agentd 自己核实过的内容：提交 SHA、按严重度的计数、PR 编号。PR 编号从本任务 open_draft_pr 的副作用记录里取，不用工作流传来的 pr_url。
    - 带隐藏标记 `<!-- agent-effect:<effect_id> -->`。查找时只认令牌本人账号发的评论。
- **补丁检查**（`internal/patch`，go-gitdiff + doublestar）。open_draft_pr 和 git.apply_check 共用这段代码，拒绝以下补丁：
  - 二进制改动、改名和复制、权限位变化；改完后不是普通文件（100644）的。
  - 路径经过 `.git`、`.gitmodules`、`.gitattributes` 的。
  - 路径不规范的，包括 `..`、绝对路径、反斜杠、控制字符。
  - 超出大小和文件数上限的。
  - 命中 deny_paths 的。deny_paths 不区分大小写，`makefile` 绕不过 `Makefile`。

  补丁按 hunk 写的位置严格应用，对不上就拒绝，不做模糊匹配。原文件用 `git ls-tree` 和 `git cat-file` 从镜像读，不跑过滤器、钩子或 diff 驱动，也不读用户和系统的 git 配置。不带 `diff --git` 头的普通 diff 去掉第一层路径（同 `git apply -p1`）。
- **dry-run**：
  - 用法：`agentctl runs start ... --dry-run`。是否 dry-run 记在 runs 表里，Worker 改不了。
  - 效果：写工具只做 Prepare，记成 DRY_RUN，返回带 `dry_run` 标记的结果。
  - agentd 没配 GitHub 时，GitHub 工具一律 dry-run，启动时打印警告。`agentd-claude.yaml` 不配 GitHub，配置测试断言了这一点：M4 之前，真模型和免审批的真实 GitHub 写入不同时出现。
- **循环保护**：每次调用记下它返回的状态。返回等待状态（needs_approval、needs_reconcile、budget_exhausted）的调用不计入模型调用次数和同参数次数，步骤数照算。以前等核对的任务每小时醒来重发一次，大约 3 小时后会被当成死循环拒绝。
- **配置**：
  - `repos` 的值可以写成镜像路径，也可以写成 `{mirror, github: owner/name}`；GitHub 名默认就是逻辑 ID。
  - 新增 `github` 一节：`api_url`、`token`（钥匙串引用；只有 api_url 是回环地址的模拟器才可以不填）、`request_timeout`（默认 30s）、`settle`（默认请求超时加 30s）、作者。
  - 默认作者 `agentos <agentos@agentos.invalid>`，这个地址不属于任何人。

### 实现中我定的几处（方案里没细说）

- **M3a 的 git.apply_check 已经做真实检查**：在 agentd 里用和 open_draft_pr 同一段代码检查补丁，并严格应用到镜像。代价：模型给的行号不准时，`git apply` 能靠偏移打上的补丁，这里会被拒。M3b 的 MCP 服务器要是用 `git apply --check`（容忍偏移），两边会不一致。M3b 开工时要定：两边都严格，还是都用 git。
- **恢复时在活动里等 Settle**，期间照常发心跳，不靠 Temporal 重试来等：工作流的重试策略最多 5 次尝试，退避加起来约 15 秒，等不到 60 秒。
- **副作用的 result_blob 现在只存工具的结果**。M1 存的是 `{status, value}`；状态改由副作用的状态决定。
- **模拟 GitHub 用 Go 写**：Go 单元测试直接用它，黑盒测试把它作为单独进程启动。它不校验令牌，只记录请求带没带令牌，Go 测试断言每个请求都带了。
- **T3 的 unsafe 工具 `test.unsafe_write`**：只在 `agentd --test-tools` 下注册，写的是数据目录里的一个本地日志。

### 推送前审查（安全审查 + 对抗性审查）发现并修掉的问题

两个审查代理都没改文件，下面的问题都核实过、已修，并补了测试：

1. **同一个核对幂等键可以生效两次**（高）。“未执行”之后重发，又一次结果未知，记录回到 UNKNOWN；这时 agentctl 重放同一个 key，会再触发一次重发。改法：核对结果按（effect_id, key）记进新表 `effect_resolutions`，同一个 key 再来只返回当初的结果；同一个 key 配不同结论直接拒绝。
2. **启动时的恢复会替已经结束的任务开 PR**（高）。例如重试次数在 GitHub 限流期间用完、任务已经发完失败报告，下次启动的恢复还是会重发。改法有三处：
   - 启动时的恢复只查不发：查不到就交还，由任务的下一次调用发；任务已结束就不会有下一次调用。
   - 查询出错直接转人工核对（UNKNOWN），不再无限重试。
   - 等待期间任务被取消，记 ABANDONED。
3. **领取之后的取消挡不住 open_draft_pr 后面的请求**（中）。这个工具要连发 7 个请求，取消只在领取时查一次。改法：工具在每个外人能看到的请求（建分支、开 PR、发评论）之前都调用 `proceed`。`proceed` 在同一条 UPDATE 里检查任务没被取消，并把 `claimed_at` 更新为这一刻，lookup 的等待从最后一个可见请求算起。
4. **Settle 没有下限**（中）。现在要求 settle ≥ request_timeout + 10 秒；回环地址上的模拟器只要求 ≥ request_timeout。测试改成 request_timeout 2 秒、settle 3 秒。另外，开 PR 时 GitHub 回 422 “already exists”、但查不到这个 PR，按结果未知处理，不再记 FAILED。
5. **工作流可以改参数发任意多条公开评论**（中）。参数每改一次就是一个新的副作用。改法：每个任务、每种写工具默认最多一次（策略的 `max_per_run`，可调大），按“已发出或可能发出”的记录计数，在插入副作用记录的同一个事务里判断。新测试 `tests/test_write_limits.py`。
6. **路径规则不够死**（低）。补丁路径里的 `:/app/db.py` 会被 git 当成 pathspec 魔法；`ſcripts/` 这类非 ASCII 字符能绕过大小写不敏感的匹配；还能在符号链接下面建文件。改法：
   - 路径各段只允许 `[A-Za-z0-9._+-]`。
   - git 命令加 `GIT_LITERAL_PATHSPECS=1`。
   - 父路径必须是目录。
   - 先用 `ls-tree -l` 查大小，超限的文件不读。
   - git 报错里的镜像路径替换成 `<mirror>`，因为报错可能经工作流进入公开报告。
7. **评论的边界情况**（低）。
   - 一长串反引号能把评论撑过 GitHub 的长度上限：现在反引号串最长截到 16 个。
   - 工作流可以把别的副作用的标记塞进围栏里的文字：现在查找只认最后一行的标记。
   - Unicode 格式字符（如双向覆盖符）也删掉。
8. **开 PR 时有一批路径永远拒绝**，不管策略怎么写，因为 GitHub 自己会对它们采取行动：
   - `.github/**`：工作流、dependabot 配置等。
   - 三个位置的 `CODEOWNERS`：决定谁必须评审。
   - `.devcontainer/**` 和 `.devcontainer.json`：有人在 Codespaces 里打开这个分支时会执行其中的命令。

   后两项是提交之后后台安全审查提醒补上的。开发策略和测试策略也加上了 deny_paths；正式策略加了 `GNUmakefile`，GNU make 会先读它。
9. **我自查发现的一处窄窗口**：同一进程里刚领取成功、还没登记“正在发送”时，另一个执行者若绕过合并读到这条记录，会把它当成无人在发。改法：领取和登记放进同一把锁。正常路径不会走到这里，但 T16 的 Go 测试正是绕过合并来测的。

还有一处改动：之后的调用不再重新渲染载荷，一律沿用第一次记录的那份。否则这种情况会出错：PR 的副作用在两次评论调用之间结算，评论载荷因此变了，已经成功的评论被当成“载荷改变”而拒绝。

### 测试怎么测

- **T2**（`tests/test_t2_lookup_recovery.py`），四个场景，都只开出一个 PR 或一条评论：
  1. PR 已在模拟 GitHub 上开出、结果还没落账时 kill -9 agentd。重启后靠查找补记，不再发。
  2. agentd 领取后、请求发出前被杀。重启时查不到，等过 Settle 再查，仍没有就交还；由任务的下一次调用发出，只发一次。
  3. 报告评论已发出、结果没落账时被杀。重启后按标记找到它。
  4. 不杀进程，模拟 GitHub 开出 PR 但扣住答复，agentd 的请求超时。agentd 当场去查，补记这个 PR。
- **T3**（`tests/test_t3_reconcile.py`），三个场景，最后都只写了一次：
  1. 写入已到外部、结果没落账时被杀。重启后任务停在 WAITING_RECONCILE，核对列表里有这条记录和它的载荷；`--executed --result` 之后任务跑完。
  2. 领取后、发出前被杀。`--not-executed` 之后用原幂等键发出。
  3. 不合工具结果 schema 的结果被拒，记录保持 UNKNOWN。
- **每任务一次**（`tests/test_write_limits.py`）：恶意工作流发三条不同的报告，只有第一条发出，后两条返回 denied；策略写 `max_per_run: 2` 时发出两条。
- **T15**（`tests/test_t15_cancel_restart.py`），三个场景：
  1. PR 已开出、结果没落账时取消任务，再 kill -9 重启。PR 靠查找补记，取消之后模拟 GitHub 没收到任何写请求，也没发报告。
  2. 记录已建、还没领取时取消再重启。记录在启动时记成 ABANDONED，什么都没发。
  3. 同样的时机，取消但不重启。领取在同一个事务里看到取消，记成 ABANDONED。
- **T16**（`tests/test_t16_one_executor.py`），两个黑盒场景，外加一个 Go 测试：
  1. 第二个 agentd 在同一数据目录上起不来，第一个还在服务。第一个 agentd 那笔开着的预留，最后按它自己的用量结算，没有被第二个当成 `open_at_start` 全额结算。
  2. 第 1 次尝试领取后卡住且不发心跳，Temporal 开出第 2 次尝试，两者合到同一个执行上；接着 kill -9，重启后的恢复和第 3 次尝试也碰到这条记录。三方合起来只开出一个 PR。
  3. 领取用的比较并交换由 Go 测试验证：`internal/gateway` 的 `TestOnlyTheClaimantSends` 让两个执行者绕过合并、同时处理同一条记录，只有一个发出。
- **dry-run**（`tests/test_dry_run.py`）：带 `--dry-run` 的任务、没配 GitHub 的 agentd，都没往模拟 GitHub 写任何东西，载荷全文都在账本里。
- **已有测试的变化**：
  - 测试镜像改成两次提交，被审计的那次正好是桩 diff 的改动，假模型的补丁能打上。
  - `stack.external()` 改为看外部世界自己的记录：模拟 GitHub 的请求日志，或测试工具的日志。

### 留到后面

- **M3b**：只读 git MCP（show_diff、apply_check），每次调用起一个沙箱进程；真实测试仓库上的 T2。两样都已完成，见下面 M3b 一节。
- **M4**：审批表（AWAITING_APPROVAL，拒绝和修改后的 ABANDONED）；门铃改走 outbox，现在核对后的门铃是直接发的。
- **其他**：
  - 同参数计数用的是工作流原样发来的参数，还没补范围参数。所以工作流可以靠写或不写某个范围参数，凑出同一调用的几个变体，最多 2³ 种。写操作有副作用去重和每任务次数上限，重复发也只算一次；读操作只是多读几次。
  - 等人核对时，工作流每小时醒一次，每次都算一个调用。总调用上限是 100，所以大约 4 天没人处理，任务就会被循环保护拒绝，以失败结束。之后再处理成“未执行”，记录会改成 ABANDONED，因为任务已经结束。
  - unsafe 工具没有 Settle。重启后，人可以马上判“未执行”；如果旧请求其实还在对方那里处理，就可能出现重复。lookup 工具会拒绝过早的“未执行”。
  - 同一进程领取的记录，如果请求还在途、尝试次数又用完了，在 agentd 重启前不会出现在核对列表里。
  - 模拟 GitHub 的建 tree 只是对请求求哈希，没有模拟 GitHub 合并 base_tree 的行为。M3b 在真实仓库上跑 T2 时会覆盖到。
  - 设计文档第 7 节策略示例的 deny_paths 还没有 `GNUmakefile`，`max_per_run` 和“启动时只查不发”也还没写进文档。这几处等你确认后再改文档。
  - 报告超过 60,000 个字符会被截断。
  - lookup 的等待时长依赖 GitHub 文档写的 10 秒处理上限。就算估错，这两个工具的后果也有限：迟到的建 PR 会被 422 挡住，评论最多多出一条。

## M3b：只读 git MCP（2026-10-18）

`git.show_diff` 不再是桩。两个 git 工具都通过一个只读的 git MCP 服务器读仓库，agentd 每次调用起一个新进程，放进沙箱运行。

### 做了什么

- **git MCP 服务器**（`internal/gitmcp`、`cmd/agentos-mcp-git`，官方 MCP Go SDK v1.8.0），两个工具：
  - `show_diff`：
    - 提交号只收完整的 40 位 SHA，而且只看对象头：必须是提交对象，不超过 1 MiB。
    - 用 `git diff-tree -p --text --root --diff-merges=first-parent --no-ext-diff --no-textconv`：首个提交整份显示，合并提交只对第一个父提交显示，二进制文件也按文本显示，不跑外部 diff 程序和文本转换。
    - diff 按原样的字节、base64 编码传回，不是 UTF-8 的提交也不会被改动。
    - diff 超过 1 MiB 就拒绝，不截断。
    - 算 diff 之前先按对象头量大小，下面两种情况直接拒绝：
      - 改动的文件（改前或改后）有一个超过 4 MiB；
      - 所有改动的文件加起来超过 256 MiB。
  - `apply_check`：建一个临时索引，只放补丁涉及的文件（`ls-tree` 交给 `update-index --index-info`，经 `GIT_INDEX_FILE`），再跑 `apply --cached --check`。镜像和它的索引都不动，树的其余部分也不读。
  - git 怎么跑：
    - 不读用户和系统的 git 配置。
    - 属性从空树读（`GIT_ATTR_SOURCE`），也不读系统属性。
    - 忽略 replace 引用。
    - 路径按字面解释。
    - 不拿可选锁。
    - 单次分配不超过 256 MiB（`GIT_ALLOC_LIMIT`）。
    - 外面传进来的 `GIT_` 变量一律去掉。
    - 报错里的镜像路径换成 `<mirror>`；报错里引用的路径截到 200 个字符。
    - 只在镜像目录里找仓库，不往上找（`GIT_CEILING_DIRECTORIES`）：镜像目录要是还不是仓库、又恰好在别的仓库里面，git 会报错，而不是读外面那个仓库。
    - 这套环境放在新包 `internal/gitenv` 里，agentd 自己跑的 git（`internal/patch`、`internal/tasks`）也用它。
  - 两种错误分开报：
    - 工具错误：git 拒绝了输入，例如补丁打不上、超过上限、git 用完了它能用的内存或 CPU 时间。重试没用，所以不重试。
    - 协议错误：服务器没能干活，例如镜像读不了、git 不在、看不到这次任务的提交（agentd 在任务开始时已经在同一个镜像里找到过它，所以只能是镜像出了问题）。按失败处理，会重试，原因记进 agentd 的日志；git 的警告也随服务器的 stderr 进日志。
- **每次调用一个进程**（agentd 端的 `gitmcp.Client`）：
  - 经沙箱启动脚本起服务器，走 stdio。一次调用一个新进程：就算某个精心构造的仓库攻破了服务器，它也留不下任何状态影响下一次调用。
  - 每次调用新建一个目录 `/tmp/agentos-tools.<pid>.<随机>`（0700），调用结束就删。启动时清掉已经不在的 agentd 进程留下的目录。没有常驻目录，所以不怕 macOS 的 tmp_cleaner 删掉闲置目录，也不怕别的用户抢先占用这个名字。
  - 同时最多跑 4 个服务器。等空位最多 2 分钟；拿到空位后才开始算这次调用的超时（默认 1 分钟）。超时按失败处理、会重试：慢的可能是机器。拒绝太费力的提交靠启动脚本的 CPU 时间上限，那个对同样的输入每次都一样。
  - 单条回复和单条请求都有大小上限，分别够装下最大 diff 的 base64 和全是控制字符的最大补丁。
  - 启动脚本和它起的所有进程是一个进程组，超时或调用结束时整组 SIGKILL。
  - 服务器的 stderr 只进 agentd 的日志。返回给工作流的错误只说“失败了，详情看日志”。
  - 启动时做一次自检：在临时仓库上经启动脚本把两个工具各真调一次（apply_check 会写临时索引，顺带验证服务器能写的那个目录）。不通就拒绝启动，不会等到每个任务都失败才发现。
- **沙箱启动脚本**：
  - `sandbox/macos/run-tool.sh`（sandbox-runtime）：
    - 不允许任何网络。
    - 不能读：
      - 用户的家目录（从系统账户信息取，不看 `$HOME`）；
      - `/private/tmp` 和 `/private/var/folders`；
      - `AGENTOS_SANDBOX_DENY_READ`（一个 JSON 数组，路径里什么字符都可以有）里的路径：agentd 传数据目录、Control socket 和 Runtime socket 所在目录、Temporal 的 TLS 证书和私钥、每个镜像（包括这次调用的）。每个路径既按原样传，也按真实路径传；路径还不存在时，按已存在的上级目录解析。
    - 能读：这次调用的镜像、服务器二进制本身、这次调用的工作目录。不放行服务器所在的整个目录：sandbox-runtime 让放行目录之下的屏蔽规则优先，镜像要是放在二进制旁边，连它自己的调用都读不到。
    - 只能写工作目录。sandbox-runtime 默认放行写 `/tmp/claude`，这里也禁掉。
    - 每个进程最多 30 秒 CPU 时间，写的单个文件最大 64 MiB。
    - 清空环境变量。
    - 直接用真正的 git，不经过 `/usr/bin/git`：后者的 xcrun 会往沙箱外写缓存。
  - `sandbox/linux/run-tool.sh`（bubblewrap）：
    - 空的网络命名空间。
    - 只读挂载 `/usr`、镜像和服务器本身。
    - 私有的 `/tmp`，上限 64 MiB。根目录和 `/dev` 只读：它们是 bwrap 自己建的 tmpfs，大小可到内存的一半，可写的话会绕过 `/tmp` 的上限。
    - 清空环境变量。
    - 不许再建用户命名空间（`--disable-userns`）。
    - 每个进程：地址空间上限 4 GiB，最多 30 秒 CPU 时间，写的单个文件最大 64 MiB。
- **agentd**：
  - 新增 `git_tools` 一节：服务器路径（默认在 agentd 旁边）、沙箱启动脚本、超时。
  - 没配沙箱就拒绝启动；`--insecure-dev` 可以不用沙箱跑服务器，只用于开发，每次启动都打印警告。
  - 开发配置用 macOS 的启动脚本。
- **`git.apply_check` 要过两道检查**：
  - 先过 agentd 自己的严格检查：规则、两个工具各自的 deny_paths、`open_draft_pr` 永远拒绝的那批路径（两边共用 `githubtool.ProtectedPaths`）、按 hunk 位置精确应用。也就是 `open_draft_pr` 最终提交的内容。
  - 再过服务器沙箱里 git 自己的 `git apply --check`。
  - 两道都过才算通过。
- **报告评论的 outcome 超过 2000 字符就截断**，加上 ` [truncated]`，不再整条拒绝。工作流也先把 outcome 截到 4000 字符：comment_commit 的参数上限是 10 万字符，而错误信息可以任意长，报告却必须发出去。
- **agentd 解析任务的提交号也只看对象头**（`internal/tasks`）：先列出前缀匹配的对象，再查类型和大小，不再对可能巨大的提交做 peel。
- **真实 GitHub 上的 T2**（结果见下面“真实 GitHub 上的 T2”一节）：
  - `scripts/make-audit-target.sh` 用固定的作者和日期造 fixture，提交号固定（HEAD 是 `01f7b30c`）。
  - `tests/test_t2_live.py` 只能经 `live_stack` 这个 fixture 跑，要求 `AGENTOS_GITHUB=live`。
  - 令牌从单独的钥匙串条目 `agentos-github-test-token` 读。
  - 启动 agentd 之前先核对克隆下来的 HEAD 就是 fixture 的提交。

### 我定的几处

- **M3a 留下的问题，现在定为“两道都要过”**：模型给的行号不准时，git 能靠偏移打上补丁，但 agentd 的严格检查会拒绝。这样 apply_check 说能打上的，和 open_draft_pr 实际提交的，始终是同一份。
- **sandbox-runtime 会把沙箱里的 `TMPDIR` 改成它自己的 `/tmp/claude`**，那个目录不可写。所以启动脚本另传 `AGENTOS_TMPDIR`，告诉服务器能写的唯一目录。
- **每次调用的目录放在 `/tmp` 下**，和 Worker 启动脚本的做法一样。
- **show_diff 单个文件的上限定为 4 MiB，所有文件合计 256 MiB**。实测（M 系列 Mac，git 2.50）最费力的是随机短行文件：

  | 单个文件 | 耗时 | 内存 |
  | --- | --- | --- |
  | 1 MiB | 5 秒 | 96 MB |
  | 2 MiB | 11 秒 | 183 MB |
  | 4 MiB | 32 秒 | 356 MB |
  | 8 MiB | 超过 60 秒 | 660 MB |

  - 4 MiB 大约在 30 秒的 CPU 时间上限上下：要么算完后因为 diff 太大被拒，要么 git 在上限处被 SIGXCPU 杀掉、被拒。两种都不重试。
  - 代价：改了 4 到 8 MiB 文件的提交整个拒绝。正常的大 lock 文件只改几行，diff 算得很快，但也一样被拒。
  - 超限的提交整个拒绝，而不是去掉那个文件再显示：路径按字面解释时，没法用 pathspec 排除文件。
  - 合计上限对付的是“很多个大文件、每个只改一行”：每个文件都要整个读进来，耗时随总大小线性增长。
- **`GIT_ALLOC_LIMIT` 定为 256 MiB**：比两个 4 MiB 文件做 diff 时最大的那次分配（约 128 MiB）留出一倍余量。合法的提交对象、树对象远小于这个数。
- **拒绝按 CPU 时间判定，不按墙钟**：两个启动脚本给每个进程 30 秒 CPU（`ulimit -t`）。git 因此被 SIGXCPU 杀掉，算工具错误：同样的输入每次都一样。agentd 那边的 1 分钟墙钟超时按失败处理、会重试，因为慢的可能是机器（负载高、卷挂住了）。有了上面的上限，合法输入几秒内就能算完。`--insecure-dev` 不经过启动脚本，没有 CPU 上限，只有墙钟超时。
- **只有文件头的补丁**：`patch.Check` 拒绝既不新建、也不删除、又没有 hunk 的段落（git apply 会把它当成“没有补丁”）。新建空文件、删除空文件仍然允许，git 也接受。git apply 以 128 退出（不是补丁）时算“打不上”，不再当成服务器故障。

### 推送前审查（安全审查 + 对抗性审查）发现并修掉的问题

两个审查代理都没改文件，下面的问题都核实过、已修，并补了测试：

1. **精心构造的仓库能让 show_diff 看不到改动**（高）。工作树里的 `.gitattributes` 写 `*.py -diff`，或者文件里放一个 NUL 字节，diff 就只剩一句 “Binary files differ”，模型看不到代码。改法：`--text`，属性从空树读，不读系统属性。
2. **replace 引用能换掉被审计的提交，也能换掉 open_draft_pr 写进去的文件**（中）。`git clone --mirror` 会把 `refs/replace/*` 一起拉下来。改法：服务器、`internal/patch`、`internal/tasks` 的 git 都设 `GIT_NO_REPLACE_OBJECTS=1`。
3. **很小的仓库能让 git 用掉无限内存**（中）：输出炸弹、大树、大文件。改法：
   - 输出边读边计数，超限就停掉 git。
   - apply_check 的临时索引只放补丁涉及的文件，不再 `read-tree` 整棵树。
   - show_diff 的单文件上限（上面那条）。
   - Linux 上 `/tmp` 限 64 MiB、地址空间限 4 GiB。
   - 同时最多 4 个服务器。
4. **服务器端的任何失败都被当成 git 拒绝输入**（中）：临时故障让任务直接结束，启动脚本坏了却一直重试。改法：工具错误和协议错误分开报（见上），agentd 启动时自检。
5. **diff 只要有上限的三分之一就会撑破回复上限，然后被重试 5 次**（中）。SDK 会把结构化结果再转义一遍放进文本，JSON 转义最多放大 6 倍。改法：工具自己给一句短文本，diff 用 base64 传，上限按编码后的大小算。
6. **不是 UTF-8 的字节被悄悄替换**（中），审计的 diff 和提交的 diff 不一样。改法：同上，base64 传原样的字节。
7. **apply_check 说能打上、open_draft_pr 却一定拒绝的补丁**（低）：`.github/**` 那批路径只在开 PR 时检查。改法：两边共用一张表。
8. **macOS 上超时的服务器在调用结束后还活着**（低）：只杀了启动脚本。改法：进程组整组杀，调用结束后再杀一次。
9. **服务器的 stderr 进了错误信息**（低）：长的 stderr 会让最终报告发不出去，还会暴露本机路径。改法：stderr 只进 agentd 的日志；评论的 outcome 改为截断。
10. **macOS 沙箱放行的比注释写的多**（低）：能写 `/tmp/claude`，能读别的镜像、TLS 证书私钥、`/tmp` 下别的调用的目录。改法：见上面的启动脚本。
11. **live 模式影响整套测试，还复用正式的钥匙串条目**（低）。改法：见上面的 T2。
12. **调用目录没人清理**（审查列为遗留风险）：agentd 在调用中途被杀（T1 就这么干），目录就留在 `/tmp`。改法：目录名带上进程号，启动时清掉已经不在的进程留下的。
13. **Linux 上沙箱里还能再建用户命名空间**（审查列为遗留风险）。改法：`--disable-userns`。

我自己又发现三处：

- **Linux 沙箱的根目录可写，而且没有大小上限**（补探针时发现）。bwrap 自己建的根目录是一个 tmpfs，归沙箱里的用户所有，上限是内存的一半。写进去的东西不会出现在宿主机上，但被攻破的服务器可以绕过 `/tmp` 的 64 MiB 上限，把宿主机内存写满。现在加了 `--remount-ro /`，只有 `/tmp` 能写。
- **sandbox-runtime 只解析一部分符号链接**（补探针时发现）。denyRead 里写 `/etc/hosts`，沙箱里照样能读 `/etc/hosts`：Seatbelt 按真实路径 `/private/etc/hosts` 匹配，而 sandbox-runtime 只把 `/tmp/...`、`/var/...` 解析到 `/private` 下，别的符号链接都保留原样（比如 `/etc`，或者镜像自己的链接）。agentd 传的路径只要经过这样的链接，原先就屏蔽不了。现在启动脚本把每个路径的真实路径也加进去。（这一条原先写成“`/tmp`、`/var` 下的都屏蔽不了”，第三轮复审指出不对：这两处 sandbox-runtime 自己会解析。）
- **最大的补丁装不进一条请求**。服务器每条请求上限 1 MiB；补丁上限 256 KiB，但控制字符在 JSON 里要转义成 6 个字节，最多约 1.5 MiB。超限的请求让服务器读失败，被当成故障重试 5 次。现在上限按最坏情况算，并用真实的二进制测了一个全是控制字符、大小到上限的补丁。

### 复审（第二轮安全审查 + 对抗性审查）发现并修掉的问题

上面的修复做完后，又开了两个审查代理只看这些修复。它们也没改文件，下面的问题都核实过、已修，并补了测试：

1. **超大的提交对象和树对象绕过所有内存上限**（中）。一个 512 MiB 的提交信息，打包后只有 0.5 MB。服务器的四条 git 命令和 agentd 自己的 `rev-parse` 都要把它整个读进来，各用 500 多 MB，而得到的 diff 只有 99 字节。改法：
   - 提交号只看对象头（`cat-file --batch-check`），超过 1 MiB 不读。agentd 解析任务提交号时也一样。
   - 所有 git 设 `GIT_ALLOC_LIMIT=256m`。撞到上限算工具错误，在 agentd 里算违规。
   - 笔记里原来写的“最坏约 550 MB”不对，已按实测改正（见上面的表）。
2. **合并提交的 diff 包含对每个父提交的 diff**（中，两个审查都发现了）。`-m --first-parent` 对 diff-tree 不起“只看第一个父提交”的作用：`--first-parent` 只管遍历历史。结果是主线自分叉以来的所有改动都被当成这个合并带进来的。改法：`--diff-merges=first-parent`，加了合并提交的测试。
3. **commit() 把 git 的任何失败都说成“镜像里没有这个提交”**（中）。镜像读不了（worktree 的 gitdir 在家目录里、正在重新 clone）时，每个任务都以“没有这个提交”结束，不重试，也不记日志。改法：只看对象头；“missing”或类型不对才算工具错误，git 自己出错算协议错误。
4. **macOS 会删掉闲置的调用目录根**（中）。系统的 tmp_cleaner 每天删 `/tmp` 下 3 天没动过的空目录。`/tmp/agentos-tools.<pid>` 在两次调用之间是空的，删掉后每次调用都失败，直到 agentd 重启。改法：不再有常驻目录，每次调用直接在 `/tmp` 下新建自己的目录。
5. **很多个大文件、每个只改一行的提交**（中）。两个上限都没超，但 diff 会跑过 1 分钟的超时，然后被重试 5 次，每次都占一个空位。等空位的时间还算在调用的超时里，别的任务会因为“没有空位”失败。改法：
   - 所有文件合计 256 MiB 的上限。
   - 拿到空位后才开始算超时，等空位另有 2 分钟上限。
   - 超时算工具错误（第三轮复审后改为：按 CPU 时间判定拒绝，墙钟超时会重试，见下）。
6. **很长的路径让报告发不出去**（中）。一个 10 万字符的路径进了拒绝信息，工作流把它写进 outcome，超过 comment_commit 的参数上限，任务失败，也没发报告。改法：报错里的路径截到 200 字符，工作流把 outcome 截到 4000 字符。
7. **Linux 的 `/dev` 和 `/dev/shm` 也是不限大小的可写 tmpfs**（低），可以绕过 `/tmp` 的上限。改法：`--remount-ro /dev`。
8. **只有文件头的补丁**（低）能过 agentd 的检查，再让 git apply 以 128 退出，被当成服务器故障重试 5 次。改法：见上面“我定的几处”。
9. **钥匙串探针是假通过**（低）。探针的 HOME 不是用户的，security 根本找不到钥匙串，不在沙箱里也一样查不到。改法：显式指定登录钥匙串的文件，沙箱外用同样的环境先查到一次。
10. **屏蔽名单的探针其实被整块屏蔽挡住了**（低）。账本、别的镜像都在 `/var/folders` 下，启动脚本整块屏蔽了那里，名单写错也看不出来；测试还自己抄了一份名单。改法：
    - 整个栈放到 `/var/tmp`，那里不被整块屏蔽，而且 macOS 上要经符号链接。
    - 用一个记录用的启动脚本，录下 agentd 传出的名单，再把它交给探针。
    - 名单的内容由 agentd 的单元测试检查，包括 TLS 证书私钥和 Runtime socket。
11. **带冒号的路径会被拆错**（低）。原来用冒号分隔，镜像目录名里有冒号就屏蔽不了。改法：名单改成 JSON 数组。

另外两条审查列为遗留风险的，也顺手改了：

- 自检原来只调 show_diff，服务器写不了临时目录也能通过。现在也调 apply_check。
- apply_check 和 open_draft_pr 各读各的 deny_paths，“apply_check 放行的补丁 open_draft_pr 一定接受”只在两份一样时成立。现在 apply_check 两份都用。

### 第三轮复审发现并修掉的问题

又开了一个对抗性审查代理，只看第二轮的修复。下面的问题都核实过、已修，并补了测试：

1. **镜像放在服务器二进制旁边时，连它自己的调用都读不到**（中）。macOS 启动脚本放行了服务器所在的整个目录，而 sandbox-runtime 让放行目录之下的屏蔽规则排在后面、优先生效。比如二进制在 `/opt/agentos/`、镜像在 `/opt/agentos/mirrors/` 下，每次调用都失败、重试 5 次。自检用的仓库在 `/tmp` 下，查不出来。改法：只放行二进制本身（原样和真实路径）。
2. **“missing” 又成了永久拒绝**（中）。镜像正在重新 clone，或者对象放在沙箱外的 alternates 里，git 会回答 “missing”、退出码 0，任务就以“没有这个提交”结束，不重试，没有日志。可提交号是 agentd 在任务开始时在同一个镜像里找到的，所以 “missing” 只能是镜像的问题。改法：算协议错误；git 的警告随服务器的 stderr 进 agentd 的日志。
3. **握手之前的超时也成了永久拒绝**（低）。启动脚本卡住（挂住的外接卷、内存换页）时，服务器根本没拿到输入，“同样的输入一样慢”不成立。改法：拒绝改按 CPU 时间判定（见上面“我定的几处”）。
4. **Linux 上撞到地址空间上限还是会重试 5 次**（低）：git 报的是 “Out of memory, malloc failed” 或 “mmap failed”，不是分配上限的那句。改法：这两句也算“太大”。
5. **被攻破的服务器能让自己的调用目录删不掉，在 macOS 上还能写满磁盘**（低）：把目录改成 000，`os.RemoveAll` 不改权限。改法：删不掉时先把目录的权限改回来再删；启动脚本限制单个文件 64 MiB。

提交后，自动的安全审查又指出第 5 条的第一版改法有竞态（中）：先判断“是目录”、再按路径 chmod，中间可以把目录换成指向用户文件的符号链接，agentd 的 chmod 就落到沙箱外了。条件是 macOS 上被攻破、又用 `setsid` 逃出进程组的服务器还活着。改法：
- 平时只删一次，删不掉才去改权限。
- 改权限全程经文件描述符（`fchmodat` 加 `AT_SYMLINK_NOFOLLOW`、`openat` 加 `O_NOFOLLOW`），从不经过符号链接。
- 启动时的清扫只碰属于本用户的真实目录。
- Linux 上这要 `fchmodat2`（内核 6.6 起）；不过 Linux 沙箱根本不挂载宿主机上的调用目录。

审查列为遗留风险的，也改了两条：

- **git 会往上找仓库**：镜像目录要是还不是仓库、又在一个检出的仓库里面（开发配置正是这样放的），agentd 那边沙箱外的 git 会读外面那个仓库。改法：`GIT_CEILING_DIRECTORIES`。
- **测试没检验启动脚本的路径解析**：`/var/tmp` 下的路径 sandbox-runtime 自己就会解析，去掉启动脚本的解析，测试照样通过。改法：另一个镜像改用测试自己建的符号链接配置。验证过：去掉启动脚本的解析，这个测试就失败。

## M3b 补充：agentd 不再自己读镜像（2026-10-18）

M3b 三轮审查都把这一条列为最大的遗留风险：agentd 自己在沙箱外对不可信的镜像跑 git。`internal/patch.MirrorSource`（`git ls-tree -l`、`git cat-file blob`，apply_check 和 open_draft_pr 都要经过它）和 `internal/tasks.resolveCommit`（任务开始时的 `git rev-parse --disambiguate`、`git cat-file --batch-check`）都是这样。精心构造的对象要是触发了 git 的漏洞，代码就以 agentd 的身份运行，而 agentd 持有 API 密钥。现在这些读取都挪到了沙箱里的 git MCP 服务器后面。agentd 自己只在自检时、在它自己新建的临时仓库上跑 git，不再碰任何镜像。

合并为 PR #12。设计文档 rev 299 按你批准的清单改了信任边界的写法：第 3 节（validate_patch 一行、“触发”一条、威胁表“借仓库逃逸”一行）、第 4 节（开头一段、组件表“MCP 工具服务器”一行）、第 8 节（威胁表新增“解析不可信数据的代码被攻破”一行）、第 12 节（M3b 一条）。

### 做了什么

- **服务器加两个工具**（`internal/gitmcp`）：
  - `resolve_commit`：7 到 40 位十六进制数字，换成它指的那一个提交的完整 SHA。和原来 agentd 的做法一样只看对象头：`rev-parse --disambiguate` 列出前缀匹配的所有对象，`cat-file --batch-check` 查类型和大小。
    - 拒绝（工具错误）：
      - 格式不对；
      - 没有这个提交（只有 blob、树或 tag 对象匹配也算）；
      - 匹配到两个以上提交；
      - 提交对象超过 1 MiB；
      - 前缀匹配的对象列表超过 1 MiB（只有构造出来的仓库才会这样）。
    - 协议错误：镜像读不了、git 自己出错；还有什么都没找到、但 git 在 stderr 上说有对象读不了（比如 alternates 在沙箱外），这时“没有”不可信。
  - `read_files`：一个提交和最多 20 个路径，返回每个路径的模式、类型、大小，以及不超过 1 MiB 的 blob 的内容（base64，原样的字节）。
    - 每个路径最多两次 `ls-tree`，不管多深：
      - 先 `ls-tree -t` 只查这个路径：git 显示路上的每一层目录和路径本身，不列这些目录里的其他文件。
      - 路径上什么都没有时，看最深的那层目录下面那一段：再单独查它一次。它不在，路径就是“没有”；它在（只能不是目录：文件、符号链接、子模块），就报 `not_dir`。
      - 原来的做法是把路径和所有上级目录一起交给 `ls-tree`，git 会把每个上级目录整个列出来，路径很深时参数还会超过系统上限。
    - 内容用一次 `cat-file --batch` 读，先按 `ls-tree -l` 给的对象头核对大小。超过 1 MiB 的文件只报大小，不读内容。
    - 拒绝：
      - 提交号不是完整的 SHA、不是提交、提交对象超过 1 MiB；
      - 路径数不是 1 到 20，或者有重复；
      - 路径不是从顶层起的普通路径：绝对路径、`.`、`..`、多余的斜杠、控制字符、超过 4096 字节；
      - 构造出来的树：路上或路径本身的名字列了两次、给文件的模式配了树或提交对象、路上的目录列出来超过 1 MiB（一千来层深，名字越长层数越少；4096 字节的路径最多也只有 2048 层）。
    - 协议错误：镜像里没有这个提交（任务开始时 resolve_commit 找到过它，所以只能是镜像变了）、git 自己出错。
  - git 把路径按字节原样处理：在 macOS 上建的仓库会设 `core.precomposeUnicode`，git 会把分解形式的 Unicode 路径换成组合形式再查。`internal/gitenv` 现在用 `GIT_CONFIG_COUNT` 把它关掉。
- **agentd 这边**（`gitmcp.ResolveCommit`、`gitmcp.ReadFiles`）：
  - read_files 每次只问一个路径。这样服务器的任何一条回复都不超过 show_diff 的上限（约 2 MiB，一个 1 MiB 的文件编成 base64 约 1.4 MiB）。被攻破的服务器能让 agentd 解码的东西就有了上限：SDK 把结构化结果解成 `any`，最坏的形状要几十倍于回复大小的内存。
  - 回复里的 JSON 值超过 1000 个就拒收，不再解码成结果类型：诚实的回复只有十几个值，而几百万个小值解码时每个都会变成一个结构体（审查实测：一条 40 MiB 的回复能让 agentd 涨到 7 GB）。数不了的类型（SDK 哪天改成保留原始 JSON）也拒收，不当成一个值放过。
  - 核对服务器的回答，能核对的都核对，对不上的算失败（会重试），不算拒绝：
    - 解析出的提交号必须是 40 位，而且以给出的数字开头（数字本身先查格式）。
    - 回答的路径就是问的路径。
    - 模式只能是 `ls-tree` 会显示的五种之一，类型和模式对得上；`not_dir` 只能出现在路径上什么都没有时，而且必须是路径的上级目录。
    - 只有不超过 1 MiB 的 blob 带内容，内容长度等于报的大小。
  - 服务器的文字（拒绝，以及 apply_check 说补丁打不上的原因）最多 4 KiB，去掉 agentd 给的镜像路径：它会进工作流，可能进公开的报告。
  - 服务器的 stderr 在它退出之后才记进 agentd 的日志：拒绝时记 Info，失败时记 Warn。原来失败时立刻记，stderr 有时还没读完（复审实测：并发时约百分之三的失败日志里 stderr 是空的）。
  - read_files 的一连串调用只排一次队（`Client.InOneSlot`）：拿到一个槽后，所有路径都在这个槽里问完。不然 20 个文件的补丁在槽位紧张时要排 20 次队，每次最多 2 分钟，可能拖过活动的 10 分钟上限，然后整个重来。
- **`patch.MirrorSource`** 改成经 read_files 读出补丁涉及的所有文件（`patch.Source` 改成批量读）：
  - 规则不变：只认普通文件（100644 blob），上面的目录必须是目录，文件不超过 1 MiB。
  - 服务器的拒绝算违规，失败照旧重试。读到的内容长度和大小对不上也算失败：绝不把没读全的文件当成空文件。
  - 补丁照旧在 agentd 里用 go-gitdiff 应用。`git.apply_check` 和 `github.open_draft_pr` 都经过它。
- **任务开始时解析提交号**（`tasks.resolveCommit`）改调 resolve_commit：
  - 服务器拒绝的，agentctl 得到 InvalidArgument，说法和原来一样。
  - 服务器出了故障的，得到 Unavailable（`tasks.Unavailable`），只说“失败了，详情看 agentd 的日志”，可以稍后再试。原来两种都是 InvalidArgument。
  - 任务启动用自己的 2 个槽（`Client.WithOwnSlots`）：正在跑的任务的工具调用再慢，也挡不住别的任务启动。所以同时最多 6 个服务器（工具调用 4 个，任务启动 2 个）；解析提交号的服务器很轻。
- **自检**改成四个工具各调一次：服务器二进制比 agentd 旧、缺了工具时，agentd 也拒绝启动。用 sandbox-runtime 时每次调用约 0.16 秒。
- **顺带修掉一个 M3b 的问题**：补丁新建文件时，只要那个文件在顶层，或者它所在的目录还没有，原来的 MirrorSource 就报 `git ls-tree: unexpected entry ""`（git 什么都没列出来）。这不算违规，于是被重试，最后整个调用失败。现在这种文件就是“不存在，可以新建”。用 origin/main 的代码复现过。

### 我定的几处

- **服务器只报事实，规则留在 agentd**：read_files 报每个路径是什么（模式、类型、大小、内容、哪个上级不是目录），哪些能改由 `internal/patch` 决定，补丁规则还在一处。所以符号链接、可执行文件这类 blob 的内容也会传回来（都不超过 1 MiB），agentd 再拒绝。
- **服务器一次收最多 20 个路径，agentd 每次只问一个**：工具本身照任务的要求收 20 个；问几个是 agentd 对内存的取舍。代价是每个文件起一次沙箱进程（macOS 上启动一次约 0.16 秒），20 个文件的补丁要 20 次；常见的一两个文件感觉不到。
- **路径最长 4096 字节**（Linux 的 `PATH_MAX`）：只是服务器的输入上限。`internal/patch` 本来就只收字母、数字和 `._+-`。
- **测试辅助包 `internal/gitmcp/gitmcptest`**：构建真实的服务器二进制（或用 `AGENTOS_TEST_MCP_GIT` 指定的）。patch、tasks、githubtool 的测试都经它调用真实的服务器，只是不加沙箱。

### 推送前审查（安全审查 + 对抗性审查）发现并修掉的问题

两个审查代理都没改仓库里的文件，下面的问题都核实过。

安全审查（没有高、中危，四条低危）：

1. **在 fsck 通不过的树上，上级目录查得比原来少**（低）：同时有 blob `a` 和目录 `a` 时接受 `a/b`；条目名里带 `/` 时把 `a/b/c` 当成没有。原来一次列出所有上级目录，会报“`a` 不是目录”。没改代码，记进“留到后面”：这些树 fsck 都会拒绝。
2. **构造的树给文件的模式配了树或提交对象，被当成故障重试**（低）。改法：`cat-file` 的回答说对象是别的类型时，算拒绝。
3. **遗留风险写轻了**（低）：被攻破的服务器还能谎报类型（让草稿 PR 删掉整个目录、子模块），解析提交号也不限于镜像里的提交。改法：改正“留到后面”的写法。
4. **服务器给的字符串没有约束，回复上限对所有工具都放大了 20 倍**（低）。改法：核对模式、类型和 `not_dir`；拒绝的文字截到 4 KiB；数字先查格式；回复上限见下面对抗性审查第 1 条。

对抗性审查：

1. **被攻破的服务器用一条 read_files 回复能让 agentd 涨到约 7 GB**（中）：40 MiB 的 `{"files":[0,0,0,...]}`，SDK 先解成 `any`（约 1 GB），再经 Marshal、Unmarshal 时每个元素都变成一个 `File`。同时 4 个调用就是约 30 GB，每次 Temporal 重试都会再来一遍。改法：每次只问一个路径，回复上限回到约 2 MiB；超过 1000 个值的回答直接拒收。
2. **根树构造得很大时 read_files 会超时、被重试，而且任务启动现在要和工具调用抢那 4 个槽**（中低）：一个 238 MB 的根树（打包后 9.4 MB），每次 `ls-tree` 约 0.5 秒；20 个很深的新文件要 240 次 `ls-tree`，超过 1 分钟。改法：`ls-tree -t`，每个路径最多两次；任务启动用自己的槽。
3. **alternates 在沙箱外时，resolve_commit 报“没有这个提交”，日志里什么都没有**（低中）：git 退出码 0、什么都不输出，原因只在 stderr。改法：什么都没找到而 git 有抱怨时算协议错误；服务器拒绝时也把它的 stderr 记进日志。
4. **macOS 上建的镜像会把分解形式的 Unicode 路径换掉**（低，目前到不了：补丁只收 ASCII）。改法：`core.precomposeUnicode=false`。

审查还补了几处测试缺口：顶层新文件、git 有抱怨的 resolve_commit。

### 复审（对这些修复的对抗性审查）发现并修掉的问题

没有高、中危：每条修复在合法的输入上都做到了它说的。复审拿随机构造的树比对了新的查找和 git 自己的回答（几百次查询，两个 git 版本），也查过 resolve_commit 在健康的镜像上从不误报“读不了”（裸仓库、gc 过的、浅克隆、partial clone、带 commit-graph 和 bitmap 的等等）。几条低危：

1. **失败时的日志常常丢掉 git 的话**（低）：见上面“服务器的 stderr 在它退出之后才记”。
2. **值个数的上限假定 SDK 把结果解成 map 和 []any**（低）：别的类型会被当成一个值放过，而且删掉这道检查测试照样通过。改法：数不了的类型拒收；用测试二进制自己扮演一个被攻破的服务器，经真实的进程测 `Call`（值太多、很长的拒绝、失败和拒绝时的 stderr 日志）。
3. **每个路径各排一次队，槽位紧张时可能拖过活动的超时**（低）。改法：`InOneSlot`。
4. **apply_check 说补丁打不上的原因没有截短**（低，M3b 起就有）。改法：和拒绝一样经 `gitmcp.Reason`。
5. **笔记里几处数字不准**（同时最多几个服务器、被攻破的服务器能让 agentd 用掉多少内存、多深的目录会超过 1 MiB），已改正。

另外：`WithOwnSlots` 收到 0 或负数时和 `Options.Parallel` 一样当成 4（原来会建一个无缓冲的通道，每次调用都等满 2 分钟）。`patch.MirrorSource` 里“内容长度和大小对不上”的检查只是兜底：`gitmcp` 那边的核对先挡住了，而两边的上限一样时（有测试保证）它本来就走不到，没有测试覆盖它。

### 留到后面

- **服务器的回答在内容上是被信任的**（补丁涉及的文件已改：开 PR 前对照 GitHub 核对，见下面的“M3b 补充二”。解析出的提交号只确认了 GitHub 取得到这个提交，还不够，见那一节的“留到后面”；diff 和拒绝的文字照旧）。被攻破的服务器（精心构造的对象触发了沙箱里 git 的漏洞）能谎报这个仓库自己的内容：
  - diff：M3b 起就是这样，模型看到的可能不是真实的改动。
  - 补丁涉及的文件：它能谎报内容，也能谎报类型。open_draft_pr 把谎报的内容当成原文件，打上补丁后提交到草稿 PR，作者是 agentos 的身份。补丁删除或修改的路径在真实的树里要是目录、子模块、符号链接或可执行文件，而服务器说是普通文件，那么删除会删掉那里的整个东西（go-github 的 CreateTree：整个目录可以这样删掉），修改会把它变成普通文件。范围：只限补丁点名的路径（最多 20 个），受保护的路径和 deny_paths 照样拒绝，内容必须是 UTF-8、不超过 1 MiB；草稿 PR 要人审（M4 的审批单还会列出补丁和改动的文件）。
  - 解析提交号：agentd 接受任何以给出的数字开头的 40 位 SHA，不一定是镜像里的提交，比如只在某个 fork 里的提交（GitHub 经父仓库也能取到它）。给完整 SHA 就没有余地。
  - 拒绝的文字：最多 4 KiB 服务器读得到的任何东西（macOS 的沙箱按黑名单屏蔽，`/etc` 这类是读得到的），可能进公开的报告。diff 和文件内容本来就是这样的通道。
  - 比原来小得多：原来是 agentd 自己的 git 被攻破，等于 agentd 被攻破。
  - 改法：开 PR 之前，用 GitHub 的 Git Trees API 查被审计提交里每个补丁涉及的路径，比对模式、类型和 blob SHA：新建的文件那里必须什么都没有，修改和删除的必须是 100644 的 blob，SHA 和 agentd 收到的内容算出来的一致；再确认解析出的 SHA 在 GitHub 上是个提交。
- **构造的、fsck 通不过的树**：查找假定树是合法的。在 fsck 会拒绝的树上（同一层里同名的 blob 和目录、条目名里带 `/`、条目没排序、目录模式配了 blob 对象），read_files 看到的可能和原来一次列出所有上级目录时不同（比如同时有 blob `a` 和目录 `a` 时接受 `a/b`；原来报“`a` 不是目录”），或者以协议错误失败、被重试。open_draft_pr 的基础是 GitHub 上的同一个提交，SHA 相同就是同样的对象，而 GitHub 推送时会检查对象（没实测）。改法：以后自动建镜像时，fetch 打开 `fetch.fsckObjects`（或 `transfer.fsckObjects`），这些形状都会被拒绝（本地用 `receive.fsckObjects` 测过）。
- **agentd 的内存**：诚实的最大回答（一个 1 MiB 的文件）约 1.4 MiB。被攻破的服务器最坏能让 agentd 为一条约 2 MiB 的回复分配约 75 到 130 MB、占住 45 到 90 MB 的堆（SDK 解成 `any` 的那一步，复审实测；最坏的形状是几十万个空对象），同时最多 4 个工具调用加 2 个任务启动。和 show_diff 自 M3b 起一样。
- **每次调用都要读根树**：每个路径最多两次 `ls-tree`，每次都读一遍根树。根树构造得很大（几百 MB，打包后几 MB）时，每个文件要一两秒，20 个文件的补丁要半分钟左右，一直占着槽，但每次调用都在超时之内。
- **对象在沙箱外的 alternates 里的镜像**：任务开始时报 Unavailable，原因（git 读不了的目录）在 agentd 的日志里。只影响配置镜像的人。
- **SHA-256 的镜像**：resolve_commit 一直报协议错误（Unavailable），而不是拒绝。只是配置问题。
- **`gitmcp.Options.DenyRead` 为空时**（M3b 起就有，agentd 里到不了：`toolDenyRead` 从不为空）：JSON 是 `null`，启动脚本解析失败，每次调用都失败。
- **补丁可以同时新建 `a` 和 `a/b`**（已改，见“M3b 补充二”；和这次的改动无关，M3a 起就有）：`patch.Check` 不查一个路径是不是另一个的上级目录。`a` 已经存在时，agentd 的检查会拒绝（是目录就“不是普通文件”，是文件就“`a` 不是目录”）；两个都是新文件时都能通过，`git apply --cached --check` 也接受（测过）。于是 open_draft_pr 交给 GitHub 的树里同时有文件 `a` 和 `a/b`，GitHub 会怎么处理没测过。`patch.Check` 可以直接拒绝这种补丁。

## M3b 补充二：开 PR 前对照 GitHub 核对补丁涉及的文件（2026-10-18）

上一节“留到后面”的第一条：被攻破的 git 工具服务器能在 read_files 里谎报补丁涉及的文件，内容和类型都能谎报。open_draft_pr 原来照单全收：删除一个其实是目录或子模块的路径，会把它整个删掉（go-github 的 CreateTree）；修改一个其实是符号链接或可执行文件的路径，会把它变成普通文件；内容只要过得了补丁规则就行。解析出的提交号也只核对了以给出的数字开头。现在 open_draft_pr 在写任何东西之前，先对照 GitHub 上的被审计提交核对这些文件。解析出的提交号只确认了 GitHub 取得到它，这一条两个审查都判为高危，要用户定怎么改（见“留到后面”第一条）。

合并为 PR #15。设计文档 rev 309 按你批准的清单改了：第 3 节（步骤表 open_pr 一行的“做什么”和“失败时”、威胁表“借仓库逃逸”一行）、第 6 节（第 1 步里 max_per_run 算哪些写、第 3 步的 DENIED、“open_draft_pr 是组合操作”一条）、第 8 节（威胁表“解析不可信数据的代码被攻破”一行剩下的风险）、第 10 节（“绑定”一条的载荷内容）、第 12 节（M3b 一条的补充）、第 13 节（新增待定问题：开 PR 的提交是否必须在 base 分支的历史里）。rev 310 又按你的同意改了第 13 节开头一句：表后还剩两条待定问题，不再说只剩外部访谈。

### 做了什么

- **载荷记下每个文件原来是什么**：`patch.Apply` 对 read_files 读到的原内容算 git 的 blob SHA-1（`patch.BlobID`，和 `git hash-object` 一样），记在 `patch.Change.OldBlob` 里。载荷里每个文件要么写 `old_blob`，要么写 `"new": true`（新建，服务器说那里什么都没有）。
- **`OpenDraftPR.Execute` 在第一个写请求（CreateTree）之前**：
  - 用 `Git.GetCommit` 取被审计的提交。404 算拒绝：GitHub 上没有这个提交，或者令牌看不到这个仓库。回答的 SHA 和问的不一样算失败，会重试。
  - 从这个提交的树开始，用 Git Trees API（不带 recursive）逐层列出每个路径上的目录：
    - 新建的文件：那里什么都没有，路上已有的只能是目录（040000 tree），同一层也不能有只差大小写的名字（`App/x.py` 旁边有 `app`、`app/DB.py` 旁边有 `app/db.py`、`app/setup.py` 旁边有 `app/ſetup.py`（长 s），在不分大小写的检出里是同一个路径；补丁规则也这样分辨路径）。名字先转大写再转小写来比，长 s、开尔文符号这类只转小写看不出来的也算；
    - 修改和删除的文件：100644 的 blob，SHA 等于 `old_blob`；
    - 既没写 `old_blob` 也没写 `new` 的载荷（这次之前的格式）：拒绝。
  - 每棵树（按 SHA）只列一次。一个列表最多读 8 MiB（约 4 万个条目），一次核对最多读 64 MiB，超过都算拒绝。列表里只留下补丁路径的某一段（不分大小写）叫到的条目，其余的读完就丢。
  - GitHub 截断的列表、同一个名字列了两次：拒绝（同一棵树每次列出来都一样）。
  - GitHub 的失败（5xx、超时、限流）和这个工具的其他请求一样处理：算没发出，重试；4xx 算 GitHub 拒绝。
  - 要拒绝时先看载荷的分支在不在：GitHub 上什么都没有，才是“没发出”。分支在，可能是之前的一次尝试已经发出了一部分（恢复后的重发），改报 ConflictError，记录转 UNKNOWN，由人核对。看不出来时也一样：令牌看不到仓库时 GitHub 对什么都回 404，分支也是，所以 GetCommit 回 404 时先确认仓库看得见（`GET /repos/{o}/{r}`）；查分支被拒（403 之类）也交给人。GitHub 失败（5xx、超时、限流）照常重试。
- **网关**：Execute 返回 `tools.DeniedError`（只在什么都没发出时）时，记录改为新的状态 DENIED，原因写进记录，工作流得到 denied，报告照发。同一调用再来还是 denied，什么都不发。DENIED 算进 max_per_run：核对本身要发 GitHub 请求，被攻破的 Worker 不能拿一个个新补丁让它一遍遍核对（见下面第二轮审查）。原来这种错误会走“结果不明”的恢复：unsafe 类直接转 UNKNOWN 等人核对，lookup 类先查、再重发，每次都再被拒绝。
- **`patch.Check`**：
  - 一个路径是同一补丁里另一个路径的上级目录时拒绝，比如同时新建 `a` 和 `a/b`，或者删掉文件 `a`、新建 `a/b`。和 deny_paths 一样不区分大小写。
  - 路径最多 32 段（`patch.MaxDepth`）：核对要逐层列目录，一次核对最多列 20 × 32 = 640 次。
- **githubsim**：`--repo owner/name=目录` 给它一个仓库的本地副本，GitHub 就有这个副本里的提交和树。`GetCommit` 返回真实的树和父提交，没有的提交回 404；列树按 `git ls-tree -l` 列一层。故障文件的 `entries` 能按名字改所有列表里的条目（mode、type、sha），让 GitHub 和镜像对不上。没给副本的仓库照旧：任何 40 位 SHA 都是提交。`GET /repos/{o}/{r}` 对任何仓库都回 200（令牌看得到）。harness 把镜像交给它。

### 我定的几处

- **核对放在 Execute，不放在 Prepare**：
  - 载荷只在第一次调用时渲染、记录一次。没配 GitHub 的 agentd 没有客户端，Prepare 核对不了；这份载荷之后却可能由配了 GitHub 的 agentd 发出去：agentd 在记录和记成 DRY_RUN 之间停了，重启时配上了 GitHub，记录还是未领取的 PENDING，下一次调用就领取、发出。放在 Execute，每次发出之前都核对，包括恢复后的重发和核对后改回 PENDING 的重发。
  - 所以 dry-run 不核对：它不执行，GitHub 一个请求都不发，读也不读。它的结果和载荷按服务器读到的内容渲染，载荷里的 `old_blob`、`new` 写明当时以为每个文件是什么。按任务开的 dry-run（agentd 配了 GitHub）也一样：评测（第 11 节）要跑很多 dry-run，不该花 GitHub 的配额。
  - 代价：M4 的审批单上的载荷没核对过，审批人批了，执行时才可能被拒绝。M4 可以在生成审批单时做同样的只读核对。
- **用 Git Trees API，不用 contents API**：contents API 看不出可执行位；路径是指向仓库里普通文件的符号链接时，它返回的是目标文件（GitHub 文档这样写），符号链接就能冒充普通文件。
- **不带 recursive，逐层列**：带 recursive 一次能列整棵树，但有 10 万条、7 MB 的上限，大仓库会被截断，还得另写一套逐层的。逐层只列路上的目录：修一两个文件的补丁通常三到六个请求。列多少次由补丁决定（每个路径最多它的段数），所以诚实的补丁不会因为列表次数被拒；上限来自路径深度。
- **GetCommit 404 算拒绝（denied），不算 GitHub 拒绝（FAILED）**：这是 agentd 自己的核对没通过，和文件对不上一样，结果都是不开 PR、照发报告。
- **blob SHA 用 Go 的 `crypto/sha1`，没有碰撞检测**：比对的另一方是 GitHub 上的对象，而 GitHub 收对象时用带碰撞检测的 SHA-1（sha1dc），SHAttered 那类碰撞块进不去。被攻破的服务器也就拿不出 SHA 相同、内容不同的文件。
- **拒绝记成新的状态 DENIED，不用 ABANDONED**：两者对工作流都是 denied，区别在 max_per_run。ABANDONED（取消、M4 审批被拒或被修改）不算数，修改后的补丁才能再走一遍；DENIED 算数。自带的工作流被拒以后就发报告结束，不会换补丁再试，所以不受影响。只在 GitHub 上没有分支时才拒绝（见上）。
- **在 github.com 上实测过 githubsim 照着做的回答**（2026-10-18，测试仓库 jchen0426/agentos-audit-target，只读请求）：目录的模式是 `040000`；不带 recursive 的回答里 `truncated` 是 false；`app/db.py` 的 blob SHA 是 `40f0c5d58706e66e4df57ca3877eb3fe9c77a649`，和 agentd 对同样的内容算出来的一样；`git/commits` 对不存在的 SHA、blob 和树都回 404；`git/trees` 对 blob 回 422，对提交直接列出它的树，对不存在的 SHA 回 404。

### 推送前审查（安全审查 + 对抗性审查）发现并修掉的问题

两个审查代理都没改仓库里的文件。下面的问题都核实过；第 1 条没改代码，要用户定。

1. **GetCommit 返回 200 不说明提交属于这个仓库**（高，两个审查都报了；没改，见“留到后面”第一条）。GitHub 经父仓库也给出只在 fork 里的提交：对抗性审查在 github.com 上实测，`GET /repos/octocat/Spoon-Knife/git/commits/d7fefb16…` 返回 200，那个提交只在一个 fork 里。7 位前缀暴力算只要几秒（6 位 9 秒，8 位 96 秒，14 核）。被攻破的服务器在 resolve_commit 里答出这样一个提交，文件核对照样通过（它的树就是它自己的），agentd 在原仓库里建分支、开 PR：PR 里是那个提交的整段历史加补丁，推送触发的 CI 会带着仓库的 secrets 跑它的代码。我原来在笔记里写“GitHub 只证明它是仓库里的一个提交”，不对，已改。不经攻破也一样：直接审计一个 fork 里的 PR 提交（完整 SHA），它的历史同样被推进原仓库的分支。
2. **100 次列表的上限会拒掉诚实的补丁**（中，对抗性审查）：20 个文件各在一个模块里、9 层深（`modules/mNN/src/main/java/com/acme/mNN/Codec.java`）要列 2 + 7 × 20 = 142 次，被拒，不开 PR。改法：去掉次数上限，改为补丁路径最多 32 段；列多少次由补丁决定。笔记里“20 个文件、每个十几层深也够用”的说法不对，已改。
3. **核对时把每个列表整个留在内存里**（中，安全审查）：构造的仓库让路上每层目录各有 10 万个条目（实测一个这样的列表 20.7 MB JSON、解码后占 30 MB），100 层就是 3 GB，每次尝试、每个并发任务各一份。改法：只留补丁路径叫到的条目；一个列表最多读 8 MiB，一次核对最多 64 MiB。
4. **重发时被拒，记成 ABANDONED，可之前的尝试也许已经建了分支**（低，两个审查都报了）：比如第一次尝试建了分支、开 PR 时 502，恢复后重发，这时 GetCommit 回 404（令牌刚失去权限），记录成了“没发出”，也不再算进 max_per_run。改法：拒绝前先查分支，分支在就报冲突、交给人核对（复审又补了一处，见下）。
5. **这次之前的载荷，修改的文件会被当成新建来核对**（低，安全审查）：旧载荷没有 `old_blob`，一个服务器凭空说有、GitHub 上其实没有的文件，按“新建”核对就通过了（审查实测开出了 PR）。改法：载荷对每个文件写明 `new` 或 `old_blob`，两个都没有就拒绝。
6. **新建的文件和已有的只差大小写**（低，两个审查都报了）：`App/db.py` 旁边有 `app/db.py`、`app/Run.sh` 旁边有可执行的 `app/run.sh`，在 macOS、Windows 的检出里是同一个文件，后到的覆盖先到的。改法：新建的路径（包括路上缺的目录）在同一层有只差大小写的名字时拒绝。

审查确认过、不用改的：所有写请求都只经 Execute，启动恢复从不重发，人核对后改回 PENDING 的和 dry-run 之后改成真跑的载荷发出前都会核对；没有 TOCTOU（核对和 CreateTree 用同一个不可变的树 SHA）；重试有上限（`maximum_attempts=5`）；拒绝的原因里只有路径、SHA 和仓库名；上级目录的规则没找到绕过的办法；`BlobID` 和 git 算的一样，发出去的就是打在核对过的原内容上的补丁（合法的 UTF-8，JSON 转义能原样还原）。对抗性审查在一份副本里跑过 T2 查找恢复、dry-run、T3、T15、T16、写次数上限、agentd 重启这些黑盒测试，没有回归。

## M3b 补充三：只在 base 分支历史里的提交上开 PR（2026-10-19）

上一节“留到后面”的第一条，两个审查都判为高危：GitHub 经原仓库也给出只在 fork 里的提交，`Git.GetCommit` 回 200 不说明提交属于这个仓库。被攻破的 git 工具服务器能把操作员给的几位数字解析成攻击者 fork 里前缀相同的提交（7 位前缀暴力算只要几秒），文件核对照样通过（那个提交的树就是它自己的），open_draft_pr 就在原仓库建分支：分支带进那个提交的整段历史，推送触发的 CI 带着仓库的 secrets 跑那些提交里的工作流。不经攻破也一样：操作员审计 fork 里 PR 的头提交。用户选了第一种改法：开 PR 前用 GitHub 的 compare 确认提交在 base 分支的历史里，不在就只发报告。

审查又发现，在 base 分支的历史里也不等于推上去的内容有人审过：合并进来的 PR 的中间提交就是（中危，两个审查都报了）。用户定了这个 PR 先合，另做（见“留到后面”第一条）。

### 做了什么

- **`OpenDraftPR.Execute` 在 GetCommit 之后、核对文件之前（`inBase`）**：
  - 先读 base 分支指向的提交（`GET /repos/{o}/{r}/git/ref/heads/{base}`），后面拿这个 SHA 比较，不拿分支名：同名的标签顶替不了分支，带斜杠的分支名也不用转义。回答必须正是 `refs/heads/{base}`、指向一个提交、带 40 位 SHA，否则算拒绝。404 也算拒绝：没有这个分支，或者令牌看不到仓库，所以和 GetCommit 的 404 一样，先确认仓库看得见。
  - 再取 `GET /repos/{o}/{r}/compare/{分支的提交}...{被审计的提交}?per_page=1`：merge base 就是被审计的提交、状态是 `behind` 或 `identical`，才往下走；否则拒绝，原因里写 GitHub 给的状态和提交多出来的提交数。两者没有共同的历史时 GitHub 回 404，也算拒绝（同样先确认仓库看得见）。
  - 回答最多读 8 MiB：在分支历史里的提交，回答里没有提交也没有文件，只有两个提交对象（签过名的提交，提交信息要出现两次），通常几 KB 到十几 KB；超过就拒绝。`per_page=1` 让多出来的提交只列第一个，不在历史里的提交，回答也小一些。
  - 拒绝都经 `refused`：GitHub 上已有载荷的分支、或者看不出来，就交给人（上一节）。GitHub 失败照旧算没发出、重试。
  - 放在核对文件之前：被拒的提交不花列目录的请求。
- **GitHub 拒绝的请求（403、422 这类，不是限流）也经 `refused`**，读写都一样：GetCommit、读 base 分支、比较、列目录，以及开始写之后的建树、建提交、建分支、找 PR、开 PR。分支不在，照旧记 FAILED（GitHub 拒绝，什么都没发生）；分支在、或者看不出来，交给人。原来不看分支就记 FAILED，可这次或者之前的尝试也许已经建了分支：比如令牌能推分支、没有开 PR 的权限，分支推上去之后找 PR 回 403，记录却是“什么都没发生”。GitHub 拒绝了请求之后，`refused` 总先确认仓库还看得见：拒绝也可能是令牌刚失去了权限。
- **base 分支名要是 git 自己会起的名字**（`git check-ref-format --branch` 的规则，`tools.ValidBranch`）：不能有空的段、以点开头的段、以 `.lock` 结尾的段，不能以点结尾，不能是 `HEAD`。任务开始时、Prepare 时、Execute 时都查：这次之前记下的载荷里可能有原来收下的名字。原来只拒绝 `..`，`a/./b`、`main/.`、`stable//3.5` 都收；go-github 把 `a/./b` 问成 a/b，GitHub 对 `a//b` 回 a/b 的提交，而且照原样回显问的名字，检查的和开 PR 的就成了两个分支。
- **githubsim**：
  - 仓库副本的分支就是 GitHub 上的分支（`GET .../git/ref/heads/...`；API 建的和测试设的优先，测试能用 `SetRef` 挪动 main）。和 GitHub 一样，`a//b` 找到的是 a/b、回答里照原样写问的名字，以 `/` 结尾的找不到。经 API 建一个副本已有的分支回 422，PR 开到 GitHub 上没有的 base 分支也回 422。
  - `compare` 照 github.com 的回答：base 和 head 各是分支名或 40 位 SHA；状态、`ahead_by`、`behind_by` 用 `git merge-base` 和 `git rev-list` 算；列出 head 多出来的提交（从旧到新，`per_page` 截断）和它们从 merge base 起改的文件；提交对象带提交信息（和 GitHub 一样去掉 git 最后的换行）。没有的提交或分支、树、blob 都回 404，两者没有共同历史时也回 404，消息和 GitHub 的一样；git 出错回 500。只比较副本里的提交，不比较经 API 建的。
- dry-run 的注释写明：dry-run 不核对提交，不在 base 分支里的提交也会 dry-run 出一个 PR。

### 我定的几处

- **条件看 merge base 和状态两样**：merge base 就是被审计的提交，说明它在分支的历史里；状态是 GitHub 自己的结论。两样都对上才算，GitHub 的回答哪一处不对都是拒绝。
- **按分支指向的 SHA 比较**，为此多一个请求（GetRef）。
- **不在 base 分支里的提交只发报告**：fork 和 PR 头上的提交都是这样。agentd 不能往 fork 推，往原仓库推又会带进 fork 的提交。同一仓库 feature 分支上的提交，`--base` 给那个分支就能开 PR（PR 开到那个分支上）。
- **在 base 分支历史里的提交照样开 PR，不管多旧、是怎么进来的**：这只说明提交是仓库历史的一部分，不说明它的树有人整体审过。分支推上去时跑的是那棵树里的工作流和代码。我原来以为“那是有写权限的人放进去的”，审查指出不对（见下面第 1 条）。
- **GitHub 拒绝的请求一律交给 `refused`，不只新加的两个读请求**：一个请求被拒时 agentd 说不准之前发出过什么，规则只有一条：GitHub 上没有载荷的分支，拒绝才算数。代价：第一次尝试时令牌配错了（401，或者 SSO 拦下的 403），记录转 UNKNOWN 等人核对，不直接记 FAILED，和令牌看不到仓库时一样（上一节）；原因里那句“可能已经发出了一部分”对第一次尝试是多虑的。
- **ref 的回答对不上算拒绝，不重试**：重试改不了它，原来那样只会试满 5 次、记录一直是 PENDING。
- **没有要求完整的 40 位 SHA**（第二种改法没做）：剩下的风险见“留到后面”。

### 推送前审查（安全审查 + 对抗性审查）发现的问题

两个审查代理都没改仓库里的文件。两个审查都确认：只伪造 merge base 或只伪造状态都会被拒；fork 的提交、自成一段历史的提交、别的分支上的提交，都在任何写请求、任何列目录之前被拒；criss-cross 的历史（两个 merge base）不会误拒在历史里的提交。

1. **在 base 分支的历史里，不等于推上去的树有人审过**（中，两个审查都报了；没改，用户定了这个 PR 先合、另做，见“留到后面”第一条）。攻击者的 fork PR 有两个提交：Y 加进 `.github/workflows/evil.yml`（`on: push`，把 secrets 发出去），Z 再删掉。审核人看的是净 diff，干净；用 merge commit 合并（GitHub 默认，保留 fork 原来的 SHA）或 rebase 合并后，Y 就在 main 的历史里，推到 main 时跑的只是头提交的工作流。之后：
   - 不经攻破：操作员顺着 `git blame` 审计“引入这段代码的提交”，落在 Y 上，模型给出修复，agentd 在原仓库建分支 Y + 补丁，`on: push`、`on: create` 的工作流就从 Y 的树里跑，带着现在的 secrets。补丁碰不了 `.github`，删不掉它。
   - 经攻破：Y 和 Z 都是攻击者的，可以先把两者的 7 位前缀算成一样；操作员照 GitHub 页面输入 Z 的前 7 位，被攻破的服务器答 Y，检查通过。
   - 只比对 `.github` 子树挡不住：Y 改的 `conftest.py`、`package.json` 也会被 main 自己的 push 工作流执行。`pull_request` 的工作流不受影响：它跑 PR 的合并提交，Y 之后的改动都在里面。两个审查都在 githubsim 里复现了（检查通过，分支的树就是 Y 的树，evil.yml 在里面）；GitHub 上要写才能测，没测。

3. **新加的两个读请求被 GitHub 拒绝（403、422）时直接记 FAILED，不看载荷的分支**（低，两个审查都报了）：重发时分支已经在，记录却成了“什么都没发生”。改法见上面“做了什么”，GetCommit 和列目录一起改。

5. **核对和建分支之间有一段时间**（低，安全审查）：base 读在列目录之前，最多 640 次列目录之后才建分支；这期间维护者 force push 去掉了这个提交，分支照样建在它上面。没改：下一步把分支建在 base 的头上，这段时间就不要紧了。
6. **操作员给的任何分支都算数**（低，安全审查）：`gh-readonly-queue/*` 这类分支里有没审过的提交。没改：base 由操作员定；以后可以在策略里列出允许的 base 分支，或者要求是受保护的分支。
7. **重发时 inBase 在找 PR 之前**（低，对抗性审查）：第一次已经开了 PR、回答丢了，之后 main 被 force push 去掉了这个提交，再重发时得到冲突（UNKNOWN），而这时找得到那个 PR。没改：结果偏安全；要先找 PR，就会在核对分支之前认下一个同名分支上的 PR。
8. **githubsim 和 github.com 的差异**（提示）：提交对象没有提交信息（回答的大小测不出第 4 条）、忽略 `per_page`、git 出错时回答成 identical、建 ref 和开 PR 看不到副本已有的分支：都改了。没改：compare 不认标签（以后有人把比较改回按分支名，测试测不出标签顶替）；不比较经 API 建的提交（以后要测“base 经网页合并往前走了”会误拒）。

### 复审（对这些修复的对抗性审查）发现并修掉的问题

没有高危。复审确认：`ValidBranch` 和 `git check-ref-format --branch` 在这些字符里的近两万个名字上只差 `HEAD` 一个；限流照旧重试；拒绝的原因准确；每一处修复拿掉以后都有测试失败。

### 留到后面

- **在 base 分支历史里、但树没人整体审过的提交，照样能开 PR**（中，上面第 1 条）：合并进来的 PR 的中间提交，或者工作流后来修过的旧提交。分支推上去时，`on: push`、`on: create` 的工作流从那棵树里跑，带着仓库现在的 secrets。给的提交号不到 40 位时，被攻破的服务器还能换成攻击者经合并的 PR 预先埋好、前缀相同的提交。用户定了另做（2026-10-19）：把 PR 的提交建在 base 分支的头上（父提交是头，树是头的树加补丁，文件核对也对着头的树；补丁涉及的文件在头上变了就拒绝；重发时要认得建在旧的头上的分支），推上去的就总是“头加补丁”，上面第 5 条也随之消失。真实仓库上的根本办法仍是设计文档第 3 节写的：从专用 fork 开 PR，或者把 secrets 放进需要人工批准的环境；模型写的补丁本身改了 CI 会执行的代码，也只有这样才挡得住。
- **核对和建分支之间 base 被改写**（上面第 5 条）：这次照样开 PR。之后的重发再核对，提交不在了而分支已经在，交给人。
- **很旧的提交比较起来慢**（Linux 上落后上百万个提交要 5 到 7 秒）：超过请求超时（默认 30 秒）就重试，最多 5 次，之后记 FAILED。
- **不在 base 分支里的提交，报告照样发在那个提交上**（上面第 9 条）。
- **base 分支没有白名单**（上面第 6 条）；**重发时先核对后找 PR**（上面第 7 条）；**githubsim 的 compare 不认标签、不比较经 API 建的提交**（上面第 8 条）。
- **分支推上去之后的取消、分支建好之后的拒绝、建分支 422 的原因**（第二次复审，上面三条）：留给下一步，和把提交建在 base 头上一起改。

## M3b 补充四：镜像里不能有 agentd 的数据（2026-10-19）

PR #20 的安全审查发现，git 工具服务器有和 Worker 同一类的问题（当时记在 m1-notes 的“还没解决的风险”）：Linux 的 `run-tool.sh` 把这次调用的镜像整个只读挂进沙箱（`--ro-bind "$(readlink -f "$mirror")" "$mirror"`），而只读挂载挡不住读，也挡不住 `connect()`。镜像要是包住了 agentd 的数据目录，比如 `repos` 写成家目录（`acme/payments: ~/`），默认的数据目录 `~/.agentos` 就在里面，被攻破的工具服务器就能读账本，经 Control socket 起任务、加预算、取消任务。设计文档第 8 节说工具服务器不读密钥、账本和别的镜像。启动脚本每次调用都扫一遍镜像太慢，而且只能按名字认，所以改由 agentd 加载配置时拒绝。

macOS 上本来就挡住了：srt 的拒读路径在允许的目录里面时拒读优先，镜像里列进拒读单子的数据目录和别的镜像都读不到（实测 `Operation not permitted`），srt 也不让连任何按路径的 Unix socket。这次的检查两个平台都做。

PR #N。设计文档没改。

### 做了什么

- **`config.Load` 解析完所有路径之后（`checkMirrors`），拒绝镜像就是、或者包住了下面任何一样的 repo**：
  - 数据目录；
  - Control socket 所在的目录；
  - Runtime socket 所在的目录（`runtime_listen` 是 `unix://` 时；TCP 端口没有文件）；
  - Temporal 的客户端证书和私钥；
  - 别的 repo 的镜像：包住它、在它里面，或者就是同一个目录。

  这正是 `toolDenyRead` 交给启动脚本拒读的那张单子（这次调用自己的镜像除外）。报错写明哪个 repo、哪个镜像、包住了什么，用配置里的写法（清理过）；名字上看不出包含关系时（经符号链接、别名认出来的），再附上两边的真实路径。
- **三种比较，任何一种成立就拒绝**：
  - 名字：清理过的绝对路径（`filepath.Rel`）。`m` 和 `m2`、`m-data` 这种前缀相同的名字不算。
  - 真实路径：像内核那样一段一段地解析（`resolve`），存在的部分照内核的语义（符号链接的目标接着解析，`..` 在符号链接之后处理，最多跟 40 个链接），还不存在的部分按名字接上：数据目录在 Load 之后才建，socket 的目录更晚，它们会建在存在的那一段指向的地方。指向还不存在的地方的符号链接也照样跟：镜像是这样一个链接、数据目录又正好要建在它指的地方时，agentd 建好数据目录，镜像就包住了它。对存在的路径，结果和 `filepath.EvalSymlinks` 一样（有测试对照）；不用它，是因为它遇到不存在的部分就只报错。
  - 同一个目录的另一个名字：镜像存在时，从目标的真实路径（含它自己）往上，每一层存在的目录都和镜像比 `os.SameFile`（设备号和 inode）。符号链接之外，同一个目录还有只有文件系统知道的名字：macOS 的 firmlink（`/System/Volumes/Data/Users/...` 就是 `/Users/...`）和另一种大小写（APFS 默认不分大小写），Linux 上镜像是目标的某个上级目录的 bind mount（`readlink -f` 和 `EvalSymlinks` 都看不出）。这台 Mac 上实测，`EvalSymlinks` 对 `/USERS/joechen` 和 `/System/Volumes/Data/Users/joechen` 都原样返回，前两种比较认不出那是家目录。
- **只比较绝对路径**：空的路径什么都不指。`runtime_listen: unix://` 的目录原来算成 `.`，判断随 agentd 的当前目录变。
- **每个路径只查一次文件系统**，比较都在内存里做：原来每一对都重新解析、往上 stat，200 个镜像的配置 Load 要约 2 秒；现在约 40 毫秒，1000 个约 0.7 秒。
- **镜像在数据目录里面没关系**：开发配置就是 `~/.agentos/mirror`，数据目录是 `~/.agentos`，工具服务器只看得到镜像。
- **配置里的绝对路径也清理**（`filepath.Clean`，包注释写明了：所有路径的 `..` 都按名字去掉前一段，符号链接也一样）。相对路径和 `~/` 路径本来就经 `filepath.Join` 清理过，绝对路径原样保留。agentd 往这些路径上 `filepath.Join` 出账本和锁文件，`..` 按名字去掉；`MkdirAll` 和 `listen()` 却把原样的路径交给内核，内核在符号链接之后才处理 `..`。`data_dir: /x/away/../inner`、`away` 指向别处、`inner` 指进镜像时，检查看的是内核解析的那个地方，锁文件和账本却落在镜像里；`control_socket: /S/link/../control.sock`、`link` 指进镜像里的子目录时，检查看的是 `/S`，socket 却建在镜像里（我和两个审查各自实测）。现在每个路径就是清理后的那个名字，检查和用法一致。
- **镜像的真实路径里有控制字符就拒绝**：Linux 的启动脚本在 shell 里取真实路径，`$(readlink -f "$mirror")` 会去掉末尾的换行，挂进去的就不是检查过的那个目录。查的是真实路径，不只是配置里的写法：镜像可以是指向名字以换行结尾的目录的符号链接；配置里的写法带控制字符时，真实路径里照样有（不存在的部分按名字保留），那一段是符号链接时挂进去的又正是检查过的目录。
- 检查按下标跳过镜像自己，不靠 repo id：原来用空字符串标记“不是镜像”，id 为空的 repo 就跳过了对 agentd 自己路径的检查。
- `toolDenyRead` 的注释写明 Load 会拒绝包住单子上其余路径的镜像；README 的 Requirements 加了一句。

### 我定的几处

- **放在 `config.Load`**：路径都在这里解析、补默认值，配置一错，agentd 什么都还没建就停下。只有 agentd 调 Load。
- **证书和私钥也查**：任务只列了数据目录、两个 socket 的目录和别的镜像。第 8 节说工具服务器不读密钥，`toolDenyRead` 也拒读这两个文件，所以按 `toolDenyRead` 的整张单子查。`cmd/agentd` 的测试把单子上的每一项轮流当成镜像：以后单子上加了东西而 Load 不查，这个测试就失败。
- **多比一层 `os.SameFile`**：任务只要求比清理过的路径和真实路径，原因见上。
- **只查一个方向**：镜像在这些路径里面不拒绝（数据目录里的镜像就是这样）。
- **名字上在镜像里就拒绝**，哪怕那是一个指向镜像外的符号链接：沙箱里那个链接指向的地方并没有挂进去，其实没暴露什么（对抗性审查指出），但这样的配置多半是写错了，照任务比清理过的名字。
- **两个 repo 共用一个镜像也拒绝**（任务要求“相同也不行”）：比如 fork 和原仓库想共用一份对象，现在要各 clone 一份（alternates 指到沙箱外的目录，工具服务器读不到）。
- **bind mount 只认一种**：镜像是目标某个上级目录的别名。另外两种（镜像里面挂进了别的目录，目标是从镜像里面挂出去的）要读 `/proc/self/mountinfo`，没做，见“留到后面”。
- **家目录、`/tmp`、`$XDG_RUNTIME_DIR` 不在单子上**：它们不是 agentd 自己的路径，算不算镜像不能包住的东西，要另外定（见“留到后面”）。

### 推送前审查（安全审查 + 对抗性审查）发现并修掉的问题

两个审查代理各自在副本里、Mac 和虚拟机上做了实验，都没改仓库里的文件。没有高危。

1. **路径里符号链接后面跟 `..`，socket 和账本会落进镜像**（安全审查列为低，对抗性审查列为中；我自己也发现了数据目录的那一种）：`control_socket: /S/link/../control.sock`、`runtime_listen: unix:///S/link/../runtime.sock`，`link` 指向镜像里的 `refs`。虚拟机里经真实的 `run-tool.sh` 起的探针连上了两个 socket。对抗性审查还发现，另一个 repo 的镜像写成 `…/link/../c` 时同样放行，之后建在第一个镜像里；数据目录那一种第一次启动放行、之后每次都拒绝。改法：清理绝对路径（见上）。
2. **bind mount 另外两个方向认不出**（安全审查列为低，对抗性审查列为中）：镜像里面挂进了数据目录（`mount --bind /B/data /B/mirror/sub`，bwrap 的 `--ro-bind` 连子挂载一起挂），或者数据目录是从镜像里面挂出去的。虚拟机里两个审查都实测：Load 放行，沙箱里读到了账本、连上了 Control socket。没改：要运维者自己挂载，改法要读 mountinfo，记在“留到后面”；代码注释原来说能认出 bind mount，改成只说认得出的那一种。
3. **镜像路径末尾的换行**（提示，安全审查）：`mirror: |` 块标量得到 `/B/u\n`，`run-tool.sh` 的 `$(readlink -f ...)` 去掉了换行，挂进去的是 `/B/u`，里面有数据目录（虚拟机里实测读到了账本）。改法：镜像路径里有控制字符就拒绝（复审后改成查真实路径，见下一节第 3 条）。
4. **镜像是指向还不存在的地方的符号链接**（低，对抗性审查）：数据目录正好要建在它指的地方时，Load 放行，agentd 建好数据目录，镜像就包住了它，直到下次重启才被拒绝。改法：`resolve` 顺着悬空的链接接着解析（复审后改写，见下一节第 1、2 条）。
5. **id 为空的 repo 跳过了对 agentd 自己路径的检查**（低，对抗性审查）：原来用空字符串标记“不是镜像”。策略里写 `repos: [""]`、agentctl 不带 `--repo` 时，空的 id 用得上。改法：按下标跳过镜像自己。
6. **仓库多时 Load 很慢**（低，对抗性审查）：每一对都重新解析，实测 100 个 0.43 秒、300 个 3.8 秒、1000 个 43 秒。改法：每个路径只查一次。
7. **判断随 agentd 的当前目录变**（提示，对抗性审查）：`runtime_listen: unix://` 的目录算成 `.`。改法：只比较绝对路径。
8. **报错看不出为什么**（提示，安全审查）：经真实路径或 inode 认出时，配置里的两个写法看不出包含关系。改法：附上两边的真实路径。
9. **测试缺口**（对抗性审查）：
   - macOS 上“往上比 `SameFile` 时跳过目标自己”这个改坏活了下来：没有数据目录就是镜像的别名的用例。加了。
   - 家目录那个用例只查报错里有没有 `home/.agentos`，而两个 socket 的目录也以它开头，去掉“查数据目录”照样通过。改成要求报错里出现的正是那个路径，后面不再跟 `/`。
   - Linux 的 CI 只在 Go 任务里跑这些测试，那里没有别名用例，往上比 `SameFile` 的那一层测不到（对抗性审查在 Linux 上有 4 个改坏活了下来）。没改，见“留到后面”。
   - 审查也确认：开发配置（镜像是普通目录，或指向某个 checkout 的符号链接）和测试 harness 的布局都照常加载，没发现误拒；虚拟机经 virtiofs 共享的目录 inode 号是生成的，深度 4 以内的 889 个目录没有重复。

### 复审（对这些修复的对抗性审查）发现并修掉的问题

复审没做完变异测试（被提前停了），找到的三条都在上面第 1、3、4 条的修法里：

1. **悬空链接的目标以 `/` 结尾时，`resolve` 把最后一段重复了一次**（低）：`<dir>/up/soon/` 解析成 `<dir>/up/soon/soon`，上面第 4 条又绕过去了（Mac 和虚拟机上实测）。
2. **悬空链接的目标里的 `..` 又按名字处理了**（低）：目标 `sub/../later`、`sub` 指向 `elsewhere/a/b` 时，内核去的是 `elsewhere/a/later`，`resolve` 却得出 `<dir>/later`：数据目录建在 `elsewhere/a/later` 里时放行，建在 `<dir>/later` 里时反而误拒。正是第 1 条刚去掉的那种名字和内核不一致。改法（1、2 一起）：`resolve` 改成像内核那样一段一段地走，存在的部分跟链接、`..` 在链接之后处理，不存在的部分按名字接上。
3. **控制字符只查了配置里的写法**（低）：镜像是指向名字以换行结尾的目录的符号链接时，真实路径以换行结尾，`readlink -f` 照样把它去掉，挂进去的是旁边那个没有换行的目录（虚拟机里实测）。改法：查真实路径。启动脚本取路径的写法本身没改（见“留到后面”）；macOS 的启动脚本也这样取，但那边拒读优先，结果是读不了自己的镜像。
4. **`Clean` 也作用到 agentd 读的、执行的文件**（提示）：策略、模型、价格文件，证书，`git_tools.server` 和启动脚本。`/opt/agentos/current/../sandbox/linux/run-tool.sh`、`current` 指向 `releases/v2` 时，原来打开的是 `releases/sandbox/...`，现在是 `/opt/agentos/sandbox/...`。和相对路径、agentctl 的 `filepath.Abs` 一致，仓库里的配置和测试都不这样写。改法：包注释写明所有路径都按名字处理 `..`。
5. **笔记写过头了**（提示）：第 3、4 条的修法原来说得太满，已改；PR 号补上了。

复审也确认：按下标跳过，不会漏掉或重复哪一对，报出的错误是确定的（先 agentd 自己的路径，再按 id 排序的镜像）；空的证书路径和 `unix://` 不会包住什么、也不会被包住；`resolve` 总会结束；无效的 UTF-8 藏不住换行；`TestAgentdMakesNothingInAMirror` 三个路径任何一个出问题都会失败，用的是 `/tmp` 下的短路径，不会留下文件，也不会时好时坏。

### 留到后面

- **bind mount 的另外两个方向**（上面第 2 条）：镜像里面的子挂载，从镜像里面挂出去的目录。Linux 上可以按 `/proc/self/mountinfo` 把路径换算成（设备，文件系统里的路径）再比，并且拒绝底下有挂载点的镜像；也可以让 `run-tool.sh` 每次调用时自己查（它收到了 `AGENTOS_SANDBOX_DENY_READ`，却没用），或者只挂 git 用得到的东西（`.git` 里的 `HEAD`、`config`、`objects/`、`refs/`、`packed-refs`），不挂整个镜像。
- **启动脚本取路径的写法**：`$(readlink -f "$mirror")` 会去掉末尾的换行（macOS 的 `$(cd "$1" && pwd -P)` 也是）。现在由 Load 拒绝真实路径里有控制字符的镜像；启动脚本自己也可以防：用哨兵取（`real=$(readlink -f -- "$mirror"; echo .)` 再去掉最后的 `.`），或者要求 `[[ $real -ef $mirror ]]`。
- **只在启动时查一次**：镜像之后被改指（比如运维脚本把镜像的符号链接指向家目录）、镜像在 agentd 起来之后才建、之后才加的挂载，都发现不了。启动脚本每次调用都重新 `readlink -f`；agentd 可以在每次调用前再比一次（只是几次 stat），把检查过的真实路径交给启动脚本。
- **agentd 不知道的东西照样能被包进镜像**：数据目录放在别处时，`repos` 写成家目录照样通过，Linux 上的工具服务器能读 `~/.ssh`、`~/.gnupg`、`~/.config/gh` 里的令牌、`~/.netrc`、另一套 agentd 的数据目录、生产环境里 Temporal 的数据库（开发时 README 让它放进 `~/.agentos`，算在数据目录里）。镜像包住 `/tmp` 时能连 ssh-agent 的 socket，还会盖掉沙箱自己的私有 `/tmp`；包住 `$XDG_RUNTIME_DIR` 时能连会话总线，Linux 上 agentd 的 API 密钥就在经它访问的 Secret Service 里。可以再拒绝包住家目录、`/tmp`、`$XDG_RUNTIME_DIR` 的镜像（两个审查都建议），或者要求镜像就是用户自己的一个 git 仓库。
- **认不出的别名**：硬链接（比如 `cp -al` 把账本或私钥链进镜像；对抗性审查建议拒绝链接数大于 1 的私钥文件）；设备号不同的别名（同一棵目录树经 NFS、SMB、sshfs、bindfs 另挂了一份）。
- **inode 号会重复的文件系统**上 `SameFile` 可能误拒：各层不在同一个文件系统、又没开 xino 的 overlayfs，NFSv3 的 nohide，9p 的 `multidevs=warn`，一些 FUSE 文件系统。报错里写的是另一个目录，一查就知道。
- **Linux 的 CI 测不到 `SameFile` 那一层**：别名用例只在 macOS 上跑，Go 任务里没有 bwrap 做 bind mount。可以在 bwrap 那个 CI 任务里经 bwrap 跑这个用例，或者把 stat 换成可注入的。
- **id 为空的 repo**：现在检查照常，但 Load 本身还接受空的 id，可以直接拒绝。
