# M3 记录：工具与副作用

M3 拆成两段（设计文档第 12 节，rev 262）：M3a 副作用协议和 GitHub 写工具，M3b 只读 git MCP。

## M3a：副作用协议和 GitHub 写工具（2026-10-18）

验收 T2、T3、T15、T16 通过，GitHub 用本地模拟的。真实测试仓库上的那次 T2 放在 M3b 收尾。

### 做了什么

- **数据目录锁**：agentd 启动后第一件事是对数据目录加排他锁（`agentd.lock`，flock），拿不到就退出，账本和 socket 都不碰。以前第二个 agentd 会删掉并抢走 Control socket（Linux 上还有 Runtime socket），而且在绑定端口之前就执行 `SettleOpen`，把第一个 agentd 还在途的模型预留按全额结算，还会启动 gateway worker 领活动任务。锁随进程走，kill -9 也会释放。
- **副作用协议**（`internal/gateway/effects.go`，迁移 `00007_effect_claims.sql`）。一次写分四步：
  1. 渲染载荷：工具的 Prepare 生成外部系统将收到的全部内容，同一个请求每次渲染结果相同。
  2. 记录：载荷存成 blob，哈希存进 `payload_sha256`。
  3. 领取：按 `version` 比较并交换，记下 `claimed_by`（本进程的标识）和 `claimed_at`。领取在同一个事务里检查任务没被取消，所以 CancelRun 落库之后任何尝试都领不到。
  4. 发送，记结果。

  重试时重新渲染，载荷和记录的不一致就不执行（`PayloadChanged`）。M4 的审批绑定的就是这份载荷。
- **发送的结果分四种**：
  - 成功：SUCCEEDED。
  - 没发出去（`ErrNotSent`）或对方要求稍后再试（限流）：交还领取，返回可重试错误，下次尝试再领。
  - 对方明确拒绝（4xx）：FAILED，不可重试。
  - 同名资源已存在但内容不同：UNKNOWN，等人核对，不覆盖。

  其余情况（5xx、超时、连接断开）结果未知，当场按类别恢复。
- **按类别恢复**：
  - 适用于两种记录：被已经不在的进程领取的；被本进程领取、但当前没有执行在跑的。
  - 规则：
    - idempotent：同键重发。
    - lookup：先查。查不到就等到“最后一个可见请求发出的时间 + Settle”，再查一次，仍没有才重发；查询本身出错就转人工核对。
    - unsafe：记 UNKNOWN，返回 needs_reconcile。
    - 已取消的任务：只查，不发；查不到记 ABANDONED。
  - agentd 启动时还有两件事：
    - 已取消任务里没领取过的记录直接记 ABANDONED。
    - 上个进程领取的记录在后台恢复，和工作流重试走同一个 singleflight 键，谁先到谁做，另一个等结果。启动时的恢复只查不发：查不到就交还，由任务的下一次调用发出。任务已经结束的，不会再有下一次调用，也就不会再发。
  - 本进程领取、执行还在跑的记录，同时到的另一个执行者返回可重试的 `EffectBusy`，不会再发一次。
- **核对**：
  - `ListPending` 列出 UNKNOWN 的记录，包括当时要发的载荷全文。
  - `ResolveReconciliation` 有两个出口：
    - 已执行：结果由人给出（按工具的结果 schema 校验），或者 `--lookup` 让 agentd 去查，记录改成 SUCCEEDED。
    - 未执行：记录改回 PENDING，下次调用用原幂等键重发；任务已取消或已结束则改成 ABANDONED。lookup 工具在最后一个请求发出后的 Settle 时间之内，不接受“未执行”。
  - 并发和重复提交的处理：
    - 按 `version` 防并发，`resolve_key` 防重复提交。
    - 同一个 key 再发一次，返回同样的结果。
    - 换一个 key 再处理，报“已不在待核对状态”。
  - 处理完直接给工作流发门铃（outbox 留到 M4）。
  - 命令行：`agentctl reconcile list | show | resolve`。
- **工具注册表**（`internal/tools`）：
  - 每个工具在代码里声明三样东西：类别、参数 schema（`additionalProperties: false`）、写工具的结果 schema。
  - 写工具实现 Prepare、Execute 和 DryRun；lookup 类工具另外实现 Find 和 Settle。
  - 策略文件里的 `effect` 改为可选。要写，只能写工具自己声明的类别，或者对写工具写 unsafe。
  - agentd 启动时检查：策略写了更弱的类别，或者列出 agentd 没有的工具，都拒绝启动。
  - 网关只给工具补它声明了的范围参数；schema 拒收未知参数。由此堵上两个口子：Scope 只管列出的参数名（m1-notes），以及塞无关字段绕过同参数计数（m2-notes）。
- **GitHub 写工具**（`internal/githubtool`，go-github v92）：
  - `github.open_draft_pr`：
    1. 检查补丁，应用到镜像里的原文件。
    2. 经 Git Data API 建 tree、建提交（作者和时间固定）、建分支。分支已存在时，比较 tree 和父提交，不比较提交哈希。
    3. 按 head 分支查 PR（state=all），查不到才开草稿 PR；遇到 422 再查一次。
    4. PR 正文里没有模型写的文字。
  - `github.comment_commit`：
    - 按模板从 report_ref 渲染。
    - 模型和工作流给的文字全部放进代码围栏，围栏比其中最长的一串反引号还长。
    - 围栏外只有 agentd 自己核实过的内容：提交 SHA、按严重度的计数、PR 编号。PR 编号从本任务 open_draft_pr 的副作用记录里取，不用工作流传来的 pr_url。
    - 带隐藏标记 `<!-- agent-effect:<effect_id> -->`。查找时只认令牌本人账号发的评论。
- **补丁检查**（`internal/patch`，go-gitdiff + doublestar）。open_draft_pr 和 git.apply_check 共用这段代码，拒绝以下补丁：
  - 二进制改动、改名和复制、权限位变化；改完后不是普通文件（100644）的。
  - 路径经过 `.git`、`.gitmodules`、`.gitattributes` 的。
  - 路径不规范的，包括 `..`、绝对路径、反斜杠、控制字符。
  - 超出大小和文件数上限的。
  - 命中 deny_paths 的。deny_paths 不区分大小写，`makefile` 绕不过 `Makefile`。

  补丁按 hunk 写的位置严格应用，对不上就拒绝，不做模糊匹配。原文件用 `git ls-tree` 和 `git cat-file` 从镜像读，不跑过滤器、钩子或 diff 驱动，也不读用户和系统的 git 配置。不带 `diff --git` 头的普通 diff 去掉第一层路径（同 `git apply -p1`）。
- **dry-run**：
  - 用法：`agentctl runs start ... --dry-run`。是否 dry-run 记在 runs 表里，Worker 改不了。
  - 效果：写工具只做 Prepare，记成 DRY_RUN，返回带 `dry_run` 标记的结果。
  - agentd 没配 GitHub 时，GitHub 工具一律 dry-run，启动时打印警告。`agentd-claude.yaml` 不配 GitHub，配置测试断言了这一点：M4 之前，真模型和免审批的真实 GitHub 写入不同时出现。
- **循环保护**：每次调用记下它返回的状态。返回等待状态（needs_approval、needs_reconcile、budget_exhausted）的调用不计入模型调用次数和同参数次数，步骤数照算。以前等核对的任务每小时醒来重发一次，大约 3 小时后会被当成死循环拒绝。
- **配置**：
  - `repos` 的值可以写成镜像路径，也可以写成 `{mirror, github: owner/name}`；GitHub 名默认就是逻辑 ID。
  - 新增 `github` 一节：`api_url`、`token`（钥匙串引用；只有 api_url 是回环地址的模拟器才可以不填）、`request_timeout`（默认 30s）、`settle`（默认请求超时加 30s）、作者。
  - 默认作者 `agentos <agentos@agentos.invalid>`，这个地址不属于任何人。

### 实现中我定的几处（方案里没细说）

- **M3a 的 git.apply_check 已经做真实检查**：在 agentd 里用和 open_draft_pr 同一段代码检查补丁，并严格应用到镜像。代价：模型给的行号不准时，`git apply` 能靠偏移打上的补丁，这里会被拒。M3b 的 MCP 服务器要是用 `git apply --check`（容忍偏移），两边会不一致。M3b 开工时要定：两边都严格，还是都用 git。
- **恢复时在活动里等 Settle**，期间照常发心跳，不靠 Temporal 重试来等：工作流的重试策略最多 5 次尝试，退避加起来约 15 秒，等不到 60 秒。
- **副作用的 result_blob 现在只存工具的结果**。M1 存的是 `{status, value}`；状态改由副作用的状态决定。
- **模拟 GitHub 用 Go 写**：Go 单元测试直接用它，黑盒测试把它作为单独进程启动。它不校验令牌，只记录请求带没带令牌，Go 测试断言每个请求都带了。
- **T3 的 unsafe 工具 `test.unsafe_write`**：只在 `agentd --test-tools` 下注册，写的是数据目录里的一个本地日志。

### 推送前审查（安全审查 + 对抗性审查）发现并修掉的问题

两个审查代理都没改文件，下面的问题都核实过、已修，并补了测试：

1. **同一个核对幂等键可以生效两次**（高）。“未执行”之后重发，又一次结果未知，记录回到 UNKNOWN；这时 agentctl 重放同一个 key，会再触发一次重发。改法：核对结果按（effect_id, key）记进新表 `effect_resolutions`，同一个 key 再来只返回当初的结果；同一个 key 配不同结论直接拒绝。
2. **启动时的恢复会替已经结束的任务开 PR**（高）。例如重试次数在 GitHub 限流期间用完、任务已经发完失败报告，下次启动的恢复还是会重发。改法有三处：
   - 启动时的恢复只查不发：查不到就交还，由任务的下一次调用发；任务已结束就不会有下一次调用。
   - 查询出错直接转人工核对（UNKNOWN），不再无限重试。
   - 等待期间任务被取消，记 ABANDONED。
3. **领取之后的取消挡不住 open_draft_pr 后面的请求**（中）。这个工具要连发 7 个请求，取消只在领取时查一次。改法：工具在每个外人能看到的请求（建分支、开 PR、发评论）之前都调用 `proceed`。`proceed` 在同一条 UPDATE 里检查任务没被取消，并把 `claimed_at` 更新为这一刻，lookup 的等待从最后一个可见请求算起。
4. **Settle 没有下限**（中）。现在要求 settle ≥ request_timeout + 10 秒；回环地址上的模拟器只要求 ≥ request_timeout。测试改成 request_timeout 2 秒、settle 3 秒。另外，开 PR 时 GitHub 回 422 “already exists”、但查不到这个 PR，按结果未知处理，不再记 FAILED。
5. **工作流可以改参数发任意多条公开评论**（中）。参数每改一次就是一个新的副作用。改法：每个任务、每种写工具默认最多一次（策略的 `max_per_run`，可调大），按“已发出或可能发出”的记录计数，在插入副作用记录的同一个事务里判断。新测试 `tests/test_write_limits.py`。
6. **路径规则不够死**（低）。补丁路径里的 `:/app/db.py` 会被 git 当成 pathspec 魔法；`ſcripts/` 这类非 ASCII 字符能绕过大小写不敏感的匹配；还能在符号链接下面建文件。改法：
   - 路径各段只允许 `[A-Za-z0-9._+-]`。
   - git 命令加 `GIT_LITERAL_PATHSPECS=1`。
   - 父路径必须是目录。
   - 先用 `ls-tree -l` 查大小，超限的文件不读。
   - git 报错里的镜像路径替换成 `<mirror>`，因为报错可能经工作流进入公开报告。
7. **评论的边界情况**（低）。
   - 一长串反引号能把评论撑过 GitHub 的长度上限：现在反引号串最长截到 16 个。
   - 工作流可以把别的副作用的标记塞进围栏里的文字：现在查找只认最后一行的标记。
   - Unicode 格式字符（如双向覆盖符）也删掉。
8. **开 PR 时有一批路径永远拒绝**，不管策略怎么写，因为 GitHub 自己会对它们采取行动：
   - `.github/**`：工作流、dependabot 配置等。
   - 三个位置的 `CODEOWNERS`：决定谁必须评审。
   - `.devcontainer/**` 和 `.devcontainer.json`：有人在 Codespaces 里打开这个分支时会执行其中的命令。

   后两项是提交之后后台安全审查提醒补上的。开发策略和测试策略也加上了 deny_paths；正式策略加了 `GNUmakefile`，GNU make 会先读它。
9. **我自查发现的一处窄窗口**：同一进程里刚领取成功、还没登记“正在发送”时，另一个执行者若绕过合并读到这条记录，会把它当成无人在发。改法：领取和登记放进同一把锁。正常路径不会走到这里，但 T16 的 Go 测试正是绕过合并来测的。

还有一处改动：之后的调用不再重新渲染载荷，一律沿用第一次记录的那份。否则这种情况会出错：PR 的副作用在两次评论调用之间结算，评论载荷因此变了，已经成功的评论被当成“载荷改变”而拒绝。

### 测试怎么测

- **T2**（`tests/test_t2_lookup_recovery.py`），四个场景，都只开出一个 PR 或一条评论：
  1. PR 已在模拟 GitHub 上开出、结果还没落账时 kill -9 agentd。重启后靠查找补记，不再发。
  2. agentd 领取后、请求发出前被杀。重启时查不到，等过 Settle 再查，仍没有就交还；由任务的下一次调用发出，只发一次。
  3. 报告评论已发出、结果没落账时被杀。重启后按标记找到它。
  4. 不杀进程，模拟 GitHub 开出 PR 但扣住答复，agentd 的请求超时。agentd 当场去查，补记这个 PR。
- **T3**（`tests/test_t3_reconcile.py`），三个场景，最后都只写了一次：
  1. 写入已到外部、结果没落账时被杀。重启后任务停在 WAITING_RECONCILE，核对列表里有这条记录和它的载荷；`--executed --result` 之后任务跑完。
  2. 领取后、发出前被杀。`--not-executed` 之后用原幂等键发出。
  3. 不合工具结果 schema 的结果被拒，记录保持 UNKNOWN。
- **每任务一次**（`tests/test_write_limits.py`）：恶意工作流发三条不同的报告，只有第一条发出，后两条返回 denied；策略写 `max_per_run: 2` 时发出两条。
- **T15**（`tests/test_t15_cancel_restart.py`），三个场景：
  1. PR 已开出、结果没落账时取消任务，再 kill -9 重启。PR 靠查找补记，取消之后模拟 GitHub 没收到任何写请求，也没发报告。
  2. 记录已建、还没领取时取消再重启。记录在启动时记成 ABANDONED，什么都没发。
  3. 同样的时机，取消但不重启。领取在同一个事务里看到取消，记成 ABANDONED。
- **T16**（`tests/test_t16_one_executor.py`），两个黑盒场景，外加一个 Go 测试：
  1. 第二个 agentd 在同一数据目录上起不来，第一个还在服务。第一个 agentd 那笔开着的预留，最后按它自己的用量结算，没有被第二个当成 `open_at_start` 全额结算。
  2. 第 1 次尝试领取后卡住且不发心跳，Temporal 开出第 2 次尝试，两者合到同一个执行上；接着 kill -9，重启后的恢复和第 3 次尝试也碰到这条记录。三方合起来只开出一个 PR。
  3. 领取用的比较并交换由 Go 测试验证：`internal/gateway` 的 `TestOnlyTheClaimantSends` 让两个执行者绕过合并、同时处理同一条记录，只有一个发出。
- **dry-run**（`tests/test_dry_run.py`）：带 `--dry-run` 的任务、没配 GitHub 的 agentd，都没往模拟 GitHub 写任何东西，载荷全文都在账本里。
- **已有测试的变化**：
  - 测试镜像改成两次提交，被审计的那次正好是桩 diff 的改动，假模型的补丁能打上。
  - `stack.external()` 改为看外部世界自己的记录：模拟 GitHub 的请求日志，或测试工具的日志。

### 留到后面

- **M3b**：只读 git MCP（show_diff、apply_check），每次调用起一个沙箱进程；真实测试仓库上的 T2，到时需要你建公开测试仓库和只授权它的细粒度令牌。
- **M4**：审批表（AWAITING_APPROVAL，拒绝和修改后的 ABANDONED）；门铃改走 outbox，现在核对后的门铃是直接发的。
- **其他**：
  - 同参数计数用的是工作流原样发来的参数，还没补范围参数。所以工作流可以靠写或不写某个范围参数，凑出同一调用的几个变体，最多 2³ 种。写操作有副作用去重和每任务次数上限，重复发也只算一次；读操作只是多读几次。
  - 等人核对时，工作流每小时醒一次，每次都算一个调用。总调用上限是 100，所以大约 4 天没人处理，任务就会被循环保护拒绝，以失败结束。之后再处理成“未执行”，记录会改成 ABANDONED，因为任务已经结束。
  - unsafe 工具没有 Settle。重启后，人可以马上判“未执行”；如果旧请求其实还在对方那里处理，就可能出现重复。lookup 工具会拒绝过早的“未执行”。
  - 同一进程领取的记录，如果请求还在途、尝试次数又用完了，在 agentd 重启前不会出现在核对列表里。
  - 模拟 GitHub 的建 tree 只是对请求求哈希，没有模拟 GitHub 合并 base_tree 的行为。M3b 在真实仓库上跑 T2 时会覆盖到。
  - 设计文档第 7 节策略示例的 deny_paths 还没有 `GNUmakefile`，`max_per_run` 和“启动时只查不发”也还没写进文档。这几处等你确认后再改文档。
  - 报告超过 60,000 个字符会被截断。
  - lookup 的等待时长依赖 GitHub 文档写的 10 秒处理上限。就算估错，这两个工具的后果也有限：迟到的建 PR 会被 422 挡住，评论最多多出一条。

## M3b：只读 git MCP（2026-10-18）

`git.show_diff` 不再是桩。两个 git 工具都通过一个只读的 git MCP 服务器读仓库，agentd 每次调用起一个新进程，放进沙箱运行。

### 做了什么

- **git MCP 服务器**（`internal/gitmcp`、`cmd/agentos-mcp-git`，官方 MCP Go SDK v1.8.0），两个工具：
  - `show_diff`：
    - 提交号只收完整的 40 位 SHA，而且只看对象头：必须是提交对象，不超过 1 MiB。
    - 用 `git diff-tree -p --text --root --diff-merges=first-parent --no-ext-diff --no-textconv`：首个提交整份显示，合并提交只对第一个父提交显示，二进制文件也按文本显示，不跑外部 diff 程序和文本转换。
    - diff 按原样的字节、base64 编码传回，不是 UTF-8 的提交也不会被改动。
    - diff 超过 1 MiB 就拒绝，不截断。
    - 算 diff 之前先按对象头量大小，下面两种情况直接拒绝：
      - 改动的文件（改前或改后）有一个超过 4 MiB；
      - 所有改动的文件加起来超过 256 MiB。
  - `apply_check`：建一个临时索引，只放补丁涉及的文件（`ls-tree` 交给 `update-index --index-info`，经 `GIT_INDEX_FILE`），再跑 `apply --cached --check`。镜像和它的索引都不动，树的其余部分也不读。
  - git 怎么跑：
    - 不读用户和系统的 git 配置。
    - 属性从空树读（`GIT_ATTR_SOURCE`），也不读系统属性。
    - 忽略 replace 引用。
    - 路径按字面解释。
    - 不拿可选锁。
    - 单次分配不超过 256 MiB（`GIT_ALLOC_LIMIT`）。
    - 外面传进来的 `GIT_` 变量一律去掉。
    - 报错里的镜像路径换成 `<mirror>`；报错里引用的路径截到 200 个字符。
    - 只在镜像目录里找仓库，不往上找（`GIT_CEILING_DIRECTORIES`）：镜像目录要是还不是仓库、又恰好在别的仓库里面，git 会报错，而不是读外面那个仓库。
    - 这套环境放在新包 `internal/gitenv` 里，agentd 自己跑的 git（`internal/patch`、`internal/tasks`）也用它。
  - 两种错误分开报：
    - 工具错误：git 拒绝了输入，例如补丁打不上、超过上限、git 用完了它能用的内存或 CPU 时间。重试没用，所以不重试。
    - 协议错误：服务器没能干活，例如镜像读不了、git 不在、看不到这次任务的提交（agentd 在任务开始时已经在同一个镜像里找到过它，所以只能是镜像出了问题）。按失败处理，会重试，原因记进 agentd 的日志；git 的警告也随服务器的 stderr 进日志。
- **每次调用一个进程**（agentd 端的 `gitmcp.Client`）：
  - 经沙箱启动脚本起服务器，走 stdio。一次调用一个新进程：就算某个精心构造的仓库攻破了服务器，它也留不下任何状态影响下一次调用。
  - 每次调用新建一个目录 `/tmp/agentos-tools.<pid>.<随机>`（0700），调用结束就删。启动时清掉已经不在的 agentd 进程留下的目录。没有常驻目录，所以不怕 macOS 的 tmp_cleaner 删掉闲置目录，也不怕别的用户抢先占用这个名字。
  - 同时最多跑 4 个服务器。等空位最多 2 分钟；拿到空位后才开始算这次调用的超时（默认 1 分钟）。超时按失败处理、会重试：慢的可能是机器。拒绝太费力的提交靠启动脚本的 CPU 时间上限，那个对同样的输入每次都一样。
  - 单条回复和单条请求都有大小上限，分别够装下最大 diff 的 base64 和全是控制字符的最大补丁。
  - 启动脚本和它起的所有进程是一个进程组，超时或调用结束时整组 SIGKILL。
  - 服务器的 stderr 只进 agentd 的日志。返回给工作流的错误只说“失败了，详情看日志”。
  - 启动时做一次自检：在临时仓库上经启动脚本把两个工具各真调一次（apply_check 会写临时索引，顺带验证服务器能写的那个目录）。不通就拒绝启动，不会等到每个任务都失败才发现。
- **沙箱启动脚本**：
  - `sandbox/macos/run-tool.sh`（sandbox-runtime）：
    - 不允许任何网络。
    - 不能读：
      - 用户的家目录（从系统账户信息取，不看 `$HOME`）；
      - `/private/tmp` 和 `/private/var/folders`；
      - `AGENTOS_SANDBOX_DENY_READ`（一个 JSON 数组，路径里什么字符都可以有）里的路径：agentd 传数据目录、Control socket 和 Runtime socket 所在目录、Temporal 的 TLS 证书和私钥、每个镜像（包括这次调用的）。每个路径既按原样传，也按真实路径传；路径还不存在时，按已存在的上级目录解析。
    - 能读：这次调用的镜像、服务器二进制本身、这次调用的工作目录。不放行服务器所在的整个目录：sandbox-runtime 让放行目录之下的屏蔽规则优先，镜像要是放在二进制旁边，连它自己的调用都读不到。
    - 只能写工作目录。sandbox-runtime 默认放行写 `/tmp/claude`，这里也禁掉。
    - 每个进程最多 30 秒 CPU 时间，写的单个文件最大 64 MiB。
    - 清空环境变量。
    - 直接用真正的 git，不经过 `/usr/bin/git`：后者的 xcrun 会往沙箱外写缓存。
  - `sandbox/linux/run-tool.sh`（bubblewrap）：
    - 空的网络命名空间。
    - 只读挂载 `/usr`、镜像和服务器本身。
    - 私有的 `/tmp`，上限 64 MiB。根目录和 `/dev` 只读：它们是 bwrap 自己建的 tmpfs，大小可到内存的一半，可写的话会绕过 `/tmp` 的上限。
    - 清空环境变量。
    - 不许再建用户命名空间（`--disable-userns`）。
    - 每个进程：地址空间上限 4 GiB，最多 30 秒 CPU 时间，写的单个文件最大 64 MiB。
- **agentd**：
  - 新增 `git_tools` 一节：服务器路径（默认在 agentd 旁边）、沙箱启动脚本、超时。
  - 没配沙箱就拒绝启动；`--insecure-dev` 可以不用沙箱跑服务器，只用于开发，每次启动都打印警告。
  - 开发配置用 macOS 的启动脚本。
- **`git.apply_check` 要过两道检查**：
  - 先过 agentd 自己的严格检查：规则、两个工具各自的 deny_paths、`open_draft_pr` 永远拒绝的那批路径（两边共用 `githubtool.ProtectedPaths`）、按 hunk 位置精确应用。也就是 `open_draft_pr` 最终提交的内容。
  - 再过服务器沙箱里 git 自己的 `git apply --check`。
  - 两道都过才算通过。
- **报告评论的 outcome 超过 2000 字符就截断**，加上 ` [truncated]`，不再整条拒绝。工作流也先把 outcome 截到 4000 字符：comment_commit 的参数上限是 10 万字符，而错误信息可以任意长，报告却必须发出去。
- **agentd 解析任务的提交号也只看对象头**（`internal/tasks`）：先列出前缀匹配的对象，再查类型和大小，不再对可能巨大的提交做 peel。
- **真实 GitHub 上的 T2 已经准备好**：
  - `scripts/make-audit-target.sh` 用固定的作者和日期造 fixture，提交号固定（HEAD 是 `01f7b30c`）。
  - `tests/test_t2_live.py` 只能经 `live_stack` 这个 fixture 跑，要求 `AGENTOS_GITHUB=live`。
  - 令牌从单独的钥匙串条目 `agentos-github-test-token` 读。
  - 启动 agentd 之前先核对克隆下来的 HEAD 就是 fixture 的提交。

### 我定的几处

- **M3a 留下的问题，现在定为“两道都要过”**：模型给的行号不准时，git 能靠偏移打上补丁，但 agentd 的严格检查会拒绝。这样 apply_check 说能打上的，和 open_draft_pr 实际提交的，始终是同一份。
- **sandbox-runtime 会把沙箱里的 `TMPDIR` 改成它自己的 `/tmp/claude`**，那个目录不可写。所以启动脚本另传 `AGENTOS_TMPDIR`，告诉服务器能写的唯一目录。
- **每次调用的目录放在 `/tmp` 下**，和 Worker 启动脚本的做法一样。
- **show_diff 单个文件的上限定为 4 MiB，所有文件合计 256 MiB**。实测（M 系列 Mac，git 2.50）最费力的是随机短行文件：

  | 单个文件 | 耗时 | 内存 |
  | --- | --- | --- |
  | 1 MiB | 5 秒 | 96 MB |
  | 2 MiB | 11 秒 | 183 MB |
  | 4 MiB | 32 秒 | 356 MB |
  | 8 MiB | 超过 60 秒 | 660 MB |

  - 4 MiB 大约在 30 秒的 CPU 时间上限上下：要么算完后因为 diff 太大被拒，要么 git 在上限处被 SIGXCPU 杀掉、被拒。两种都不重试。
  - 代价：改了 4 到 8 MiB 文件的提交整个拒绝。正常的大 lock 文件只改几行，diff 算得很快，但也一样被拒。
  - 超限的提交整个拒绝，而不是去掉那个文件再显示：路径按字面解释时，没法用 pathspec 排除文件。
  - 合计上限对付的是“很多个大文件、每个只改一行”：每个文件都要整个读进来，耗时随总大小线性增长。
- **`GIT_ALLOC_LIMIT` 定为 256 MiB**：比两个 4 MiB 文件做 diff 时最大的那次分配（约 128 MiB）留出一倍余量。合法的提交对象、树对象远小于这个数。
- **拒绝按 CPU 时间判定，不按墙钟**：两个启动脚本给每个进程 30 秒 CPU（`ulimit -t`）。git 因此被 SIGXCPU 杀掉，算工具错误：同样的输入每次都一样。agentd 那边的 1 分钟墙钟超时按失败处理、会重试，因为慢的可能是机器（负载高、卷挂住了）。有了上面的上限，合法输入几秒内就能算完。`--insecure-dev` 不经过启动脚本，没有 CPU 上限，只有墙钟超时。
- **只有文件头的补丁**：`patch.Check` 拒绝既不新建、也不删除、又没有 hunk 的段落（git apply 会把它当成“没有补丁”）。新建空文件、删除空文件仍然允许，git 也接受。git apply 以 128 退出（不是补丁）时算“打不上”，不再当成服务器故障。

### 推送前审查（安全审查 + 对抗性审查）发现并修掉的问题

两个审查代理都没改文件，下面的问题都核实过、已修，并补了测试：

1. **精心构造的仓库能让 show_diff 看不到改动**（高）。工作树里的 `.gitattributes` 写 `*.py -diff`，或者文件里放一个 NUL 字节，diff 就只剩一句 “Binary files differ”，模型看不到代码。改法：`--text`，属性从空树读，不读系统属性。
2. **replace 引用能换掉被审计的提交，也能换掉 open_draft_pr 写进去的文件**（中）。`git clone --mirror` 会把 `refs/replace/*` 一起拉下来。改法：服务器、`internal/patch`、`internal/tasks` 的 git 都设 `GIT_NO_REPLACE_OBJECTS=1`。
3. **很小的仓库能让 git 用掉无限内存**（中）：输出炸弹、大树、大文件。改法：
   - 输出边读边计数，超限就停掉 git。
   - apply_check 的临时索引只放补丁涉及的文件，不再 `read-tree` 整棵树。
   - show_diff 的单文件上限（上面那条）。
   - Linux 上 `/tmp` 限 64 MiB、地址空间限 4 GiB。
   - 同时最多 4 个服务器。
4. **服务器端的任何失败都被当成 git 拒绝输入**（中）：临时故障让任务直接结束，启动脚本坏了却一直重试。改法：工具错误和协议错误分开报（见上），agentd 启动时自检。
5. **diff 只要有上限的三分之一就会撑破回复上限，然后被重试 5 次**（中）。SDK 会把结构化结果再转义一遍放进文本，JSON 转义最多放大 6 倍。改法：工具自己给一句短文本，diff 用 base64 传，上限按编码后的大小算。
6. **不是 UTF-8 的字节被悄悄替换**（中），审计的 diff 和提交的 diff 不一样。改法：同上，base64 传原样的字节。
7. **apply_check 说能打上、open_draft_pr 却一定拒绝的补丁**（低）：`.github/**` 那批路径只在开 PR 时检查。改法：两边共用一张表。
8. **macOS 上超时的服务器在调用结束后还活着**（低）：只杀了启动脚本。改法：进程组整组杀，调用结束后再杀一次。
9. **服务器的 stderr 进了错误信息**（低）：长的 stderr 会让最终报告发不出去，还会暴露本机路径。改法：stderr 只进 agentd 的日志；评论的 outcome 改为截断。
10. **macOS 沙箱放行的比注释写的多**（低）：能写 `/tmp/claude`，能读别的镜像、TLS 证书私钥、`/tmp` 下别的调用的目录。改法：见上面的启动脚本。
11. **live 模式影响整套测试，还复用正式的钥匙串条目**（低）。改法：见上面的 T2。
12. **调用目录没人清理**（审查列为遗留风险）：agentd 在调用中途被杀（T1 就这么干），目录就留在 `/tmp`。改法：目录名带上进程号，启动时清掉已经不在的进程留下的。
13. **Linux 上沙箱里还能再建用户命名空间**（审查列为遗留风险）。改法：`--disable-userns`。

我自己又发现三处：

- **Linux 沙箱的根目录可写，而且没有大小上限**（补探针时发现）。bwrap 自己建的根目录是一个 tmpfs，归沙箱里的用户所有，上限是内存的一半。写进去的东西不会出现在宿主机上，但被攻破的服务器可以绕过 `/tmp` 的 64 MiB 上限，把宿主机内存写满。现在加了 `--remount-ro /`，只有 `/tmp` 能写。
- **sandbox-runtime 只解析一部分符号链接**（补探针时发现）。denyRead 里写 `/etc/hosts`，沙箱里照样能读 `/etc/hosts`：Seatbelt 按真实路径 `/private/etc/hosts` 匹配，而 sandbox-runtime 只把 `/tmp/...`、`/var/...` 解析到 `/private` 下，别的符号链接都保留原样（比如 `/etc`，或者镜像自己的链接）。agentd 传的路径只要经过这样的链接，原先就屏蔽不了。现在启动脚本把每个路径的真实路径也加进去。（这一条原先写成“`/tmp`、`/var` 下的都屏蔽不了”，第三轮复审指出不对：这两处 sandbox-runtime 自己会解析。）
- **最大的补丁装不进一条请求**。服务器每条请求上限 1 MiB；补丁上限 256 KiB，但控制字符在 JSON 里要转义成 6 个字节，最多约 1.5 MiB。超限的请求让服务器读失败，被当成故障重试 5 次。现在上限按最坏情况算，并用真实的二进制测了一个全是控制字符、大小到上限的补丁。

### 复审（第二轮安全审查 + 对抗性审查）发现并修掉的问题

上面的修复做完后，又开了两个审查代理只看这些修复。它们也没改文件，下面的问题都核实过、已修，并补了测试：

1. **超大的提交对象和树对象绕过所有内存上限**（中）。一个 512 MiB 的提交信息，打包后只有 0.5 MB。服务器的四条 git 命令和 agentd 自己的 `rev-parse` 都要把它整个读进来，各用 500 多 MB，而得到的 diff 只有 99 字节。改法：
   - 提交号只看对象头（`cat-file --batch-check`），超过 1 MiB 不读。agentd 解析任务提交号时也一样。
   - 所有 git 设 `GIT_ALLOC_LIMIT=256m`。撞到上限算工具错误，在 agentd 里算违规。
   - 笔记里原来写的“最坏约 550 MB”不对，已按实测改正（见上面的表）。
2. **合并提交的 diff 包含对每个父提交的 diff**（中，两个审查都发现了）。`-m --first-parent` 对 diff-tree 不起“只看第一个父提交”的作用：`--first-parent` 只管遍历历史。结果是主线自分叉以来的所有改动都被当成这个合并带进来的。改法：`--diff-merges=first-parent`，加了合并提交的测试。
3. **commit() 把 git 的任何失败都说成“镜像里没有这个提交”**（中）。镜像读不了（worktree 的 gitdir 在家目录里、正在重新 clone）时，每个任务都以“没有这个提交”结束，不重试，也不记日志。改法：只看对象头；“missing”或类型不对才算工具错误，git 自己出错算协议错误。
4. **macOS 会删掉闲置的调用目录根**（中）。系统的 tmp_cleaner 每天删 `/tmp` 下 3 天没动过的空目录。`/tmp/agentos-tools.<pid>` 在两次调用之间是空的，删掉后每次调用都失败，直到 agentd 重启。改法：不再有常驻目录，每次调用直接在 `/tmp` 下新建自己的目录。
5. **很多个大文件、每个只改一行的提交**（中）。两个上限都没超，但 diff 会跑过 1 分钟的超时，然后被重试 5 次，每次都占一个空位。等空位的时间还算在调用的超时里，别的任务会因为“没有空位”失败。改法：
   - 所有文件合计 256 MiB 的上限。
   - 拿到空位后才开始算超时，等空位另有 2 分钟上限。
   - 超时算工具错误（第三轮复审后改为：按 CPU 时间判定拒绝，墙钟超时会重试，见下）。
6. **很长的路径让报告发不出去**（中）。一个 10 万字符的路径进了拒绝信息，工作流把它写进 outcome，超过 comment_commit 的参数上限，任务失败，也没发报告。改法：报错里的路径截到 200 字符，工作流把 outcome 截到 4000 字符。
7. **Linux 的 `/dev` 和 `/dev/shm` 也是不限大小的可写 tmpfs**（低），可以绕过 `/tmp` 的上限。改法：`--remount-ro /dev`。
8. **只有文件头的补丁**（低）能过 agentd 的检查，再让 git apply 以 128 退出，被当成服务器故障重试 5 次。改法：见上面“我定的几处”。
9. **钥匙串探针是假通过**（低）。探针的 HOME 不是用户的，security 根本找不到钥匙串，不在沙箱里也一样查不到。改法：显式指定登录钥匙串的文件，沙箱外用同样的环境先查到一次。
10. **屏蔽名单的探针其实被整块屏蔽挡住了**（低）。账本、别的镜像都在 `/var/folders` 下，启动脚本整块屏蔽了那里，名单写错也看不出来；测试还自己抄了一份名单。改法：
    - 整个栈放到 `/var/tmp`，那里不被整块屏蔽，而且 macOS 上要经符号链接。
    - 用一个记录用的启动脚本，录下 agentd 传出的名单，再把它交给探针。
    - 名单的内容由 agentd 的单元测试检查，包括 TLS 证书私钥和 Runtime socket。
11. **带冒号的路径会被拆错**（低）。原来用冒号分隔，镜像目录名里有冒号就屏蔽不了。改法：名单改成 JSON 数组。

另外两条审查列为遗留风险的，也顺手改了：

- 自检原来只调 show_diff，服务器写不了临时目录也能通过。现在也调 apply_check。
- apply_check 和 open_draft_pr 各读各的 deny_paths，“apply_check 放行的补丁 open_draft_pr 一定接受”只在两份一样时成立。现在 apply_check 两份都用。

### 第三轮复审发现并修掉的问题

又开了一个对抗性审查代理，只看第二轮的修复。下面的问题都核实过、已修，并补了测试：

1. **镜像放在服务器二进制旁边时，连它自己的调用都读不到**（中）。macOS 启动脚本放行了服务器所在的整个目录，而 sandbox-runtime 让放行目录之下的屏蔽规则排在后面、优先生效。比如二进制在 `/opt/agentos/`、镜像在 `/opt/agentos/mirrors/` 下，每次调用都失败、重试 5 次。自检用的仓库在 `/tmp` 下，查不出来。改法：只放行二进制本身（原样和真实路径）。
2. **“missing” 又成了永久拒绝**（中）。镜像正在重新 clone，或者对象放在沙箱外的 alternates 里，git 会回答 “missing”、退出码 0，任务就以“没有这个提交”结束，不重试，没有日志。可提交号是 agentd 在任务开始时在同一个镜像里找到的，所以 “missing” 只能是镜像的问题。改法：算协议错误；git 的警告随服务器的 stderr 进 agentd 的日志。
3. **握手之前的超时也成了永久拒绝**（低）。启动脚本卡住（挂住的外接卷、内存换页）时，服务器根本没拿到输入，“同样的输入一样慢”不成立。改法：拒绝改按 CPU 时间判定（见上面“我定的几处”）。
4. **Linux 上撞到地址空间上限还是会重试 5 次**（低）：git 报的是 “Out of memory, malloc failed” 或 “mmap failed”，不是分配上限的那句。改法：这两句也算“太大”。
5. **被攻破的服务器能让自己的调用目录删不掉，在 macOS 上还能写满磁盘**（低）：把目录改成 000，`os.RemoveAll` 不改权限。改法：删不掉时先把目录的权限改回来再删；启动脚本限制单个文件 64 MiB。

提交后，自动的安全审查又指出第 5 条的第一版改法有竞态（中）：先判断“是目录”、再按路径 chmod，中间可以把目录换成指向用户文件的符号链接，agentd 的 chmod 就落到沙箱外了。条件是 macOS 上被攻破、又用 `setsid` 逃出进程组的服务器还活着。改法：
- 平时只删一次，删不掉才去改权限。
- 改权限全程经文件描述符（`fchmodat` 加 `AT_SYMLINK_NOFOLLOW`、`openat` 加 `O_NOFOLLOW`），从不经过符号链接。
- 启动时的清扫只碰属于本用户的真实目录。
- Linux 上这要 `fchmodat2`（内核 6.6 起）；不过 Linux 沙箱根本不挂载宿主机上的调用目录。

审查列为遗留风险的，也改了两条：

- **git 会往上找仓库**：镜像目录要是还不是仓库、又在一个检出的仓库里面（开发配置正是这样放的），agentd 那边沙箱外的 git 会读外面那个仓库。改法：`GIT_CEILING_DIRECTORIES`。
- **测试没检验启动脚本的路径解析**：`/var/tmp` 下的路径 sandbox-runtime 自己就会解析，去掉启动脚本的解析，测试照样通过。改法：另一个镜像改用测试自己建的符号链接配置。验证过：去掉启动脚本的解析，这个测试就失败。

- **Go**：

### 留到后面

- **真实测试仓库上的 T2**：需要你建公开测试仓库和只授权它的细粒度令牌，测试已经准备好。
- **agentd 自己仍在沙箱外读仓库对象**。apply_check 和 open_draft_pr 都要经过 `patch.MirrorSource`，它在 agentd 进程里跑 `git ls-tree` 和 `git cat-file`；任务开始时解析提交号也是：
  - 已经限制了：只读补丁涉及的文件，先查大小，提交只看对象头，单次分配不超过 256 MiB，不读属性，不跑过滤器。
  - 剩下的风险：git 解析对象的代码要是有漏洞，会落在 agentd 身上；树对象可以接近 256 MiB。
  - 改法：把这些读取也挪到沙箱里的服务器后面，加一个按路径返回文件内容的工具。
- **macOS 上服务器的内存没有总上限**：Seatbelt 管不了内存，macOS 也不执行 `ulimit -v`。目前靠这几样兜住：单次分配 256 MiB、单文件 4 MiB、合计 256 MiB、30 秒 CPU、同时 4 个服务器。实测最坏的单个文件约 360 MB。层层嵌套的大树对象还能叠加。Linux 每个进程有 4 GiB 的上限，但 4 个服务器加起来会超过 6 GiB 的虚拟机内存。
- **最坏的输入要耗 30 秒 CPU**：接近上限、内容是随机短行的文件，git 会一直算到 CPU 时间上限。那算工具错误，所以每个任务最多耗一次。
- **macOS 上被攻破的服务器还能写满磁盘**：单个文件限 64 MiB，但文件个数不限，1 分钟内能写很多。Linux 上 `/tmp` 只有 64 MiB（只限文件内容，inode 和 xattr 不受限，见下）。它还能给文件加不可改标志（`chflags`），删除就会失败；只有攻破了服务器才做得到。
- **自检用的是 `/tmp` 下的临时仓库**：某个配置好的镜像沙箱里读不了，要等第一次调用才发现（按失败处理，重试，记进日志）。启动时可以对每个镜像经启动脚本查一次。
- **macOS 上服务器还能读家目录以外的系统文件**：sandbox-runtime 的读权限是按黑名单屏蔽，和 Worker 的沙箱一样。两个平台的沙箱定稿在 M5。
- **sandbox-runtime 自己加的环境变量会留在沙箱里**：代理设置、`GIT_SSH_COMMAND`、`GIT_CONFIG_PARAMETERS` 等。服务器跑 git 前去掉了所有 `GIT_` 变量，沙箱也不允许任何网络。
- **在 macOS 上，自己调用 `setsid()` 的进程能逃出进程组的整组击杀**。在 Linux 上，bwrap 的 `--die-with-parent` 会结束它。
- **bwrap 没有 seccomp 过滤**。
- **Worker 的 Linux 沙箱（`run-worker.sh`）**：原来根目录、`/dev`、`/tmp`、`/run` 四处都是不限大小的可写 tmpfs。2026-10-18 已修：Worker 哪儿都不能建文件，也不许再建用户命名空间（见 `docs/m1-notes.md`）。
- **工具服务器的 `/tmp` 只限文件内容**：`--size` 管不住 inode 和 xattr。在 Worker 的沙箱上实测过同样的 tmpfs：6 万个空文件占了 51 MiB 不记在进程名下的内核内存，上限约为内存的 1/8，每次调用一份，最多 4 个同时，调用结束才释放。要靠 cgroup（M5）。
- **Linux 启动脚本不看 `AGENTOS_SANDBOX_DENY_READ`**：只挂载 `/usr`、镜像和服务器，所以只有 agentd 要屏蔽的东西放在 `/usr` 下面时才有影响。
- **镜像目前是测试自己 clone 的普通仓库**：属性从空树读，所以工作树不会被读到。以后自动建镜像时，用裸仓库，只取分支和标签。
- **镜像必须属于运行 agentd 的用户**：git 不读全局配置，也就不认 `safe.directory`。属于别的用户的镜像，git 一律拒绝（“dubious ownership”）。agentd 解析提交号时会把 git 的原话报给 agentctl；服务器那边按协议错误处理，原因记进 agentd 的日志。
