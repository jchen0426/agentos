# M2 记录：模型网关与预算

M2 拆成三段（设计文档第 12 节）：M2a 预算、M2b Claude 适配器、M3 之后的 M2c OpenAI 兼容适配器。

## M2a：预算（2026-10-17）

验收 T7 通过。供应商仍是假的，预算逻辑本身和供应商无关。

### 做了什么

- **价格表** `config/prices.yaml`（`internal/pricing`）：带版本号，单位是美元每百万 token，也就是每 token 多少 micro 美元。内部按千分之一 micro 存成整数，$0.20 这样的价格也是精确值；所有取整一律向上。没填价格（null）的模型调用不了；agentd 启动时检查每个任务可能用到的模型（含回退）都有价格。
- **上限**：输入 token（供应商的计数方法）加 10%，乘以所有候选模型里最高的输入单价（含缓存写入价）；再加 `max_tokens` 乘以最高的输出单价。`max_tokens` 现在是 `models.yaml` 的必填项。
- **账本**：迁移 `00003_budget.sql` 重建了 `budget_entries`（M1 的占位表从没写过数据）。每次网络请求一条 RESERVE，之后恰好由一条 SETTLE 或 RELEASE 关闭，两个部分唯一索引保证这一点；EXTEND 按 `(run, 幂等键)` 去重。预留在一个 IMMEDIATE 事务里检查“已结算 + 未结算预留 + 本次 ≤ 上限”再写入。
- **网关**：模型调用改成“计数 → 预留 → 记录请求 → 发送 → 结算”。答复和结算在同一个事务里落库。没答复的请求按三种情况关闭：没离开 agentd 的释放；供应商回 429/5xx 的按 0 结算；其余（超时、连接断开）不知道供应商收没收费，按整笔预留结算。预留不够时返回 `budget_exhausted`，工作流停在 PAUSED_BUDGET。
- **崩溃**：agentd 启动时，在接任何请求之前，把还开着的预留按全额结算（reason `open_at_start`）。T1 的“供应商已答复、结果没落账时杀 agentd”现在断言了这一条。
- **追加**：`agentctl budget extend <run-id> --usd 2.50`（`ExtendBudget`，幂等键默认每次新生成）。记下 EXTEND 后直接给工作流发门铃信号；通知 outbox 留到 M4。门铃丢了，暂停的调用最多一小时后也会自己重查。`runs get` 显示已花、已预留和上限。
- **适配器接口**：拆成 `CountTokens` 和 `Call` 两步，`Call` 只发一次网络请求，错误分三类：`ErrNotSent`、`*RejectedError`（429/5xx 可重试，其余不可重试）、其他（结果未知）。

### 我做的取舍（开工前已确认）

- 429/5xx 不在网关里重试，交给 Temporal 的活动重试：每次尝试一个请求、一笔预留。重试节奏由工作流定，所以保护供应商的只能是网关的限流，限流要和 Claude 适配器（M2b）一起上线。
- 结构化输出校验、拒答、缓存统计、限流、循环保护放到 M2b。

### T7 怎么测

一个工作流同时发 50 个模型调用，起始预算只够约 20 笔预留。测试本身发现一个问题：假供应商一次调用约 1 毫秒，前面的调用很快按实际费用结算、腾出余额，后面的就都能预留，50 个全部通过，根本没有争抢。所以测试让每个请求在发出前持有预留 500 毫秒。

- 第一波（前 50 次调用）不注入故障：20 笔预留成功，30 个调用停在 PAUSED_BUDGET。
- 追加 $5 后第二波：按调用次序注入 429、500、答复丢失、请求没发出、按回退模型答复各一次。预算充足，每个故障都必然触发。
- 断言：按写入顺序重放账本，每一条之后都满足“已结算 + 未结算预留 ≤ 上限”；每笔预留恰好关闭一次，结算不超过预留；假供应商自己的记录（测试用自己的单价独立计价）和账本逐个请求对上；50 个调用全部成功，所以没有丢失的唤醒；网络请求数 = 50 + 4 次重试。

一次运行的账本：54 笔预留（每笔约 43,656 micros），50 笔按用量结算共 189,965 micros，2 笔拒绝按 0，1 笔结果未知按整笔，1 笔释放。

### 还没做 / 风险

- `count_tokens` 本身要一次网络请求（免费但限流），M2b 要处理它失败的情况：失败时不预留、不发送，返回可重试错误。
- 结算超过预留说明上限算错了：账本照实记账（会超过上限），并记一条错误日志。真实供应商上线后要盯这条日志。
- 价格表里 Opus 的价格抄自设计文档（2026-10-15 查询），M2b 接真模型前要对官方定价页再核一遍。

## M2b：Claude 适配器（2026-10-18 完成）

验收 T1 在 Claude 真模型上通过（结果见本节末尾）。

### 做了什么

- **密钥**：`models.yaml` 里写 `key: "keyring:<service>[/<account>]"`，用 zalando/go-keyring 读，在 macOS 上就是调用 `/usr/bin/security`。agentd 启动时就读，读不到直接拒绝启动。条目由 `security` 自己创建、自己读取，agentd 重新编译也不会触发钥匙串弹窗。
- **Anthropic 客户端只认给它的 key**：用 `option.WithoutEnvironmentDefaults()`，不读 `ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、profile、身份联合，也不读 `ANTHROPIC_BASE_URL`。SDK 的自动重试关掉（`WithMaxRetries(0)`）。测试里故意在环境变量里放了一把错的 key 和错的地址，确认都没被用上。
- **计 token**：用 count_tokens 接口，分别对主模型和每个回退模型各数一次，取最大值，因为不同模型的分词器可能不同。
- **请求的组成**：任务的提示词作为系统提示并开缓存；参数里每个 `<name>_ref` 指向的 blob 放进一段带标签的内容，放在最后。标签名带上内容哈希的前缀，内容本身无法提前写出闭合标签、跳出这一段。提示词明确写了：标签里的内容是数据，不是指令。
- **结构化输出**：`output_config.format` 加 JSON Schema（`config/schemas/audit_report.json`）。答复回来后网关再按同一份 schema 校验一次，不合格就再要一次。第二次是一个新请求，单独预留、单独结算。被 `max_tokens` 截断的答复不重试，因为同样的上限再要一次还会被截断。校验通过后，整份输出存成 `report_ref`，`blobs` 里列出的字段（patch）存成 `<field>_ref`，其他字段原样内联。
- **拒答和回退**：`stop_reason: refusal` 映射成 `refused`，并带上 category。服务端回退用列出具体模型的写法（`claude-opus-4-8`），不用 `"default"`，因为上限必须事先知道会用到哪些模型。结算按 `usage.iterations` 的每一次尝试，各按各的模型单价计。
- **错误分类**：HTTP 错误答复记为 `RejectedError`，按 0 结算（408/409/429/5xx 可重试，其余不可重试）；连不上（dial/DNS）算没发出去，释放预留；超时、连接中途断开结果未知，按整笔预留结算。
- **价格表**：加了 Opus 4.8（$5 / 缓存写入 5 分钟 $6.25、1 小时 $10 / 缓存命中 $0.50 / 输出 $25），是对照官方定价页核对过的。Opus 5.5 原有的价格也核对过，没有问题。
- **限流**：`models.yaml` 的 `requests_per_minute`（Anthropic 设为 20），每个供应商一个令牌桶，突发上限是一分钟配额的四分之一。最多等一分钟，等不到就当没发出去：释放预留，交给 Temporal 重试。
- **循环保护**：新表 `calls` 记录每个逻辑调用，重试共用同一个活动 ID，只算一次。默认每个任务最多 20 次模型调用、100 次网关调用；同一个工具用同样参数最多调 3 次。“同参数”只对工具计：模型调用在预算暂停或审批之后会用同样的参数重发，这是正常流程，不是循环。
- **其他**：网关改为按供应商名找适配器，因为同一种适配器可能接多个供应商、各用各的 key。`model_calls` 加了 `request_seq`（迁移 00004）。开发用的 Claude 配置是 `config/dev/agentd-claude.yaml`。

### 还没做 / 要注意

- `max_tokens` 先设 16000，不流式。Opus 5.5 的思考也算在输出 token 里，如果经常被截断，就改成流式并调大，预留也会跟着变大。
- 安全审计任务可能碰到网络安全类拒答。Opus 5.5 允许“在源码里找漏洞”，提示词也要求不写利用代码；误拒时回退到 Opus 4.8。

### 推送前的安全审查（2026-10-17）

这次在推送之前就做了安全审查，没有像 M1 那样推完才查。审查没有发现 key 外泄的路径：日志、错误信息、账本、请求和答复记录里都没有。它报了 6 个问题，下面是核实之后的处理：

1. **回退时预留不够**（中）：一次请求里，主模型可能先输出一段再拒答，回退模型再按自己的 max_tokens 输出，两次都要计费。原来的上限只按“最贵的那一个模型”算，确实可能结算超出预算上限。现在上限改为把每个候选模型各自的上限加起来。代价是开回退后，每笔预留大约翻倍，比如 2 万 token 的 diff 从约 $0.62 变成约 $1.4。**这和设计文档第 9 节“预留按所有候选中最贵的算”不一致，文档要改，改之前先给你看改动清单。**
2. **循环保护能被绕过**（中）：活动 ID 由 Worker 自己选，而且一个活动结束后，它的 ID 可以拿来再用。现在一个逻辑调用由“活动 ID + Temporal 首次调度它的时间”来认。这个时间由服务端填写、重试时不变，所以重用 ID 发起的新调用会被重新计数。另外网关自己限制每个调用最多 10 次尝试，因为重试策略是 Worker 写的。还有一个口子没堵上：参数里多塞一个无关字段，就能绕过“同参数”的计数，要等 M3 给工具加参数 schema 时一起解决；在那之前，总调用数的上限照样有效。
3. **开发流程里 Worker 读得到 key**（中）：Worker 不开沙箱时，它和你是同一个用户，能用 `security` 读出钥匙串里的 key。实测在 srt 沙箱里读不到：带上钥匙串文件路径也找不到，列 `~/Library/Keychains` 会报 Operation not permitted。沙箱探针加了这两项检查；README 里提醒：只要用了真 key，Worker 就必须开沙箱。
4. **blob 可以跨任务读**（中）：模型调用原来会展开参数里任意一个 `sha256:` 引用，Worker 只要从别的任务的历史里看到某个引用，就能让模型读到别的任务的内容。现在每个 blob 记录是哪个任务产生的（迁移 00006），适配器只展开本任务自己的。引用参数的名字必须是小写字母和下划线，同一个 blob 不能用两次。
5. **计 token 不受限流和预算约束**（低）：现在预算连输出那部分都不够时，直接返回预算不足，不再去计 token；加上每个调用最多 10 次尝试，计 token 的次数就有了上限。
6. **key 引用写错时把原值写进日志**（低）：错误信息里不再回显这个值，因为它可能就是一把误填进去的真 key。

审查列的剩余风险里，又改了三处：
- 500/502/504 改为按整笔预留结算，只有 429、529 和其他 4xx 才按 0 结算，因为这几种 5xx 可能是服务端已经算完、在网关层超时；
- 回退时只取最后一个 fallback 块之后的答复；
- `max_tokens` 超过 SDK 的非流式上限时，agentd 启动就报错。之前这种情况会在发请求之前失败，却按整笔预留扣钱，而且每次重试都扣。

**留到后面的：**
- M3 接真工具时，dev policy 里 `open_draft_pr` 不需要审批、也没有 `deny_paths`，有人在 diff 里注入指令，就可能开出一个改 `.github/**` 的 PR。所以 `agentd-claude.yaml` 到时候要换成需要审批的 policy。
- 限流不分任务，一个预算充足的任务能占满每分钟 20 个请求的配额。
- Worker 能从 Temporal 的失败信息里看到 Anthropic 的 request ID 和 workspace ID，这些不是密钥。
- srt 沙箱里，`security` 仍然能列出系统钥匙串（`/Library/Keychains/System.keychain`）的条目属性，比如 Wi-Fi 网络名。读取密码需要管理员授权，你的登录钥匙串也碰不到（探针检查的就是它）。这算一个小的信息泄露，留到 M5 沙箱定稿时，看能不能连 securityd 也一起挡掉。

### 验收：T1 在 Claude 真模型上（2026-10-18）

- **验证 key**：先用免费的 count_tokens 确认 key 能用，这个请求的输入是 1282 个 token（Opus 5.5 和 Opus 4.8 两者取大的那个）。这个线上测试留在仓库里（`AGENTOS_LIVE=1 go test ./internal/models -run Live`），默认跳过。
- **测试框架的真模型模式**：`AGENTOS_MODEL=claude`。T1 原来的断言依赖假模型的行为，现在两种模式通用：
  - “开没开 PR”改为看模型的答复里有没有补丁；
  - 供应商收到几次请求，真模型模式下改为看账本里没释放的预留；
  - “供应商已答复”改为看网关新加的一行 `model answered` 日志。

  `max_tokens` 测试里压到 8000，这样一次请求的最坏花费约 $0.36。Worker 跑在 srt 沙箱里，因为这次 agentd 拿着真 key。
- **结果**：4 个测试全部通过，实际一共花了约 $0.05。

  | 测试 | 实际花费 |
  |---|---|
  | 模型调用进行中 kill Worker | $0.014，首次写入缓存 |
  | 模型答复后、工作流任务提交前 kill Worker | $0.009，命中缓存 |
  | 供应商已答复、结果没落账时 kill agentd | 约 $0.017 |
  | 结果落账后 kill agentd | $0.008 |

  “结果没落账时 kill agentd”那个测试里，账本按整笔预留（$0.387）记了丢失的那次请求，这是有意的保守做法；Anthropic 实际收的只是它的真实用量（约 $0.009）。
- **观察**：
  - 系统提示词加 schema 共 1212 个 token，跨任务被缓存命中，命中后按 5% 的价格计；
  - effort 设为 high 时，每次输出只有 370 个 token 左右，没有被截断，也没有用到重新生成或回退；
  - Claude 准确指出了测试 diff 里的 SQL 注入（CWE-89，high，`app/db.py` 第 2 行），并给出了修复补丁。

## M2c-a：OpenAI 兼容适配器（2026-10-18）

一个适配器接 OpenAI 和本地模型服务，外加跨供应商回退。用能模拟两种接口的假模型服务器验收 T13。真模型上的 T1 留给 M2c-b。

### 做了什么

- **适配器 `openai_compat`**（`internal/models/openai.go`，openai-go v3.81.0），`models.yaml` 的 `api` 选后端：
  - `responses`：OpenAI 的 Responses API。
    - 计数用官方的 `/v1/responses/input_tokens`：数的就是要发的那个请求，和 Claude 的 count_tokens 一样是精确值。
    - 输出用 `text.format` 的 JSON Schema，strict 模式。
    - 推理强度用 `reasoning.effort`，输出上限用 `max_output_tokens`（含推理）。
    - 固定 `service_tier: default`：价格表列的是这一档，项目默认档可能是别的、价格不同。万一答复来自别的档，就按价格表里没有的模型名计费，网关会按整笔预留结算并记日志。
    - 带 `store: false`：OpenAI 新账号默认会存下对话。
    - 带 `safety_identifier`：每个安装随机生成一次，存在数据目录的 `safety-identifier` 文件里（0600），不含任何个人信息。OpenAI 的安全机制被触发时，被追究的是这个标识，不是整个组织。
    - 用 `prompt_cache_key` 让同一个任务的请求落到同一份缓存上。
    - 答复状态是 `failed` 时：错误码是安全类的（`cyber_policy`、`bio_policy`、`misalignment_policy_violation`、`invalid_prompt`）算拒答，其余按“结果未知”处理（扣整笔预留，Temporal 重试）。`invalid_prompt` 是 OpenAI 的“提示词疑似违反使用政策”，作为 400 错误返回时也算拒答，这样跨供应商回退才接得上。计数时就被拒的，按 4xx 处理、不重试。
  - `chat`：Chat Completions，给 Ollama 和 vLLM。
    - 输出上限用 `max_tokens`：Ollama 不认 `max_completion_tokens`，只传它的话就没有上限。
    - 输出用 `response_format` 的 JSON Schema：Ollama 把它变成受约束的解码，忽略 strict。
    - 推理强度用 `reasoning_effort`。
  - 客户端只用显式给的地址和 key：不用 `openai.NewClient`（它会读 `OPENAI_*` 环境变量），而是直接建各个服务；SDK 的自动重试关掉。
  - 不流式：`max_tokens` 按 Anthropic SDK 的估法（每小时 12.8 万 token）可能超过 10 分钟的，启动时就拒绝，和 Claude 适配器一样。
  - 域名解析失败、连不上、代理建隧道失败、TLS 不信任服务器证书，都算“没发出去”，释放预留。Claude 适配器也按这条改了，原来这几种会扣整笔预留。
- **本地模型的上下文**：Ollama 的兼容接口不能设上下文长度。我看了 Ollama v0.40.6 的源码：输入超长时，它会悄悄截到大约半个窗口；答复写到窗口外时，它会挪动窗口、丢掉输入的开头。所以：
  - provider 里配 `context_tokens`（就是 Ollama 启动时设的 `OLLAMA_CONTEXT_LENGTH`）。
  - 发送前用 o200k_base 估算输入（gpt-oss 用的就是这套编码），再加上 schema、乘 1.2 作余量；加上 `max_tokens` 超过上下文就不发。
  - 分词按约 1 KB 一段来数，尽量在行尾切开，超过上下文就停：没有空白的长串（比如一长行 base64）整段交给分词器，耗时会按长度的平方增长。
  - 返回后核对 Ollama 报的 `prompt_tokens`（含缓存命中的部分）：输入加输出超过上下文，或者读到的不到原始估算（提示词加输入，不含 schema、不加余量）的 4/5，就判为被截断，不接受这份答复。
  - 服务器回 400、说超出上下文长度的（OpenAI 的 `context_length_exceeded`、vLLM、关了窗口挪动的 Ollama）也算超长，按 0 结算。
  - 这些都是 `ErrTooLong`，不重试。
- **推理强度**：provider 里列 `efforts`（这家的模型接受哪些）。任务的 effort 映射成列表里不超过它的最高一档；都比它高时，发列表里最低的一档（不发的话，服务端会用自己的默认值，往往更高）。任务的 effort 加载时就检查是不是已知的七档之一。实际发出的值记在答复里（`effort` 字段），没发就为空。
- **拒答**：Responses 输出里的 refusal 内容、`content_filter`、安全类错误码，Chat Completions 的 `refusal` 字段和 `content_filter`，都映射成 `refused`。拒答之前模型写出的内容照样计费；作为错误返回的安全类拒答不计费。注意：Ollama 的兼容接口没有 `refusal` 字段，本地模型拒答时只会答出一段不合 schema 的文字，走的是“重新生成”那条路。
- **禁止 cloud 模型**：Ollama 会把 cloud 模型的请求发到它自己的服务器，任务数据就离开了本机。三道防线：
  - 模型名带 `:cloud` 或 `-cloud`（不分大小写）就拒绝加载，对所有 `openai_compat` 供应商都查：Ollama 也提供 Responses API。
  - 每次计数和每次请求之前，都先问一下服务器的 `/api/show`：答复里有 `remote_host` 或 `remote_model` 的，就是改了名字的 cloud 模型，拒绝发送。不缓存：本机任何程序都能通过 Ollama 的接口把一个名字改指向 cloud 模型。配了 key 就带上 key；没有这个接口的服务器（vLLM）回 404 或 405，跳过；别的答复按没发出去处理。只问 `api: chat` 的和地址在本机的服务器，不问 OpenAI。
  - README 让 Ollama 带 `OLLAMA_NO_CLOUD=1` 启动（v0.40.6 有这个开关），服务器自己就不跑 cloud 模型。
- **跨供应商回退**：
  - `fallback` 收紧为同一供应商的服务端回退（只有 Claude 有）。别家的模型列在新的 `cross_provider_fallback` 里。
  - 只在拒答时触发；输出不合格还是在原模型上重新生成，出错由 Temporal 重试。
  - 每一跳是一个新请求：请求序号接着往下数，只预留它自己可能计费的模型，预算不够就停在 PAUSED_BUDGET。
  - **接着上次的位置继续**：重试、丢了结果的活动、预算暂停后重新发送的调用，都跳过已经拒答过的那几家，不会再问一遍、再付一遍。“拒答过”要供应商、模型、提示词版本和 effort 都对得上：改了提示词或者换了顺序，没拒答过的照样会问。预算暂停后工作流会换一个新的活动 ID 重发同一个调用，所以网关按“同一任务、同一参数、前一个调用以预算不足结束”把它们连起来（调用记录表里本来就有参数的哈希）。
  - 某一跳因为不会好转的原因发不出去（没价格、对方 4xx、输入超长、是 cloud 模型、没有适配器、策略不允许）就跳过，问下一家；都答不了就以拒答结束，不让回退的失败盖掉原来的结论。最后一次尝试上，可重试的错误（429、500、连不上）也这样处理：没有下一次尝试会再问这家了。
  - **一次尝试只有 10 分钟**（工作流设的 start-to-close），所有跳共用。一次尝试里第二个及以后的请求，如果剩下的时间不够它可能花的时间（同上的估法），就先不发：不预留，交给下一次尝试从这一跳开始，有完整的 10 分钟。最后一次尝试上就按上一条跳过。否则它会在半路被截断、扣整笔预留，然后照样重来。
  - 换过去之前按策略检查这家供应商；agentd 启动时也检查，回退目标不在策略允许的供应商里就拒绝启动。启动时的价格检查和路由检查也覆盖每一跳。
- **价格表**：
  - 加了不分时长的 `cache_write`（OpenAI 写缓存按输入价的 1.25 倍收）和对应的用量字段。
  - 加了长上下文档位 `long_context`：输入超过阈值时，整个请求的输入（含缓存）和输出都按倍数计。OpenAI 的 GPT-6 是 272K、2 倍和 1.5 倍。预留按加了 10% 余量的输入判断档位，结算按实际输入判断。
  - `config/prices.yaml` 加了 gpt-6.1-sol（$2 / 写缓存 $2.50 / 读缓存 $0.10 / 输出 $10，2026-10-18 对照官方定价页）和 `local/gpt-oss:20b`（零单价）。
  - `api: chat` 的模型单价必须是 0，否则 agentd 拒绝启动：这类服务器发请求前没法精确计数，估算出来的预留只有在不收钱时才算得上“上限”。
- **key 和 https**：Claude 和 OpenAI（`api: responses`）必须有 key，只有地址是本机回环的服务器（本地模型服务、测试里的模拟器）可以不配。Chat Completions 的服务器只在 `models.yaml` 写了 key 时才读。不在本机的供应商，地址必须是 https：请求里有任务的 diff，也有 key。
- **调用记录**：请求记录里除了任务的 effort，还记了实际发给这家的 effort（`effort_sent`）。
- **Go 工具链升到 1.26.9**（`go.mod` 的 `toolchain`）：openai-go 的 HTTP/2 安全修复需要它。

### 我定的几处

- **一个适配器、两套请求编码**：两种后端的差别不只是地址（输出上限的字段、有没有 refusal、会不会截断），所以按 `api` 分开编码和解析，共用拼接带标签的 blob 那段（从 Claude 适配器里抽成了 `userMessage`）。
- **按请求的模型名计费**：OpenAI 的答复里可能是带日期的快照名（`gpt-6.1-sol-2026-09-30`），价格表里没有，所以按请求时的模型名计费。
- **截断的判定线定为原始估算的 4/5**：Ollama 截断时会砍到半个窗口左右，读到的远少于发出的；别家分词器比 o200k_base 省 20% 以上的情况很少。估算不含 schema：Ollama 用 schema 约束解码，不把它放进提示词，算上它会误判小请求。
- **`api: chat` 只接免费的本地服务**：见上面价格表那条。要接收费的 Chat Completions 服务，得先有精确计数的办法。
- **预算暂停后的续跑靠调用记录表认“同一个调用”**：不改工作流、不加新表。代价是：工作流如果有意用同样的参数把同一个任务再问一遍（先后或者同时），而前一次正好停在预算不足，这次也会跳过已经拒答的那家。同样的输入在同一个任务里已经被拒过，再问多半还是拒，所以我接受这一点。
- **答复状态 `failed` 默认可重试**：错误码里分不清哪些会好转，按“结果未知”扣整笔预留、最多重试 5 次；安全类错误码除外。
- **局域网里的模型服务也要 https**：一台装了 GPU 的机器跑 vLLM 用 http 很常见，但 diff 会明文过网络。对你没影响（Ollama 在本机），别人要用就在前面加一层 TLS。
- **剩余时间的估法用 Anthropic SDK 的**：每小时 12.8 万 token，对哪家都偏慢，宁可多换一次尝试，也不让请求半路被截断。

### 测试怎么测

- **Go**：
  - 适配器对着 httptest 服务器测两种后端：
    - 请求的形状（store、safety_identifier、service_tier、strict、推理强度、`max_tokens`）；不流式时可能超过 10 分钟的 `max_tokens` 启动时拒绝；
    - 故意设置错误的 `OPENAI_*` 环境变量，都没被用上；不自动重试；
    - 用量映射，含缓存写入；别的服务档按无价模型计；
    - 三种拒答、`failed` 状态、`invalid_prompt`、计数时被拒、错误分类（429、500、400、超出上下文、连不上、TLS 不信任）；
    - 超长拒发、两种截断检测、Ollama 的“提示词过长”400；
    - cloud 模型：改了名的也拦住、每次都问、请求一个都没发出去；带上 key；405 跳过、401 不发；OpenAI 不问。
  - 分段计数：在行尾切开时和整段数的结果一样；4 MiB 没有空白的长串几秒内数完并提前停下；取消后立即返回。
  - 网关的续跑（对着真的 SQLite 账本）：丢了结果后拿到回退那家的答复；回退那家没答完时只问它；两次预算暂停串起来，时间戳按文本排序是反的也对；models.yaml 换了顺序、改了提示词；前一个调用不是以预算不足结束、或者没记下结局时不串；剩余时间不够时交给下一次尝试、最后一次尝试上算这一跳失败。
  - strict schema 的子集检查（审计报告的 schema 能过；可为 null 的对象、布尔 schema、propertyNames、required 里的未知字段）；模型配置的校验（含大写的 cloud 名、未知的 effort）；价格档位的边界；`Free`；key 只走 https；safety_identifier 随机、只生成一次、0600。
- **黑盒**：
  - `tests/test_t13_model_errors.py`（T13）：一个假模型服务器（`internal/modelsim`）同时说 Anthropic、Responses、Chat Completions 三种协议，答复和用量都一样。对每种接口依次注入 429、500、答到一半断开、拒答、不合 schema，检查三种接口逐项一致：
    - 供应商实际收到几次请求；
    - 每个请求按哪种原因结算、结了多少（Chat Completions 免费，金额都是 0）；
    - 任务的结论；
    - 每个请求带的 `max_tokens` 和映射后的 effort；Responses 请求的服务档、`store` 和数据目录里的那个 safety_identifier；本机服务器在每次计数和请求之前各被问一次 `/api/show`。

    另有两个：改了名的 cloud 模型一个请求都收不到、也不预留；`api: chat` 的模型标了价，agentd 拒绝启动。
  - `tests/test_cross_provider_fallback.py`：两个假供应商，第一家按故障脚本拒答：
    - 第二家接手作答，两次请求各自预留、各自结算、各有一条调用记录；
    - 第二家第一次回 429：重试从第二家接着问，第一家只被问过一次；
    - 第二家的答复落账后、Temporal 收到之前 kill agentd：重试直接拿账本里第二家的答复，谁都没再问；
    - 预算只够第一家：停在 PAUSED_BUDGET，`agentctl budget extend` 之后新活动直接问第二家；
    - 第二家回 400：以拒答结束，日志里写明为什么没有回退成；
    - 没配回退时拒答就是结论；回退目标不在策略里时 agentd 拒绝启动。

### 推送前的两轮评审（2026-10-18）

第一轮开了两个评审 agent（一个找逻辑漏洞，一个看安全）。上面“做了什么”里的续跑、跳过失败的一跳、每一跳都做启动检查、`api: chat` 必须免费、固定服务档、`failed` 状态、截断检测、分段计数、cloud 模型探测、key 的规则、effort、strict schema、随机的 safety_identifier，都是那一轮报出来的。最重的一条是：用了回退之后，重试会把第一家的拒答直接交回去，或者从头再问一遍。

第二轮复查确认这 13 处都改对了，又报了 5 条：

1. **所有跳共用一次尝试的 10 分钟**（中）：第一家慢慢拒答完，第二家的请求会在半路被截断、扣整笔预留再重来；OpenAI 的 `max_tokens` 设大了，每次尝试都会超时。改成上面说的“剩余时间不够就交给下一次尝试”，外加启动时的时长检查。
2. **改了 models.yaml 之后续跑会跳过没拒答过的那家**（低）：原来按“最远的拒答之后”往下问，换了顺序就会跳错。改成只跳过真正拒答过的那几家，并且要提示词版本和 effort 都对得上。
3. **回退那家一直连不上，会把已经付过钱的拒答丢掉**（低）：每次尝试都从回退那家重试，5 次用完任务就失败了。改成最后一次尝试上跳过它，以拒答结束。
4. **OpenAI 的 `invalid_prompt` 没算拒答**（低）：它是使用政策类的拒绝，没算拒答的话回退接不上；计数时被拒的还会白白重试 5 次。都改了。
5. **cloud 模型探测的结果缓存了一辈子**（低，安全）：第一次问过之后，本机别的程序把这个名字改指向 cloud 模型，以后的 diff 就都发出去了。改成每次都问，加上 `OLLAMA_NO_CLOUD=1`。

另外按它列的剩余风险改了三处：TLS 和代理隧道失败按没发出去处理；局域网里的服务也要 https；请求记录里加上实际发出的 effort。补了它指出缺的测试：网关续跑的单元测试，和“回退那家的答复落账后 kill agentd”的黑盒测试。

**没改、记下来的：**
- `context_tokens` 配得比 Ollama 实际的窗口大时，答复写到窗口外被挪动，两道截断检查都发现不了。Ollama 的 `/api/ps` 能看到已加载模型的实际窗口，以后可以拿来核对。
- 4/5 的判定线对分词比 o200k 省 20% 以上的模型会误判，误判时这一跳以“输入超长”失败。
- 记下调用结局（`SetCallOutcome`）失败时只写日志：预算暂停后的续跑就串不上，会从头问、多付一次。
- Worker 重用活动 ID 时，新调用会拿到旧调用的答复，现在连拒答记录也算上。这一条 M1 就有，范围只在同一个任务里。
- 单价标成 0 的收费 Chat Completions 服务，预算对它就不起作用了。

### 还没做 / 要注意

- **M2c-b**：OpenAI（gpt-6.1-sol）和本地模型（gpt-oss:20b）上各跑一遍 T1。需要你建 OpenAI 的 key（建议单独一个项目、设月度预算）、把 Ollama 升到 0.40.x 并拉模型。
- **T13 里 `agentctl runs explain` 的部分**随 T12 放到 M5。
- **OpenAI 的计数接口是否收费**，官方文档没写；Responses 和 Chat Completions 之外的新功能（Daybreak 的 cyber 访问计划）没有接。
- **本地模型的计数是估算**：只用来判断装不装得下，它的 token 不进预算。
- **HTTPS_PROXY 之类的代理环境变量**仍然对所有模型请求生效（Go 的默认 transport 会读），Claude 适配器也一样。要不要关掉，等 M5 收紧部署时一起定。
