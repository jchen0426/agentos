# 副作用协议的状态机测试

2026-10-21。M4 的五轮审查一直在同一片状态空间里手工找边角情况，这次改成系统地找：给 agentd 的副作用协议（`internal/gateway` 的 effects.go、approvals.go，账本是真实的 SQLite）写了一个带种子的随机状态机测试。它找出了 5 个问题，都已修掉并各自补了单元测试；把 M4 第三到五轮审查找到的问题逐个改回去，它都能抓住。

## 做了什么

- **测试**：`internal/gateway/statemachine_test.go`（游走、不变量）和 `statemachine_world_test.go`（假的外部世界、假工具）。每个种子是一次游走：一到三个写工具（lookup、幂等、unsafe 各一个），每个一到两组参数，一个任务开始，之后不时有新任务开始。每一步从下面这些里抽一个：
  - 调用一个写，有或没有审批规则（策略要求审批、工具连得上、任务不是 dry-run 时才有规则，和 `dispatch` 一样）；调用多半落在还没结束的写上（等审批、发送中、等人核对，或者还没调过的）；
  - 人对审批单的决定：批准、拒绝、修改（修改后工作流会调“修改后的调用”）；偶尔看的是别的载荷哈希，偶尔用原来的幂等键重发决定；
  - 拨钟（5 秒到 26 小时），以及到期循环跑一轮；
  - 人核对 UNKNOWN 的写：已执行（给结果或让 agentd 查）、未执行；
  - 取消任务、任务的工作流结束（之后的决定和核对带 RunClosed）；
  - agentd 死掉、新的 agentd 在同一个账本上起来（大多做启动恢复 `RecoverEffects`，有时不做，留给调用路径上的恢复）；重启时可能换某个工具的策略（放行和要求审批互换、TTL、`max_per_run`、声明为 unsafe），也可能从连得上 GitHub 变成连不上，或者反过来。
- **工具的每次尝试**由游走抽：成功、结果不明（请求已发出，可能马上生效、晚一点生效或永不生效）、还没发就结果不明、`ErrNotSent`、可重试的拒绝、不可重试的拒绝、发送前被工具拒绝（denied）、对方已有同名的别的东西（conflict），以及两个请求的写（先发一个，比如推分支，再发真正做成这件事的那个）。
- **暂停点**：工具发第一个请求之前、两个请求之间、等回答时，查找时，恢复等请求时限时，游走可以插入别的步骤（嵌套最多两层），包括让这个 agentd 死掉。`proceed` 和真正发出请求之间不插入（接口约定请求在 `proceed` 之后立刻发出）。
- **假的外部世界**记录每个请求何时发出、何时生效（最晚发出后 150 秒；工具的 Settle 是 3 分钟，所以 Settle 的承诺成立）。幂等工具的外部世界按键去重；对已经生效的键，再发的请求得到原来的结果，不会被拒绝。查找看的是此刻已经生效的请求。
- **时钟**：`ledger.Clock` 换成游走自己的时钟，只在游走拨钟或恢复等待时前进，每读一次走 1 纳秒，账本里的时间各不相同、有先后。
- **agentd 死掉**：每个 agentd 有自己的账本连接，死的时候关掉，之后它什么都写不进去，账本停在它死的那一刻；新的 agentd 打开同一个文件，名字（incarnation）不同。
- **每个种子的“口味”不同**（swarm testing）：各类步骤和各类尝试结果的权重、暂停的概率、启动时恢复的概率、重启时换策略和换连通性的概率，每个种子各抽一次（通常的权重、零、或三倍）。有的种子死得多，有的换策略多，有的结果不明多。M4 第三轮里“没批过的、可能已发出的写被挂出审批单”这类要好几件事凑在一起的路径，靠这个才走得到。
- **种子**：默认跑 1 到 200，加上 `regressionSeeds`（在 200 以外找到过问题的种子）。本机约 13 秒；`go test -race` 跑 60 个种子没有数据竞争。种子是对这份游走代码而言的：改了游走抽什么，同一个种子就是另一次游走，回归种子要重新找（见“改坏检查”最后一段）。种子 1–200 各跑两次，日志逐字相同（审批单的 UUID 在日志里换成 A1、A2…）。只有一处不是单线程：启动恢复同时处理几个副作用时，各在自己的 goroutine 里查找、等时限，日志的先后和时钟走了多少可能随调度变（恢复只查不发，每个副作用最后查到什么不变）。真遇到一个复现不了的种子，先看它是不是在这里。
- **运行**：`go test ./internal/gateway -run TestEffectProtocolStateMachine`；单跑一个种子并打印整次游走：`-statemachine.seed=N -v`；多跑：`-statemachine.seeds=N`。失败时打印违反的不变量、整次游走和此刻的账本。

## 不变量

每一步之后检查（发请求时的两条在请求发出的那一刻检查）：

1. 策略要求审批的写，没有一个请求是在审批单不是 APPROVED 且已用掉（转成 PENDING）、或者没有人批准过的情况下发出的；有审批单的写，发出的载荷就是批准的人看到的那份（sha256 相同）。
2. 策略要求审批的写，审批单到期（`expires_at`）之后不发新请求。“不是新请求”只有一种：幂等工具用同一个键重发一个可能已生效的写（在途）。在途是测试自己按发生的事算的（发出过请求，之后没有工具的回答、过了时限的查找或人的核对表明它没生效），不读 `maybe_sent`。另外不管策略，审批单只能在到期之前被用掉（M4 第五轮第 4 条）。
3. 账本说没发生的写（ABANDONED、DRY_RUN、DENIED、FAILED，或审批单 EXPIRED、REJECTED）确实没生效，按 agentd 知道的也不可能已生效；账本说 SUCCEEDED 的确实生效了。
4. 写可能已生效、又没有工具的回答、查找或人表明它没生效时，`maybe_sent` 是 1；可能已生效的写不会挂出审批单（AWAITING_APPROVAL）。
5. 每个写最多生效一次（幂等工具按键算）。
6. 报告里审批的那几行和账本一致：走真实代码（`RunRecords` 和 `github.comment_commit` 的渲染），每张审批单一行，状态是账本的；批准了的写按结局写（发出或在途写 approved；ABANDONED、DENIED、DRY_RUN 写 not sent；FAILED 写 failed；UNKNOWN 写 outcome unknown）；围栏里每张审批单有一行。批准、用掉之后过期的写，或者批准之后只做了 dry-run 的写，若发出过请求，要写 “A request of it went out at”（M4 第四轮第 3 条、第五轮第 3 条）。
7. 任务取消之后，它的写不再有请求发出（`proceed` 在放行请求的同一条 SQL 里查取消）。任务说明列了要驱动取消，但六条里没有一条直接管它，我加了这一条。

第 3、4、6 条比任务说明写的更宽：除了 ABANDONED 和过期，也查 DRY_RUN、DENIED、FAILED 和拒绝；除了外部世界的真相，也查 agentd 当时知道的（这样不必等请求真的落地，就能抓住记错的状态）。第 2 条只在当前策略要求审批时检查，见“我定的几处”。

## 找到并修掉的问题

都是在本分支早先版本的游走里找到的（那时的种子号对现在的游走已无意义），每个都补了单元测试：

1. **报告把只 dry-run 了的写说成“批准”**（低）。审批是在连得上 GitHub 的 agentd 上批的，转 PENDING 时换成了连不上的 agentd（重启时去掉了 GitHub 配置），写被记成 DRY_RUN，报告却只写 “approved”，读起来像发出去了。改法：`RunRecords` 把 DRY_RUN 也写成 “approved, not sent”，原因写 agentd 连不上工具的系统、只做了 dry-run。单测 `TestTheReportOfAnApprovedWriteThatOnlyDryRan`。
2. **可能已生效的写被记成没发生**（低：只有幂等类的写会带着 `maybe_sent` 被交还或重发，现在没有幂等类工具）。不管这次尝试是因为什么停下的，只要之前的尝试可能已生效，账本就不能说它没发生。原来有七处会这样记：工具在重发前拒绝（DENIED）、对方拒绝重发（FAILED）、交还后的写被连不上 GitHub 的 agentd 接手（DRY_RUN）、任务取消（调用时、工具什么都没做时、重发领取失败时、启动时 `AbandonUnsentEffects`），后者正是 M4 记录“留到后面”里写的那一项。改法：新的 `unsent` 统一处理，可能已生效就记 UNKNOWN 交给人；启动时新加 `HandOverUnsentEffects`，已取消任务里可能已生效、没人领取的写记 UNKNOWN，`AbandonUnsentEffects` 只放弃 `maybe_sent = 0` 的。单测 `TestAWriteThatMayHaveTakenEffectIsNeverRecordedAsNotSent`（七种情况）。
3. **审批在工具准备请求时到期，请求照发**（低）。`gate` 在领取之前查有效期，之后不再查；`open_draft_pr` 推分支之前要读几次 GitHub（提交、base 的头、比较、树），推分支和开 PR 之间也要读，这段时间审批到期，请求还是会在到期后发出。和 M4 第四轮第 2 条（恢复等时限时到期）同一类。改法：`proceed` 带上约束这次尝试的审批单（`bound`；在途的写没有），每个请求发出前过期了就返回 `ErrStopped`，下一次调用让审批作废，原因写明发出过的请求；恢复路径的 `resendNew` 也用它（取代了原来的 `lapsed`）。在途的写照旧用原来的键重发。`open_draft_pr` 在开 PR 前被拦下时，按原来的约定记 conflict 交给人（消息里加了“审批过期”）。单测 `TestAnApprovalThatRunsOutWhileTheToolPrepares`（第一个请求之前、两个请求之间、在途），用可控时钟，不靠 sleep。
4. **核对的“太早”保护对已结束的任务、已取消的任务和交还过的写不起作用**（低）。lookup 类工具（`open_draft_pr`、`comment_commit` 都是）的“未执行”要等最后一个请求发出 Settle 之后才收，因为请求可能还在对方那里处理。原来这条检查排在“任务已取消或已结束就记 ABANDONED”之后，取消或结束的任务马上收下；而且参考时间只看 `claimed_at`，交还过的写没有它，就不检查。请求随后落地，账本和报告却说没发生。改法：先查是否太早，参考时间没有 `claimed_at` 时用 `last_request_at`。**这改了 M3 的一个行为**，原来的 `TestReconcile` 里有一条断言“已结束的任务马上记 ABANDONED”，现在由新的 `TestAFindingThatAWriteNeverHappenedWaits` 取代。M3 记录写的是通用规则（“lookup 工具在最后一个请求发出后的 Settle 时间之内，不接受‘未执行’”），我认为原来的顺序是疏漏，需要你确认。`agentctl reconcile resolve --help` 和 README 补了一句：能查找的工具，等到没有请求还能生效时才收“未执行”，agentd 会说是什么时候。
5. **启动恢复的 goroutine 开始前不计数**（提示）。`RecoverEffects` 起的 goroutine 进了 `track` 才计数，`Drain` 可能在它开始前就返回，关机时它会在账本关掉之后才跑（报一条 “did not finish”）。改成 `executions.Go`，起之前就计数。测试要靠 `Drain` 确定启动恢复已经做完，是这么发现的。

## 为测试加的生产代码

- `ledger.Clock`：账本的时间（`ledger.Now`）和协议里比较的时间（审批到期、请求时限、核对是否太早）都从它来；默认 `time.Now`。测试在顺序执行的测试里换掉它（不和 `t.Parallel()` 的测试同时跑）。
- `Gateway.wait`：恢复等请求时限的那一段等待，默认用系统时钟；测试换成拨自己的钟。
- `RunRecords` 从 `cmd/agentd/main.go` 挪到 `internal/gateway/records.go`，测试才能走报告的真实代码。
- `RecoverEffects` 用 `executions.Go`（上面第 5 条）。

## 我定的几处

- **第 2 条只在当前策略要求审批时检查**。策略改成放行之后，已经转 PENDING 的批准写照发（`gate` 只在有规则时才跑），这是 M4 的设计：放行的策略本来就允许发。不管策略都成立的是“审批单只能在到期前被用掉”，单独检查。
- **人核对时的行为**：能查找的工具，人只看此刻外部有没有，靠 agentd 的“太早”保护；不能查找的工具（unsafe），人只在没有在途请求时判“未执行”。unsafe 工具没有 Settle，人过早判“未执行”造成重复是人的错（M3 记录也这么写），不算 agentd 的问题。
- **工具遵守接口约定**：拒绝、denied、`ErrNotSent` 表示这次尝试什么都没做；`proceed` 失败就停；请求在 `proceed` 之后立刻发出。
- **“在途”按任何可见请求算**（包括两个请求的写里的第一个），和 `maybe_sent` 的定义一致；第 3 条按“使写生效的那个请求”算有没有生效（推了分支、PR 没开，PR 这个写没生效）。

## 状态机没覆盖的

- 两个调用真正并发：同一个进程里同一个副作用由 singleflight 合并；游走里不同副作用只在暂停点交错。领取和结算的比较交换（CAS）冲突、`isSending`、`approved` 的事务冲突这些分支走不到，靠原有的单元测试（`TestOnlyTheClaimantSends`、`TestTheFirstDecisionWins` 等）。
- 载荷被篡改（T5 和单元测试覆盖）、审批单状态和副作用对不上的坏账本（`BadApproval`）、审批单上下文（Describe、任务的 ApprovalContext）、修改补丁的格式检查、门铃 outbox、Temporal 本身。
- 时钟是测试的，不是真实的计时器；`ExpireApprovals` 的循环本身没跑，跑的是它每一轮做的事（列出到期的、逐个 `expire`）。
