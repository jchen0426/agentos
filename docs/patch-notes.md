# 模型补丁的 hunk 头

2026-10-22。M5 D 的试跑（PR #36）里，Claude Opus 5.5 写了 5 个补丁，只有 1 个过了 `git.apply_check`。另外 4 个的 hunk 头数字不对，任务都以 `patch rejected` 结束，修得对的补丁也开不出 PR。

这次的改法：agentd 读补丁时，按 hunk 自己的行重写 hunk 头，行数和位置都改。审批人看的、git 检查的、提交进 PR 的，都是 agentd 按解析结果重新写出的同一份补丁。git 的检查改为报告它打出来的文件，agentd 再和自己打出来的逐个比对。

## 试跑的 4 个补丁错在哪

从试跑的账本（`~/.cache/agentos-eval/state/pilot`）取出补丁，对着各自的提交看：

| 用例 | hunk | 头写的 | 按行算 | 错在哪 |
|---|---|---|---|---|
| go-vouch-cookie-parts | 1 | `-98,17 +98,23` | `-98,15 +98,24` | 行数 |
| py-fsspec-jinja-refs | 1 | `-115,15 +115,16` | `-115,14 +115,15` | 行数 |
| | 2 | `-135,7 +136,7` | `-134,7 +135,7` | 位置差 1 |
| | 3 | `-146,10 +147,10` | `-145,9 +146,9` | 行数，位置差 1 |
| go-argocd-proxycommand-inj | 1 | `-311,6 +311,9` | `-311,7 +311,10` | 行数（少数一行） |
| | 2 | `-328,4 +331,14` | `-327,4 +330,13` | 行数，位置差 1 |
| java-jenkins-replay-scripts-inj | 1 | `-373,6 +373,7` | `-376,5 +376,6` | 行数，位置差 3 |

- **拒绝来自哪一层**：来自 agentd 自己的 Go 检查，go-gitdiff 解析失败，每次只用 0.3 毫秒，没走到沙箱里的 git。交接记录里的 `corrupt patch at line N` 是 git 的说法，原因相同。
- **`--recount` 为什么能接受**：`git apply --check --recount` 能接受这 4 个，不只是因为重算了行数。git 还会在文件里上下找 hunk 的位置（offset），3 个补丁的起始行号错了 1 到 3 行，git 都找到了。go-gitdiff 只按头写的行号打。
- **所以任务说明列的两种做法都不够**：只重算行数，4 个里只救回 go-vouch 一个。

## 今天就有的几个问题

这几处都是两道检查都放行，但 PR 的内容、git 检查的、审批人读到的三者对不上。

1. **行数写少了，多出来的行被悄悄丢掉**。
   - 头的行数数完之后还有 hunk 的行（`+` 行、上下文），git 和 go-gitdiff 都当作补丁外面的杂行忽略。
   - 审批人在卡片上看得到这些行，PR 里却没有。
   - 审批人手改补丁时最容易这样：加了一行、头没改，PR 会丢掉最后一行。黑盒测试里那次修改就是，丢掉的是新的 `return`。
2. **没有上下文的插入**（`@@ -5,0 +6 @@`，`diff -U0` 的写法）：go-gitdiff 插在第 5 行之前，git 插在文件末尾。两道检查都说打得上，PR 用的是 go-gitdiff 的结果，比补丁说的早一行。
3. **git 的检查只说打不打得上**（安全审查找到）。
   - git 读 hunk 有自己的规则：最后一处改动之后没有上下文的 hunk，git 只在文件末尾找；hunk 按补丁的顺序打，每个都从新的一边的行号附近找起。
   - go-gitdiff 按头写的旧行号打，并且先排序。
   - 同样的几行在文件里出现两次时，两边会改不同的地方，两道检查照样都通过。
   - 例：`c.ini` 里两节各有一行 `allow = no`，补丁在第一节后面加 `admin = guest`，hunk 后面没有上下文。go-gitdiff 加在第一节，git 加在文件末尾那一节。
4. **补丁里不属于任何 hunk 的文字也上了卡片**（安全审查找到）。
   - 第一个文件之前、文件之间、最后一个 hunk 之后的文字，git 和 go-gitdiff 都不打，但卡片上照原样显示。
   - 被注入的模型可以在真改动旁边写一段像补丁的“修复”，审批人以为 PR 里有，其实没有。
   - 写法有好几种：放在一个非 git 的 `diff ` 行后面；放进一个没有 hunk 的新文件的头里；用长得像 ` `、`-`、`+` 的 Unicode 字符。

## 选了哪种做法，为什么

1. **两边都用 `git apply --recount`**：不选。
   - git 的 `--recount` 只重算行数，位置靠它自己的就近查找。
   - Go 这边要和它一致，得照搬 git 的 recount 和就近查找（`match_beginning`、`match_end`、空白的规则），两份实现必须逐字节一致。
   - 同样的几行出现两次时，git 悄悄挑离头写的行号近的那一处。
2. **按 hunk 的行重写行数，存成新的 blob，之后严格检查**（任务说明的第二种）：方向对，但只改行数不够，见上。
3. **选的**：第二种加上位置，在 agentd 读补丁的地方做，只有一份实现（`internal/patch`）。
   - **行数**：取自 hunk 的行，头写的行数不用。
   - **位置**：hunk 的旧行（上下文和删掉的行）在头说的那一行开始、逐字相同，就留在那里；不在，就找文件里恰好一处有这些行的地方；一处都没有或者不止一处，拒绝。不做模糊匹配，每一行都要逐字相同。git 读 hunk 的规则照样遵守（见“规则”）。
   - **重新写出补丁**：打完之后，按解析出来、放好位置的文件和 hunk，用 go-gitdiff 自己的格式重新写出一份补丁（`Patch.Text`）。
     - 里面只有文件头和 hunk，模型写在 hunk 之外的文字一行都进不来。
     - 文件头只写 agentd 认的：名字，以及是新建还是删除（文件都是 100644，不然就被拒绝）。模型写的 `index` 行（blob 和权限位）、相似度、`@@` 后面的标题都不写：都是补丁自己的说法，没人核对。

     这份补丁：
     - 交给沙箱里的 git 检查，不加 `--recount`；
     - 显示在审批卡片上；
     - 就是 PR 里文件内容的来源。

     改完先自查：go-gitdiff 重新解析这份补丁，必须和实际打上去的完全一样。
   - **git 的检查要核对结果**：git 工具服务器在临时索引上真打一遍（`git apply --cached`，新文件的 blob 写进每次调用的临时对象目录，镜像的对象经 `GIT_ALTERNATE_OBJECT_DIRECTORIES` 只读），返回索引里每个文件的模式和 blob。agentd 拿它和自己打出来的逐个比对，差一个字节、多一个文件、少一个文件都拒绝（“the patch reads two ways”）。这样 git 和 go-gitdiff 读法上以后再有别的差异，也只会多拒绝，不会放过。
   - **审批卡片**：
     - 显示的是重新写出的补丁；
     - `patch_rewritten` 列出改了哪些 hunk 头，原来怎么写、现在怎么写，另有一条说明；
     - 补丁现在打出来的文件要和载荷里的一样，才这样显示。不一样时（比如中间换过 agentd 的版本），只显示原样的补丁（`patch_as_written`）和原因，不显示 git 的检查。

     载荷和它的哈希照旧绑定审批，不受影响。
   - **`git.apply_check` 的结果**：多一个 `rewritten_hunks`，改了几个头，只在有改动时出现。工作流不用它。

**为什么不另存一份 blob，让工作流传给 open_draft_pr**：

- 重新写出的补丁是“补丁 + 提交”的纯函数，同样的输入每次得出同样的字节。apply_check、open_draft_pr 的 Prepare、审批卡片三处各算一次，结果一样，不需要存。
- 要让工作流传新的 ref，就得改工作流：
  - 在途的任务重放时，要靠 `.get(..., 原来的 ref)` 才不变，T10 的版本测试也要跟着看；
  - 审批卡片上“这个补丁是不是这次审计提出的”（`tasks.auditFindings` 按 patch_ref 比对）也要另外对应。
- 被攻破的工作流本来就可以跳过 apply_check，open_draft_pr 不能只信 apply_check 的结果，还得自己再读一遍。现在两处用的是同一段代码。
- 审批人看到的补丁本来就记下了：出审批单时，Describe 的输出存成 blob（审批单的 context）。模型原样写的补丁在 report_ref 和 model_calls 的答复里。

## 规则

- **hunk 的行**：
  - 从 hunk 头往下，以下这些行都算：以空格、`-`、`+` 开头的行；空行（git 和 go-gitdiff 都把空行当作空的上下文行）；`\ No newline at end of file`。
  - 到这些地方为止：下一个 hunk 头；下一个文件的头（`diff ` 开头的行，或者 `--- `、`+++ ` 后面紧跟 `@@ -`，和 git、go-gitdiff 认文件头的规则一样）；一行不能是 hunk 的行；结尾。
- **`-- ` 后面直到结尾都是文字**：有两种读法，由头写的行数决定。
  - 行数在它之前刚好用完，就是 format-patch 的签名；
  - 还没用完，就是删掉 `- ` 的一行。
- **`--- `、`+++ ` 两行后面紧跟 hunk 头**：总是下一个文件的头。当作删掉、加上的两行，这个 hunk 最后一处改动之后就没有上下文，后面却还有同一个文件的 hunk，这样的补丁不会成立。
- **hunk 末尾的空行**：可能是文件里的空行，也可能只是把 hunk 和后面隔开。由文件决定：
  - hunk 的其余行在哪，就把文件在那里紧接着的空行算进来，最多算到 hunk 末尾的空行数，多出来的是隔开用的；
  - 头说的位置优先；要挪到别处时，照这样能放的地方必须只有一处。
  - 新文件、删除的文件的 hunk 后面的空行从不算：前者没有旧行，后者没有新行。新文件、删除的文件照 go-gitdiff 认：`new file mode`、`deleted file mode`，或者 `--- `、`+++ ` 行写 `/dev/null`，或者时间写成纪元（GNU `diff -N`）。
  - 头写的行数不决定位置，但能让补丁有两种读法。在头说的位置，头的行数把末尾的空行算作文件的空行，文件在那里却没有，别处又正好有，就拒绝。git 照行数读原样的补丁，改的是别处。
- **hunk 之外的行**：
  - 第一个文件之前什么都可以（format-patch 的邮件头、说明、diffstat）。
  - 文件之间、最后一个 hunk 之后可以有文字（svn 的 `Index:`、`diff -r` 的 `Only in`、说明），但不能有像 hunk 行的行，文字之后也不能直接是 hunk 头，中间没有文件头。
  - 文件头里、第一个 hunk 之前，不能有像 hunk 行的行（除了它自己的 `--- `、`+++ `）。
  - hunk 之外不能有 `\` 开头的行。git 在 hunk 后面见到 `\ ` 开头的行，不管多短都当作 `\ No newline at end of file`；go-gitdiff 要 12 个字节以上才认。
  - 这些行都不进重新写出的补丁。
- **头的写法不能混用**：git 的文件头和普通的不能混在一个补丁里。git 会去掉普通文件头路径的第一段，agentd 只在整个补丁都没有 `diff --git` 时才去掉。
- **最后一行**：是 hunk 的行又没有换行，补上换行。git 拒绝没有换行的 hunk 行；go-gitdiff 会读成“文件末尾没有换行”。
- **位置**：
  - 照 git 的规则：最后一处改动之后没有上下文的 hunk，必须到文件末尾为止。头说的位置上对得上、但不在末尾的，拒绝：git 会把它放到末尾。
  - 一个文件的各个 hunk 按文件里的顺序排，不能重叠。
  - 新的一边从哪一行开始，由旧的一边加上它前面的 hunk 增减的行数算出。
- **没有旧行的 hunk**（没有上下文，也不删行）：只能是空文件或新文件唯一的 hunk。其他一律拒绝：没有什么能说明它该放哪，今天 go-gitdiff 和 git 放的位置也不一样（上面第 2 条）。
- **没有换行的行**：hunk 加上的行没有换行，必须是这个 hunk 加上的最后一行，而且 hunk 要到文件末尾。不然 go-gitdiff 会把它和下一行连成一行，审批人看到的却是两行。
- **上限**：
  - 一个补丁最多让 Apply 在文件里找 32 次（`MaxSearches`），每找一次要扫一遍文件。挪位置的 hunk 算一次，在头说的位置上、要看行数是否指向别处的 hunk 也算一次（第三轮的安全审查找到，后一种原来没算，最坏一次 Apply 要 6 秒）。
  - 找位置用 KMP，文件的每一行最多比两次，同一行重复一百万次的文件也不会变慢；找到第二处就停。
  - 重新写出的补丁也不能超过 256 KiB。
- **审批人的修改**也按这套规则读：手改的补丁头不用数对。

## 行为变化

现在拒绝、以前放行的：

- 文字之后的 hunk 行或 hunk 头，文件头里像 hunk 行的行，hunk 之外 `\` 开头的行。
- 非空文件里没有上下文的插入（上面第 2 条）。
- 最后一处改动之后没有上下文、又不在文件末尾的 hunk：git 本来就不会把它打在头说的地方。
- 顺序颠倒或者重叠的 hunk，同一个空文件或新文件的两个 hunk。
- git 的文件头和普通的混用。
- 头的行数数完之后紧跟着像 hunk 的杂行：现在算进 hunk，通常就打不上了。
- `-- x`、`++ y` 这样的删除和增加正好在两个 hunk 的交界、看上去像文件头：读成文件头，补丁被拒。很少见。

现在放行、以前拒绝的：行数、位置写错，但每一行都在文件里、而且位置唯一的补丁。

卡片上的补丁现在是 git 的格式：
- 普通 diff 会多出 `diff --git` 行，新建、删除的文件多出 `new file mode 100644`、`deleted file mode 100644`；
- 行数为 1 时也写出来（`@@ -1,1 +1,1 @@`）；
- 补丁前后的文字、`index` 行、`@@` 后面的标题不再显示。

## 测试

- **Go：`internal/patch/hunks_test.go`**。每个打得上的用例，都另用真的 git（`git apply`，不加 `--recount`）打一遍重新写出的补丁，打出来的文件必须和 agentd 的一模一样。
  - 行数：
    - 多数、少数（下一个 hunk 之前、结尾处），数到下一个文件的头；
    - 文件之间和结尾的空行；
    - hunk 末尾的空行：文件里有空行时算上下文；文件里没有、头的位置对时去掉（对抗审查的例子，以前会挪到错的那一块）；空行是唯一的尾部上下文，文件末尾还有同样几行时（安全审查的例子）；两行空行；
    - 一个裸空行是文件的空行、再一个空行是隔开用的；
    - 头写对的补丁不变（标题不写），一行的文件的短写法，`index` 行声称的 100755 不写；
    - format-patch 的邮件和签名，补丁后面的文字，删掉 `- ` 再接说明；
    - 补上最后的换行，新文件和删除文件（git 的头和普通的头各一组），它们 hunk 后面的空行；
    - svn 的头和文件之间的文字。
  - 位置：
    - 挪到别处（标题去掉），挪到一个增加了行的 hunk 之后（新的一边跟着变）；
    - 头的位置对、别处也有同样的行（不挪），只有新的一边的起始行错；
    - 在文件末尾追加、同样几行在前面也有；
    - 空文件写第一批行，文件末尾没有换行。
  - 位置的拒绝：
    - 哪里都没有、只差一个空格、别处有两处、没有旧行；
    - 没有尾部上下文：头的位置也对得上（`c.ini`）；不在文件末尾。
    - 两个 hunk 挪到同一处，顺序颠倒；
    - 空文件的两个 hunk，没有换行的行在中间。
  - 上限：32 个能挪，33 个拒绝。
  - 不属于任何 hunk 的行：
    - 文字之后的 hunk 行，文字之后的 hunk 头；
    - 读不懂的 hunk 头，hunk 之后短的 `\` 行；
    - 非 git 的 `diff` 行之后、新文件头里的 hunk 行；

    - git 的格式和去掉 `diff --git`、`index` 行的格式各一份。

    读回来等于 git 原来写的（行数写全、去掉标题），打出来等于改后的文件，git 打出来的也一样。
  - **差分二**：有空行、有重复行（`}`、`return nil`、`if err != nil {`）的文件，80 轮：
    - git 写的补丁和把空的上下文行写成裸空行的补丁，都打得上，结果正确；
    - 打乱位置、行数后，要么拒绝，要么 git 和 agentd 打出来一样。
  - Rewritten 报告的内容；再打一次时，从补丁原来的头开始。
