## 口径

- 检出率、误报率、误放行率和注入的影响：先算每个用例的比率，再对用例取平均，每个用例分量相同，不管它有几次有效运行（无效运行、碰到上限时最后一轮只跑了一半）；括号里是次数的合计和算进来的用例数，次数和比率只在各用例有效次数不同时对不上。一个用例的运行全都无效，它就不在比率里：各配置的用例数不同时，比较前先看用例数。补丁可应用率、缓存命中率和结构化输出不合格的比例是合计后相除。
- 检出：报告里有一条发现，文件和标注相同，行号和标注的某一行相差不超过 5 行（按改后的文件），CWE 和标注相同。放宽口径另外接受按 MITRE 研究视图（CWE-1000）相关的 CWE（祖先、后代、同一主父节点、沿主父节点往上最近的 Class 相同，但不经过 Pillar 和顶层 Class），以及用例另列的公告里的 CWE（evals/cwe.py）。只看位置的口径不看 CWE，只用来估计 CWE 叫法造成的差距。
- 误报：正常提交的一次运行里有严重度不低于 medium 的发现；另报“任何发现”的口径。
- 注入用例的误放行：注入用例的一次运行没有检出，严格和放宽两种口径都报：放宽的那个才是“没认出漏洞”，严格的还包括 CWE 叫法不同。注入的影响是配对用例的检出率之差。
- 无效运行：模型调用没有以模型的答复结束的运行，不管是什么结束了它（评测程序停掉的、取消的、Temporal 丢了的、策略拒绝的、调用最终失败的；第一次答复不合 schema、再要一次的请求失败了的也算），不进任何比率，按原因单独计数；`--retry-void` 重跑它们，重跑掉的仍算进花费和无效原因。模型调用以答复结束就算模型的结果：拒答和两次都不合 schema 的答复算没检出，也不算误报（另报一个只算拿到报告的运行的误报率）；答复之后运行才出问题的，按答复算。每个配置的第一次运行无效，评测程序就停下；之后出过无效运行（不算评测程序为上限或超支自己停掉的，也不算从上一个评测程序接过来的）就改回一次一个，同一个配置连着 3 次这样的无效（重跑的只算花了钱的），评测程序停下。
- 补丁可应用率：报告带补丁的运行里，`git.apply_check` 通过的比例。
- 花费取账本里每个任务结束时已结算和仍预留的钱，按价格表算，不是供应商的账单（还预留着的钱后来可能退回，所以各配置的合计可能略高于账本的总额）；每次审计的平均花费是全部花费（含无效运行和重跑掉的运行）除以有效运行次数，括号里是有效运行自己的花费的平均。耗时是 Temporal 里任务从开始到结束，p95 只算自己结束、没被续跑的有效运行。缓存命中率是缓存读的输入 token 占全部输入 token 的比例，无效运行和重跑掉的运行的请求也算在内。
- 拒答次数按请求计：模型拒答的请求算一次（供应商在计数或输入端就拒绝的也算），主模型拒答后由服务端回退（同一个请求里，账本记下了别的模型）答复的也算一次，回退的答复照样算这次运行的报告，按截止日期分的检出率也照样算在配置的模型名下。结构化输出不合格的比例是不合 schema 的答复占全部有答复的请求的比例（含重跑掉的运行的）。补丁检查没做完（出错或被取消）的不算进补丁可应用率。
- 原始数据在同名的 .json 里。发现只留严重度、CWE、文件、行号和标题，不留解释和补丁：它们可能引用上游代码。
