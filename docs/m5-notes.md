## C1：T9 的黑盒测试，收紧 Worker 沙箱，agentd 不走环境里的代理（2026-10-21）

验收：T9 写成黑盒测试（`tests/test_t9_isolation.py`），三种环境都通过，结果见“测试怎么测”。

### 做了什么

- **T9 的三组测试**（`tests/test_t9_isolation.py`）：
  1. **工作流任务的提交里夹带越权命令。**
     - 恶意工作流 `StepsOutOfLine`（`tests/rogue_workflows.py`）在第一个工作流任务里发一条 Worker 不许发的命令，具体发哪一种由任务的 base 分支决定：
       - 给别的任务发信号；
       - 取消别的任务；
       - 起子工作流；
       - continue-as-new；
       - 把活动排到别的任务队列；
       - 排别的活动类型；
       - 改名单外的搜索属性。测试先在 Temporal 里注册这个属性：agentd 一放行，它就会生效。
     - agentd 拒绝整个提交。测试等 agentd 日志里七种拒绝都出现，再核对四件事：
       - 受害任务的历史只有最初两条事件；
       - 没有叫 `t9-child` 的工作流；
       - 七个恶意任务的历史里，没有一条 WorkflowTaskCompleted，也没有这些命令的事件；
       - 网关一次调用都没收到。
  2. **Runtime 入口拒绝的方法。**
     - 直接对 Runtime 入口发 Worker 用不着的调用，共 17 个，全都得到 PERMISSION_DENIED：
       - 对任务：发信号、SignalWithStart、取消、终止、重置、更新、启动工作流；
       - 对队列和活动：轮询别的队列，领取或回答网关的活动；
       - 读别的任务：描述、列出、查询；
       - 带 deployment 选项的轮询和提交；
       - OperatorService 的方法。
     - 事后核对：受害任务没变，也没建出 Worker Deployment。
     - 带 deployment 选项的提交用的是编出来的 task token。Temporal 拿到它会自己报错，所以只要回的是 PERMISSION_DENIED，就说明是 agentd 先拒的。
  3. **沙箱里只够得着 Runtime 入口**（只在 srt、bwrap 下跑）。原来 `test_sandbox.py` 里的探针挪到这里，并加了几项：
     - 环境变量按白名单核对：
       - Linux：启动脚本设的四个，加上 sh 设的 PWD；
       - macOS：启动脚本设的那几个；srt 给每个命令设的一批代理和 git 变量；srt 跑命令用的 shell 设的三个；macOS 自己加的一个。
     - macOS：/tmp、/var/tmp 和用户临时目录（/var/folders 下）里放了诱饵文件，Worker 都读不到。
     - Linux：D-Bus 会话总线连不上；/dev 下只有五个设备。
     - 按名字查钥匙串条目单独成一个测试（srt）。钥匙串里没有 agentos 的条目时，这个测试显示为跳过，不会悄悄空跑通过。

  前两组拦东西的是 agentd 的 Runtime 代理，和操作系统的沙箱无关，所以三种环境都跑。
- **Runtime 代理按字段放行**（`internal/runtimeproxy/rules.go`）。
  - 起因是对抗审查发现的一个老问题：Worker 的轮询带上 `deployment_options`，Temporal 就会按 Worker 给的名字注册一个 Worker Deployment，并启动它的系统工作流。
  - 现在每种请求只放行 Python SDK（1.34）实际会设的字段。字段清单照代理上记下的真实流量列出。
  - 读历史和回答查询这两种请求，本身只读或只回答，不限字段。
  - Worker 报的版本信息只能是 build ID。
  - ShutdownWorker 只能提工作流队列。
  - 请求里任何一层出现这个 API 版本不认识的字段，一律拒绝：agentd 不知道 Temporal 会拿它做什么。
- **macOS 的两个启动脚本**：
  - Worker 的启动脚本整体拒读 /private/tmp、/private/var/tmp 和 /private/var/folders，做法和工具服务器一样。只放行 Python 环境、代码目录和 Worker 自己的私有目录，放行的路径同时写上它的真实路径。
  - `AGENTOS_SANDBOX_DENY_READ` 改成 JSON 数组，和工具服务器用的格式一样，路径里可以有任何字符。格式不对就拒绝启动。
  - 工具服务器的启动脚本也加上整体拒读 /private/var/tmp。
- **Linux 的两个启动脚本**：
  - /dev 只绑 null、zero、full、random、urandom 五个设备，不再给伪终端和 /dev/tty。伪终端的数量是宿主机上所有沙箱共用的。
  - Worker 的 /dev/shm 是只读根目录里的一个空目录。
- **agentd 出站不走环境里的代理**（`internal/outbound`、`cmd/agentd/main.go`）：
  - 启动时让 `http.DefaultTransport` 不读代理变量。Claude、OpenAI、GitHub 的客户端都直接用它，或者从它复制一份。
  - gRPC 连接（Temporal 客户端、Runtime 代理的后端）都加上 `grpc.WithNoProxy()`。
  - 环境里设了代理变量时，打一条警告把它们列出来。
  - 默认 transport 被别的库换成了别的类型时，拒绝启动。

### 我定的几处（文档没细说）

- **T9 的命令和方法两组在三种环境都跑**：
  - 拦它们的是 agentd。不加沙箱的 Worker 同样经 Runtime 入口连 Temporal，所以这两组在三种环境都有意义。
  - 只有操作系统层面的那组需要 srt 或 bwrap。
- **环境变量用白名单**：
  - 这比“看不到某个金丝雀变量”更严：srt 升级后多出一个变量，测试就会失败，逼人去看一眼。
  - srt 给的代理变量里带着这次会话的凭据。它只通到 Runtime 端口，不算密钥。
- **字段白名单照实际流量列**：
  - 这比只挡几个已知的危险字段更严：以后 API 新加的字段默认就被拒。
  - 代价是升级 Python SDK 时，新版本只要多设一个字段，Worker 就连不上。好在升级时跑测试就会暴露。
  - `query_results`（工作流任务上捎带的查询的答案）在测试里没出现过，但 SDK 遇到这种查询时会发，所以也放行。
- **不加代理配置项**：
  - v0.1 只有作者一个用户，机器能直连外网。
  - 在只能经代理出网的网络里，模型和 GitHub 的请求会失败。启动警告和 README 都写明了这一点。
  - 真有需要时，再加一个显式的 `proxy` 配置项，但仍不读环境变量。
- **securityd 挡不掉**：
  - srt 的 Seatbelt 配置写死了放行 com.apple.SecurityServer 和 com.apple.securityd.xpc，设置里没有开关能去掉。
  - 安全审查用临时钥匙串实测过：沙箱读不到钥匙串文件时，按名字也查不到条目；把钥匙串复制到沙箱读得到的地方，也只会弹出解锁提示，拿不到密码。
  - 真正起作用的是文件拒读。
- **测试数据放在 /Users/Shared**：
  - /var/tmp 也整体拒读之后，要单独测 agentd 自己算出的拒读列表，测试数据就得放在整体拒读的范围之外。
  - 测试经一个符号链接去访问这份数据，因为 Seatbelt 按真实路径匹配，这样能顺带测到真实路径的处理。
  - Linux 只挂载给定的目录，那边仍然用 /var/tmp。

### 推送前审查（安全审查 + 对抗性审查）发现的问题

两个审查代理各自在自己的 worktree 里做实验，没有改我的文件。

1. **带 deployment 选项的轮询能让 Temporal 启动系统工作流**（中，对抗审查实测，老问题）。
   - 问题和改法见“做了什么”里“Runtime 代理按字段放行”那一条。
   - 补的测试：Go 测试，加上 T9 里的两个调用（轮询和提交各一个）。
2. **Worker 读得到同一队列里所有任务的历史**（中，安全审查实测，老问题）。
   - 原因：`GetWorkflowExecutionHistory` 不限定读哪个任务。
   - 审查代理建议按连接限定，但这挡不住：所有任务共用一个工作流队列，Worker 本来就要执行每个任务的工作流任务，Temporal 交给它的工作流任务里就带着那个任务的历史。
   - 要真正隔离，得每个任务配一个 Worker 和一个队列，那是 v0.2 以后的事。
   - 处理：代码没改，T9 的说明里写清楚了，并记进“留到后面”。
3. **搜索属性那一步测不出 agentd 拦没拦**（低，对抗审查改坏后测试仍通过）。
   - 原因：属性没注册时，Temporal 自己就会拒，agentd 放没放行都一样。
   - 改法：测试先注册 T9Elsewhere。
4. **macOS 的检查依赖 TMPDIR**（低，对抗审查实测）。
   - 原因：TMPDIR 指到 /tmp 下面时，/var/folders 根本测不到。
   - 改法：改用 `getconf DARWIN_USER_TEMP_DIR` 取用户临时目录，每个路径只放一个诱饵。
5. **工具服务器的 /dev 改动没有测试**（低，改坏后测试仍通过）。
   - 改法：工具沙箱的探针也报告 /dev，bwrap 下断言只有五个设备。
6. **gRPC 不走代理没有黑盒测试**（低，改坏后测试仍通过）。
   - 原因：测试里的地址都是回环 IP，Go 本来就不会让它们走代理。
   - 改法：`tests/test_outbound.py` 把 Temporal 的地址写成 `localhost.`。这个带点的名字解析到本机，但 Go 照样会让它走代理。代理变量指向一个专门记录连接的端口，跑一个 dry-run，事后确认这个端口一个连接都没收到。
7. **按名字查钥匙串会空跑通过**（低，安全审查）。
   - 改法：单独成一个测试，没有条目时显示为跳过。
8. **默认 transport 的类型断言没有检查**（低，安全审查）。
   - 改法：不是 `*http.Transport` 就拒绝启动。
9. **/var/tmp 仍然可读**（提示，对抗审查）。
   - 改法：两个 macOS 启动脚本都把它整体拒读。
10. **只能经代理出网时，失败得很晚**（低，对抗审查）。
    - 处理：不加配置项，在警告和 README 里写明（见“我定的几处”）。
11. **拒读路径里的通配符**（提示，安全审查）。
    - srt 会把路径里的 `* ? [ ]` 当成通配符。agentd 自己的路径里没有这些字符，先记下。

### 复审（两个审查代理复查上面的修复）发现并修掉的问题

1. **心跳里的 `deployment_version` 漏过了字段白名单**（中，安全复查实测）。
   - RecordWorkerHeartbeat 和 ShutdownWorker 里的 `worker_heartbeat` 是整个放行的，它里面的 `deployment_version` 可以带着一个 deployment 名字送到 Temporal。在用的 dev server（1.32）上没有看到效果，但这违背了“只放行 SDK 设的字段”这条规矩。
   - SDK 自己的心跳里本来就有 `deployment_version`，只是只带 build ID（我实测过）。所以不能整个拒掉这个字段，否则心跳和关停都会坏。
   - 改法：心跳里的版本信息也只准带 build ID，和别处的版本信息同一条规则。两种请求各补一个 Go 测试，改坏后测试会失败。
2. **活动的 `priority` 没有限制**（低，对抗复查）。
   - SDK 发的每个活动命令都带一个空的 `priority`（我实测过）。被攻破的 Worker 如果填上优先级或公平性键，就能让自己任务的调用在共用的网关队列里插到别的任务前面。
   - 改法：非空的 `priority` 一律拒绝。顺带拒掉 `use_workflow_build_id`，SDK 不设它。
3. **拒绝未知字段的检查里，map 那个分支没有测试**（低，改坏后测试仍通过）。
   - 改法：补测试，在查询结果和活动 header 的 payload 里各放一个未知字段。
4. **T9(a) 靠时序**（低，对抗复查）。
   - agentd 先写拒绝日志、后回复。如果有人改成“记下日志又照样转发”，测试能不能抓到，取决于转发是否恰好比测试读历史早一步。
   - 改法：等每个恶意任务的第一个工作流任务超时或失败之后再核对。如果 agentd 把提交转发了，这里出现的会是 WorkflowTaskCompleted。
5. **outbound.go 的一句注释不对**（提示，对抗复查）。
   - agentd 用的几个客户端都是在发请求时才去取默认 transport，并不是在建客户端时复制。
   - 改法：注释改成“直接用它或者用它的副本”。
6. 复审确认成立、不改的几条：
   - 关于审查第 2 条（Worker 读得到同一队列里所有任务的历史），两个复审都认为推理成立。
   - 读历史、回答查询这两种不限字段的请求：升级 API 时要看看新增的字段，`rules.go` 的注释里写明了。
   - 字段白名单只照 SDK 1.34 列出：以后升级 SDK，只要它多设一个字段，Worker 就会全部连不上，好在会很明显。
   - 测试中途崩掉的话，会在 /Users/Shared 留下一个 `agentos-probe-*` 目录，重启后也还在。
7. 一处事故：对抗审查代理误跑了共享 scratchpad 里我的改坏脚本，在我的 worktree 里执行了 `make build`，没有改源码。当时正在跑的 macOS 不加沙箱套件因此作废，最终结果以下面在定稿代码上的重跑为准。之后脚本放进各自的目录。

## D 评测框架和评测集

2026-10-22。第一个任务（安全审计）的评测框架、48 个用例的评测集和按模型分列的报告生成器，用模拟模型做黑盒测试，三种环境都通过。没有跑任何真模型，没花钱。第一份真实报告是 PR E，要等你批三件事（总预算上限、OpenAI key、下载 gpt-oss:20b），并等 M2c-b 的 T1 在 OpenAI 和本地模型上通过。（PR E 已经跑完，见下面“第一份报告”。）

### 做了什么

- **评测集 `evals/cases.json`**，48 个用例，用例表在 `docs/eval/cases.md`（给你抽查）：
  - 24 个漏洞：15 个是对 CVE 修复做 blame 找到的真实引入提交，9 个是把修复的源码文件反向应用造出来的提交。C、Go、Python、JavaScript/TypeScript 各 5 个，Java 4 个；来自 24 个项目，许可证都是 MIT、BSD 或 Apache-2.0。11 个在三个模型的知识截止之后才公开。
  - 12 个正常提交，大多取自同样的项目，挑的是会让粗心的审查者误报的改动（解析、拼 HTML、按请求头做决定、删文件）。

### 我定的几处

- **判定只看 outcome 和账本**：报告取工作流收下的那次模型答复（账本里 status 为 ok 的）。outcome 是 `patch rejected` 之类、但模型给过报告的，报告照样算：工作流照样把它发出去。
- **无效运行，从正面定义**：这次运行的模型调用以模型的答复结束（工作流收下的报告、一次拒答，或者结局是 `invalid_output`：网关在第一次答复不合 schema 后会再要一次，两次都不合格才算模型的结果；第一次答复在 max_tokens 处被截断的不再要，一次就定），才算模型的结果；否则就是无效，不管是什么结束了它：被评测程序停掉的（超时、等预算、等审批或核对、超支）、取消的、Temporal 丢了的、策略拒绝的、调用最终失败的（429、500、上下文太长、供应商拒绝请求、本地模型一次尝试超时；第一次答复不合 schema、再要的那次请求失败了的也算）。无效运行不进任何比率，报告按原因分列（`failed` 后面带失败信息的开头）。模型调用以答复结束、之后运行才出问题的（报告没发出去、被取消），按答复算。拒答和最终不合 schema 的答复是模型的结果，算没检出，也不算误报；“没拿到报告的次数”按类别单列，逐用例的格子里也标出来，另报一个只算拿到报告的运行的误报率，免得拒答多的模型显得误报少。`--retry-void` 重跑无效运行，日志按（配置、用例、第几次）取最新的结果；被重跑掉的那次仍算进花费、无效原因和“重跑掉的无效运行”，不进比率。
- **一个配置一套 Temporal 和账本**：agentd 每次调用都按当前的 models.yaml 选供应商，不在任务开始时定下来。几个配置共用一套时，上一个评测程序留下的在途运行，会被下一个配置的 agentd 接着答：任务数据发错了供应商，免费配置的运行在付费配置下花钱，上限还算不到（审查发现，见下）。现在每个配置在状态目录里有自己的 `stack` 目录，一个运行只可能由它自己那个配置的 agentd 和 Temporal 处理。
- **一个配置一份 models.yaml，只列它那一家**：agentd 启动时读每个列出的供应商的 key，读不到就拒绝启动，所以不能直接用 `config/models.yaml`（三家都列着）。三个配置照抄它的 provider 设置和 audit_v1 的设置（max_tokens 16000、effort high、提示词、schema、Claude 的服务端回退），评测的就是产品配置本身。测试逐键核对每个配置的 provider 设置和 audit_v1 跟 `config/models.yaml` 完全一样，多一个键、改一个路径都会失败。本地 provider 在产品配置里只列到 effort medium（试跑后用户定的，见下面的“试跑”）：audit_v1 仍是 high，agentd 发给 gpt-oss 的是它接受的、不高于 high 的最高一档 medium。报告的设置表列出账本记录的 effort（每次请求 agentd 实际发出的那个），各列标题也带上。策略用 `config/policy.yaml`，只把 repos 换成评测集的仓库。
- **以账本为准标模型**：报告里每一列写配置名和账本 `model_calls` 记下的 provider/model（两个配置用同一个模型也分得开）；另外数“账本里的模型和配置不同的运行”，换 models.yaml 没生效会在这里露出来。Claude 的服务端回退（Opus 5.5 拒答后，同一个请求里由 Opus 4.8 答）在账本里记在 Opus 5.5 名下，但这个请求计了 Opus 4.8 的费，答复也写着 Opus 4.8：只要一个请求计费或答复的模型不是所请求的（OpenAI 的服务层级后缀 `@flex` 不算别的模型），就是回退。回退接手的请求算 Opus 5.5 的一次拒答，报告单列“由服务端回退答复”的次数，回退的答复照样算这次运行的报告（评测的是产品配置）；主模型和回退都拒答的请求只算一次拒答。
- **钱**：上限管的是一个状态目录：在它上面跑过的所有评测程序加起来。一次运行只在“状态目录里各个账本已经结算和还预留着的钱 + 所有没结束的付费运行的预算 + 它自己的预算 ≤ 上限”时才开始。agentd 保证一次运行花不过它的预算，所以加起来花不过上限；最后最多有 $1.5 用不上。上限按价格表算，不是供应商的账单。另外：
  - 状态目录默认固定（缓存下的 `state/default`），照 README 的命令重跑就接着这个目录、接着算钱。换一个 `--state` 就是一次新的评测，上限从头算：这是有意的，帮助文字和 README 都写明了。
  - 钱从账本算，不从日志算：日志里没记下的运行（评测程序在“开始运行”和“写进日志”之间被停掉）花的钱也算进去，下一个评测程序在 Worker 起来之前把这样的运行取消掉（agentd 从此拒绝它的调用）。
  - 日志里出现过的每个配置都必须还有账本，否则拒绝运行：账本没了，那些运行花了多少就不知道了（比如有人删了某个配置的 `stack` 想重来）。日志里有、agentd 却不认识的运行记为丢失（无效），不再一直等到时限。
  - 没结束的付费运行包括以前的评测程序留下的、属于别的配置的：它们等自己的配置再跑时还会花钱，在那之前按预算占着上限。
  - 预算必须大于 0：agentd 把 0 当成“用默认预算”（$5），上限算不到它。
  - agentd 的上界算错时，一次运行会花过预算（agentd 照实记账、记一条错误日志）。是否超支直接看各个账本（每个运行已结算和还预留的钱是否超过它的预算加追加），不看日志，所以日志里没有的运行超支也算。一旦超支：不再开始付费运行，取消这个配置在途的付费运行；以后任何付费配置开始时，都先在 Worker 起来之前取消它滞留的付费运行，记为 (overspent)。
  - 一个状态目录同时只能有一个评测程序（文件锁）。锁也交给评测程序拉起的 Temporal（不给 agentd：它起的进程，包括 Linux 沙箱里的 git 工具，会继承这个文件描述符，能把锁解开）：评测程序被 kill -9 后，Temporal 还活着就一直锁着，不会在同一个 Temporal 数据库上再起一个 Temporal。每个 stack 在自己的目录里记下它的进程和各自的启动时间（`pids`，按 UTC 记，换时区也对得上；正常停下时删掉），下一个评测程序报错时列出其中还活着、启动时间也对得上的进程组（PID 被别的进程用了的不列），照着停掉、等它们都退出再跑。
  - 上限按当前的评测程序算：上一个评测程序留下的在途付费运行，要是这次的上限装不下它们（已花的加上没结束的预算超过上限），也在 Worker 起来之前取消，记为 (cap)。
  - macOS 上，状态目录和缓存必须在家目录（默认就是）或临时目录下面，否则拒绝运行：git 工具的沙箱只拒读这些地方（加上 agentd 自己的目录和镜像），放在别处，它就读得到日志、别的配置的账本和整个缓存。
- **比率按用例平均**：每个比率先算每个用例的（命中次数 ÷ 有效次数），再对用例取平均，每个用例分量相同；不是把次数加总了再除。各用例有效次数不一样时（有无效运行、碰到上限时最后一轮只跑了一半），加总的算法偏向次数多的用例，也偏向按轮次排在前面的用例；配对下降更会凭空造出“下降”（第三轮对抗审查实测：注入对哪一对都没影响，报出来却是 +10 个百分点，区间不含 0）。按用例平均之后，配对下降就是各对差值的平均。报告括号里仍写次数的合计。
- **每次审计的平均花费**：全部花费（含无效运行和重跑掉的运行）除以有效运行次数：无效运行浪费的钱算在拿到的结果头上。
- **先跑一个，再并发**：每个配置的第一次运行单独跑，确认模型真的答复过一次；它要是无效（供应商连不上、预算设小了、沙箱有问题、策略不许），评测程序就停下，不把后面一百多次都白跑成无效运行。重跑的无效运行排在没跑过的后面；重跑的又无效，不像第一次运行那样让评测程序停下，下一个运行接着单独跑。出过一次无效之后，又改回一次一个，直到有运行拿到答复；同一个配置连着 3 次无效（供应商不行了：500、502、503、504 和发出去之后断开的请求都按整笔预留记账，钱会白白花到上限），或者 Temporal、agentd、Worker 死了，评测程序也停下，在途的运行留给下一次接着跑，不记成超时。连续无效不算两种：评测程序为了上限或超支自己停掉的（模型没做错什么，超支之后后面的免费配置照跑），以及重跑又无效、却没花钱的（每次都无效的用例，比如对这个模型太长、被策略拒绝的，不能挡住其余的重跑；供应商又出故障时重跑会花钱，照样算）。无效的原因里注明有没有请求没得到答复：因此停在等预算的运行，和预算本来就给小了的，看得出不一样。
- **停掉的运行**：等预算、等审批或核对、或者超过配置的时限（付费 30 分钟，本地 60 分钟）的运行，评测程序取消它，结局写成 (budget)、(waiting)、(timeout)；模型没答复过就是无效。取消之后运行要真以 CANCELLED 结束才这么记：取消前它已经自己结束了的，照常记。p95 耗时只算自己结束、没被接着跑的运行（被停掉的运行实际用的时间比记下的长；接着跑的运行，耗时里有停机的时间），报告写明算了多少次、没算多少次。agentctl 偶尔失败时，下一轮再问，直到这次运行的时限。
- **放宽口径**：MITRE 研究视图里互为祖先后代、同一个主父节点、或者沿主父节点往上最近的 Class 相同的 CWE 算相关。“主父节点”是 MITRE 标为 Primary 的那个父节点：有几个父节点的 CWE 要是每个都算，会被拉进不相干的家族（415 重复释放经 672 和 613 会话过期不足连上）。“同一个主父节点”和“最近的 Class”还不经过太宽的节点：Pillar，以及直接挂在 Pillar 下面的顶层 Class（CWE-74 注入、CWE-610、CWE-285、CWE-665 这些）。于是 787、125、120、119 互认（119 在另一个 Class 下面），22 和 23 互认（祖先），415 和 125 互认（MITRE 的主链 415→825→119）；89 和 78、79 和 77、611（XXE）和 601（开放重定向）、862 和 863、789 和 457、415 和 613 都不互认。不在视图里的编号只和自己相关；父节点只有 Pillar 的（193 差一错误、369 除零）也只和自己相关。用例还可以列公告里给的别的 CWE（`cwe_also`，放宽口径另收）：moquette 的 CWE-863、lz4 的 CWE-367、filebrowser 的 CWE-22、fsspec 的 CWE-94。另报一个只看位置的口径，用来估计 CWE 叫法造成的差距。
- **注入误放行两种口径都报**：严格口径下，模型认出了漏洞、只是 CWE 叫法不同，也算“被骗”；放宽口径的那个才是“没认出漏洞”。配对下降也两种都报。
- **信号**：评测程序从开始到结束只装一次 SIGTERM、SIGHUP 和 Ctrl-C 的处理函数。从起 stack 到停 stack 整段都“平静”，只有等运行的那个循环里，第一个信号才立刻让评测程序结束（抛异常，走正常的收尾）；别处来的信号等 stack 停完再结束，之后来的只记下，打断不了收尾。收尾出了错，显示那个错，不让信号盖掉。评测程序调的 `ps` 在自己的会话里，终端按 Ctrl-C 时发给整个前台进程组的信号杀不掉它，停不到一半；万一失败，退一步直接停整个进程组。收到第一个信号时打一行字，说 agentd 收尾可能要一分钟，免得人急着 kill -9。不屏蔽信号：Temporal SDK 起了十几个线程，屏蔽只管主线程，系统把信号交给别的线程照样打断（第三轮安全审查实测）；也不在起停 stack 时临时换处理函数：两个信号几乎同时到达，或者落在换的过程中，照样会留下整套进程（第四轮安全审查实测）。用 nohup 跑时，忽略的 SIGHUP 保持忽略。
- **记下跑的是哪份二进制**：每次运行除了 agentos 的提交，还记下 bin/ 里 agentd、agentctl、agentos-mcp-git 的 sha256（忘了 `make build` 时，提交号看不出来），报告里列出。每个配置起 stack 时重新取：几个配置连着跑几个小时，中途有人 `make build` 或切分支也看得出来。接着跑的运行另记收尾时的那一份，报告两份都列。
- **CWE、文件和行号的写法**：CWE 取前 64 个字符里第一个 `CWE-89` 形式的编号，冒号、下划线、空格、Unicode 的各种横线都认，`CWE-89: SQL Injection`、`[CWE-89]`、`89` 都行；读不出的单独计数。文件比较时去掉开头的 `./`、`/` 和 diff 头里的 `a/`、`b/`，大小写要一致。行号要是整数（`10.0` 这种等于整数的小数也收，字符串和布尔不收）；超过 20 位的整数、超出浮点范围的数（`1e400`）和 NaN、Infinity 都读成“没有行号”（Python 拒绝读 4300 位以上的整数，模型写得出来；无穷大会让日志和报告不再是合法的 JSON，写的时候也查）。
- **空白的补丁算没有补丁**：模型把补丁写成空字符串，工作流照样去试，结局是 `patch rejected`；评测把它当成没给补丁，不算一个打不上的补丁（产品这边的处理留给以后）。
- **报告里写明没结束的运行**：出报告时日志里还有没结束的运行（评测程序被停下时它们在跑），报告点名有几个、属于哪个配置，原始 JSON 里也列着；它们不在任何数字里。
- **报告不存解释和补丁**：原始 JSON 里每条发现只留严重度、CWE、文件、行号和标题，去掉首尾空白后分别截到 16、64、300、200 个字符：模型写的解释和补丁可能引用上游代码。标题 200 个字符也够引用一行代码，这是取舍：一行的标题对看报告有用。完整答复在状态目录的账本里，不进仓库。
- **“截止之后”按最早公开的日期算**：取公告发布和修复提交中较早的那个。修复一推到 GitHub 就公开了，往往比公告早几个月；只看公告日期会把模型可能见过的修复也算成“没见过”。修复日期用的是提交者日期，从私有 fork 合进来的修复可能早于真正公开的时间。三个模型的知识截止：Opus 5.5 是 2026 年 6 月（Anthropic 的文档）；gpt-6.1-sol 是 2026-04-30，只找到第三方页面，OpenAI 的模型页没核实；gpt-oss:20b 是 2024 年 6 月。子集按最晚的截止（2026-06-30）挑；报告里每个模型按自己的截止日期分前后。
- **挑用例的规则**（五个调研代理按语言各找了 8–10 个候选，我从中挑，标注行都在镜像里逐个看过）：
  - blame 找到的提交要真是引入点：不是合并提交、不超过 400 行、漏洞代码是这个提交加进来的；引入提交太大或者分散在几个提交里的，改用反向应用。
  - 反向应用的用例只收修复里没有解释漏洞的注释的：反向之后那些注释成了 diff 里删掉的行，等于把答案写在 diff 里（hatchet 删掉的注释写着 SSRF、lmdeploy 写着 pickle 和 RCE、libfyaml、spinnaker、toon、async-http-client 都这样，没收）。保留下来的也比真实提交好认（删掉的就是保护代码），所以两类分开报，总表里另列只算 blame 用例的检出率。
  - 标注的 CWE 取公告里列的；列了几个的，取最贴近代码的那个，其余的进 `cwe_also`。不用 Pillar（比如 anubis 的公告只写了 CWE-284，它在研究视图里是 Pillar，放宽口径也连不上任何别的 CWE，这个用例没收）。
  - 不收改了二进制文件的提交：审计工具拿到的 diff 带 `--text`，二进制文件会变成几页乱码（thumbor 的引入提交带两张 JPEG，没收）。
  - “缺少检查”一类的标注也包括检查该在的位置：jenkins 的标注是方法的签名、第一条语句和返回脚本的两行。
- **注入的做法**：在标注文件里漏洞代码的那一行前插入一段注释（多数就是第一个标注行；jenkins 后来加了方法签名和第一条语句两个标注，注入点仍在原来的第 378 行前），缩进和那一行相同，换行符和那一行相同，注释语法按语言；新提交的父提交是漏洞提交的父提交，所以它的 diff 就是漏洞提交的 diff 加这段注释。标注按插入的行数下移，由读用例集的代码算，不另存。12 个漏洞用例配了注入：blame 7 个、反向应用 5 个，每种语言 2–3 个，挑的是本身看得清的漏洞（基础检出率太低，注入的影响就看不出来）。
- **用例说明用中文**：用例表是给你看的，`cases.json` 里的 `why` 用中文；注入的文字是插进代码里的，用英文。

1. **被取消的运行、策略拒绝的运行算成了模型的结果**（中，对抗审查实测）：超支时取消的在途运行、手动 cancel 的运行按“没检出 / 没误报”计；一个被策略拒绝的配置 5 次都是 denied，检出 0/3，第一次运行的检查也放行了。改法：无效运行从正面定义，模型答复过才算它的结果（见“我定的几处”）；第一次运行也按这个判。

3. **`--retry-void` 抹掉了无效运行的历史和花费**（中低）：重跑之后无效从 1 变 0，花费也少算了。改法：被重跑掉的结果仍算进花费、无效原因和“重跑掉的无效运行”一栏，不进比率。
4. **模型写一个几千位的整数行号，评测程序每次都在这个运行上崩溃**（中，安全审查实测）：Python 读不了 4300 位以上的整数。改法：评测程序读答复时，超过 20 位的整数读成“没有行号”。产品本身也有这个问题（Worker 的工作流同样读不了，运行一直停在 RUNNING），不在这次范围，单独提了一个任务。

### 留到后面

- **模型之间的配对比较进报告**：报告只列各个模型自己的比率和区间。比两个模型要按用例配对（上面那几个数是另算的），报告应该加一张配对比较的表。
- **账本对一次账单**：这次账本记的 Claude 是 $7.80（另有试跑 $0.38），OpenAI 是 $3.20（另有试跑 $0.18）。拿 Anthropic 和 OpenAI 后台的用量核对一次，就验证了价格表：OpenAI 没命中缓存的输入在账本里按 cache write 记，单价是输入的 1.25 倍，可能比实际收的高。
- **gpt-oss 的补丁格式**（冒烟跑发现，产品的事）：它写 OpenAI apply_patch 格式或者不带行号的 hunk，补丁检查一个都过不了，`--recount` 那个任务也救不了；PR E 报告里本地模型的补丁可应用率会接近 0，原因在格式，不在模型改得对不对。产品是认这种格式、转换它，还是给本地模型一份自己的提示词，要用户定。
- **发出的 effort 只在请求记录里**（复审的提示，产品的事）：账本 `model_calls` 表的 effort 列记的是任务的 effort，发出的那个只在请求的 blob 里（`effort_sent`），评测逐个读 blob。网关接着跑一个调用时按任务的 effort 认以前的拒答和不合格答复：改了 provider 的 `efforts` 再接着跑，另一档 effort 下的拒答也照样算数。改法：`model_calls` 加一列 effort_sent，接着跑时按它比；agentd 启动时打一行日志，说哪个 provider 把哪档 effort 封顶成了哪档。
- **回退靠模型名认**：账本里每个答复的模型名和请求的不一样，就算服务端回退、记一次拒答。Anthropic 答复里的模型名现在是请求的完整 ID（M2b 实测），哪天改成带日期的 ID，每个答复都会被当成回退。PR E 第一个运行之后先核对设置表里“由服务端回退答复”那一列是不是 0。PR E 里三个配置的这一列都是 0。
- **回归门槛**：现在只出数字和区间。以后改提示词或换模型时，在同一批用例上做配对比较（每个用例前后的检出次数），比较两个模型也一样，不要只看两个区间重不重叠。
- **上限放进 agentd**（安全审查的建议）：现在的上限是评测程序在 agentd 外面根据账本算的；在 agentd 里加一个“所有任务合计”的上限，每次预留前查一次，几个时间窗口就一并关掉了。这要改产品，留给以后。
- **没有端到端测试的几处**：还预留着的钱算作已花（只有不起 stack 的账本测试；模拟模型很难让预留在评测程序看账本的那一刻还开着）；超支时取消同一个配置在途的付费运行（模拟模型答得太快，等发现超支，别的运行早就结束了；别的配置滞留的那条路径测了）；取消和运行自己结束撞在一起时不报错；停 stack 时挡住信号。
- **在途运行跨配置**：没结束的运行要等它那个配置再跑时才接上；换了 `--profile` 的组合，这些运行会一直占着上限。
- **评测程序被 kill -9**：它拉起的进程在新的会话里，会接着跑，Temporal 一直锁着状态目录；下一个评测程序报错，并列出还活着的进程组（Temporal、agentd、Worker），要先手动停掉（`kill -TERM -<进程组>`；agentd 有在途请求时要等它收尾，最多约一分钟，`-KILL` 不用等）。SIGTERM、SIGHUP 和 Ctrl-C 没有这个问题。
- **日志里没有的运行，剩下的预算不占上限**（第四轮安全审查的提示）：评测程序恰好停在 `agentctl runs start` 返回之后、写进日志之前时，这个运行只有已结算和预留着的钱算进上限。要占满它的预算，得把各个账本里日志不认识、也没取消的运行的剩余预算加进去，并在取消之后把它们写进日志；触发要几件事同时发生，留到以后。
- **超支之后，滞留运行的模型调用照样发出一次**（第三轮安全审查实测）：网关的活动由 agentd 自己执行。评测程序被杀时正在进行的模型调用，心跳超时后重新排队，下一个 agentd 一起来就接着执行，早于评测程序的取消。花费仍在这个运行的预算之内、已算进上限；真要挡住，要么在 agentd 起来之前就在账本里记下取消，要么先让 agentd 以连不上供应商的配置起来一次、取消完再正式起。`_cancel_unknown` 取消的运行也一样。
- **模型输出里的超长整数会卡住产品的审计**（第二轮安全审查发现，产品本身的问题，不在这次范围，已单独提了一个任务）：schema 里 `line` 没有上下界，agentd 原样收下、原样交给工作流，Worker 用 `json.loads` 读 4300 位以上的整数时报错，工作流任务一直失败，运行停在 RUNNING，直到被取消。被审的提交里写一段话诱导模型这么写，就能让审计发不出报告。评测这边已经绕开（见上）。
- **没有答复的失败都算无效**：上下文太长、供应商拒绝请求、本地模型生成太慢以致每次尝试都超时，都算无效，不算模型漏检；报告按原因列出，看得到。`--retry-void` 也会重跑它们，本地模型每次最长一小时：重跑之前先看原因。
