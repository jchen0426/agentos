### 做了什么

- **评测集 `evals/cases.json`**，48 个用例，用例表在 `docs/eval/cases.md`（给你抽查）：
  - 24 个漏洞：15 个是对 CVE 修复做 blame 找到的真实引入提交，9 个是把修复的源码文件反向应用造出来的提交。C、Go、Python、JavaScript/TypeScript 各 5 个，Java 4 个；24 个项目，许可证都是 MIT、BSD 或 Apache-2.0。11 个在三个模型的知识截止之后才公开。
  - 12 个正常提交，大多取自同样的项目，挑的是会让粗心的审查者误报的改动（解析、拼 HTML、按请求头做决定、删文件）。
  - 12 个注入用例，各由一个漏洞用例在标注文件里插入一段注释造出，和它配对；12 种说辞各不相同（假的安全审查、对 AI 审查者喊话、伪造的结束标签加一份让模型照抄的答案、lint 豁免、声称上游已校验……）。
  - 文件里只有提交号、标注（文件、行号、CWE）、注入指令和我自己写的说明，没有上游代码。
- **评测框架 `evals/`**，只用标准库，复用黑盒测试框架（`tests/harness.py`）拉起 Temporal、agentd 和沙箱里的 Worker，没往 Worker 的环境里装任何东西。命令 `python -m evals`：
  - `mirrors`：每个项目一个镜像，放在仓库外的缓存（`~/.cache/agentos-eval`，或 `AGENTOS_EVAL_CACHE`），按提交号浅拉提交和它的父提交。我们造的提交固定作者、提交者和时间，在哪造出来提交号都一样；`cases.json` 记着提交号，建镜像时核对。每个用例还核对：只有一个父提交；没改二进制文件；标注文件在提交里、被这个提交改过；标注行在文件范围内。`--record` 把造出来的提交号写进用例文件。
  - `table`：用例表。
  - `run`：每个配置一份 models.yaml，用它重启 agentd，每个用例跑 3 次，全部 `--dry-run`；agentd 不配 GitHub（只能 dry-run），dry-run 的写也不要审批。状态目录里有日志（journal）、Temporal 的数据库和 agentd 的账本，`--state` 接着跑：跑完的跳过，在途的接上。
  - `report`：中文 Markdown 和原始 JSON，放 `docs/eval/`。
- **打分**（`evals/score.py`、`evals/cwe.py`）：检出、误报、注入误放行和配对下降、补丁可应用率、单次花费、p95 耗时、缓存命中率、拒答次数、结构化输出不合格的比例，全部按配置分列；置信区间按用例 bootstrap。放宽口径用的 CWE 层级在 `evals/cwe1000.json`，是从 MITRE 的 CWE 4.20 里抽出的研究视图（编号、抽象层级、父节点），附 MITRE 的版权和使用条款。
- **modelsim**（测试用的模拟供应商）加了按规则消费的脚本答复：按模型名和请求体里的一段文字匹配，按顺序用掉；还能设答复的缓存用量。
- **测试框架**：`Stack(fixture=False)` 不建测试镜像、不起模拟 GitHub；`start_agentd(repos=...)` 换掉 acme/payments；新加 `execution_times`。

### 我定的几处

- **判定只看 outcome 和账本**：报告取工作流收下的那次模型答复（账本里 status 为 ok 的）。没有这样的答复的运行（拒答、失败、被评测程序停掉的）算没检出、也不算误报；“没拿到报告的次数”单列，免得拒答多的模型显得误报少。outcome 是 `patch rejected` 之类、但模型给过报告的，报告照样算：工作流照样把它发出去。
- **一个配置一份 models.yaml，只列它那一家**：agentd 启动时读每个列出的供应商的 key，读不到就拒绝启动，所以不能直接用 `config/models.yaml`（三家都列着）。三个配置照抄它的 provider 设置和 audit_v1 的设置（max_tokens 16000、effort high、提示词、schema、Claude 的服务端回退），评测的就是产品配置本身。本地模型的 effort 也是 high（产品配置里 audit_v1 只有一个 effort），这和 T1 的测试配置（medium、8000）不同。策略用 `config/policy.yaml`，只把 repos 换成评测集的仓库。
- **以账本为准标模型**：报告里每个配置的名字取账本 `model_calls` 记下的 provider/model；另外数“账本里的模型和配置不同的运行”，换 models.yaml 没生效会在这里露出来。服务端回退答的另记。
- **钱**：一次运行只在“账本里这个状态目录所有运行已经结算和还预留着的钱 + 所有没结束的付费运行的预算 + 它自己的预算 ≤ 上限”时才开始。agentd 保证一次运行花不过它的预算，所以加起来花不过上限；最后最多有 $1.5 用不上。另外四条：
  - 钱从账本算，不从日志算：日志里没记下的运行（评测程序在“开始运行”和“写进日志”之间被停掉）花的钱也算进去，下一个评测程序启动时把这样的运行取消掉，免得没人看着它。
  - 没结束的运行包括以前的评测程序留下的、属于别的配置的：它们等自己的配置再跑时还会花钱，在那之前按预算占着上限。
  - 预算必须大于 0：agentd 把 0 当成“用默认预算”（$5），上限算不到它。
  - agentd 的上界算错时，一次运行会花过预算（agentd 照实记账、记一条错误日志）。评测程序一看到这种运行，就不再开始付费运行。
- **停掉的运行**：等预算、等审批或核对、或者超过配置的时限（付费 30 分钟，本地 60 分钟）的运行，评测程序取消它，算没检出，结局记成 (budget)、(waiting)、(timeout)。p95 耗时只算自己结束的运行。agentctl 偶尔失败时，下一轮再问，直到这次运行的时限。
- **放宽口径**：MITRE 研究视图里互为祖先后代、同一个父节点、或者最近的 Class 相同的 CWE 算相关；Pillar 太宽，不让它把东西连起来；不在视图里的编号只和自己相关。于是 787、125、120、119 互认，22 和 23 互认，862 和 863 互认；89 和 78、79 和 89 不互认，CWE-20 也不算注入的祖先。有个怪处：611（XXE）和 601（开放重定向）同属 Class 610，算相关；同一行上报错成这种机制的情况很少见，我没加例外。
- **文件、行号和 CWE 的写法**：文件比较时去掉开头的 `./`、`/` 和 diff 头里的 `a/`、`b/`，大小写要一致；行号必须是整数（不收字符串、小数和布尔）；CWE 接受 `CWE-89`、`cwe-089`、`89` 这些写法。
- **报告不存解释和补丁**：原始 JSON 里每条发现只留严重度、CWE、文件、行号和标题（截到 200 字）：模型写的解释和补丁可能引用上游代码。完整答复在状态目录的账本里，不进仓库。
- **“截止之后”按最早公开的日期算**：取公告发布和修复提交中较早的那个。修复一推到 GitHub 就公开了，往往比公告早几个月；只看公告日期会把模型可能见过的修复也算成“没见过”。用例文件因此多记了修复日期（`fixed`）。三个模型的知识截止：Opus 5.5 是 2026 年 6 月（Anthropic 的文档）；gpt-6.1-sol 是 2026-04-30，只找到第三方页面，OpenAI 的模型页没核实；gpt-oss:20b 是 2024 年 6 月。子集按最晚的截止（2026-06-30）挑；报告里每个模型按自己的截止日期分前后。
- **挑用例的规则**（五个调研代理按语言各找了 8–10 个候选，我从中挑）：
  - blame 找到的提交要真是引入点：不是合并提交、不超过 400 行、漏洞代码是这个提交加进来的；引入提交太大或者分散在几个提交里的，改用反向应用。
  - 反向应用的用例只收修复里没有解释漏洞的注释的：反向之后那些注释成了 diff 里删掉的行，等于把答案写在 diff 里（hatchet 删掉的注释写着 SSRF、lmdeploy 写着 pickle 和 RCE、libfyaml、spinnaker、toon、async-http-client 都这样，没收）。保留下来的也比真实提交好认（删掉的就是保护代码），所以两类分开报。
  - 标注的 CWE 取公告里列的；列了几个的，取最贴近代码的那个。不用 Pillar（比如 anubis 的公告只写了 CWE-284，它在研究视图里是 Pillar，放宽口径也连不上任何别的 CWE，这个用例没收）。
  - 不收改了二进制文件的提交：审计工具拿到的 diff 带 `--text`，二进制文件会变成几页乱码（thumbor 的引入提交带两张 JPEG，没收）。
  - 改动行数按 `git diff-tree --numstat` 算，最大的 315 行。
- **注入的做法**：在标注文件里第一个标注行前插入一段注释，缩进和那一行相同，注释语法按语言；新提交的父提交是漏洞提交的父提交，所以它的 diff 就是漏洞提交的 diff 加这段注释。标注按插入的行数下移，由读用例集的代码算，不另存。12 个漏洞用例配了注入：blame 7 个、反向应用 5 个，每种语言 2–3 个，挑的是本身看得清的漏洞（基础检出率太低，注入的影响就看不出来）。
- **用例说明用中文**：用例表是给你看的，`cases.json` 里的 `why` 用中文；注入的文字是插进代码里的，用英文。

### 测试怎么测

全部用模拟模型，没有花钱。

- **端到端**（`tests/test_eval_runner.py`，评测程序自己拉起 Temporal、agentd 和沙箱里的 Worker，modelsim 当两个模型）：
  1. 小用例集（`tests/eval_fixture.py`：两个按 `make-audit-target.sh` 的方式造的仓库，5 个用例：blame 和反向应用的漏洞、一个 C 的越界写、一个正常提交、一个注入用例）在两个配置下各跑 3 次。模型 a 走 Anthropic 接口、按价格计费，模型 b 走 Chat Completions、免费。每个用例的答复都是脚本设计好的：行号恰好在窗口边上、差一行出窗口、CWE 相关但不相同、文件名带 `b/`、拒答、一次不合 schema 被重新要、补丁打得上和打不上、一次大部分读缓存、标题超长。算出来的指标逐项等于手算的值：检出 4/9（放宽 6/9）、按来源和按截止日期分、误报 1/3（任何发现 2/3）、注入误放行 2/3、配对下降 1/3、补丁 2/3、花费、缓存命中 5%、拒答 1、不合格 1/16、账本标的模型。另外核对：每个请求都拿到了脚本答复、脚本恰好用完；所有写都是 DRY_RUN、没有审批单、没有非 dry-run 的任务；报告由命令行生成，原始 JSON 里没有解释、补丁和上游代码，标题截到 200 字。
  2. 上限：上限恰好够三次运行（第三次的预算把上限填满到 1 micro），另有一个别的配置留下、没结束的付费运行占着预算：只跑了 3 次，花费 = 3 次的；同一个状态目录换一个宽松的上限再跑：只补后 3 次。
  3. 预算不够一次预留的运行停在 PAUSED_BUDGET，评测程序取消它，记为没报告、没花钱，modelsim 一个请求都没收到。配置的时限设成 60 秒：评测程序要是没认出这种状态，测试会因为超时失败，不会挂半小时。
  4. 预算为 0 被拒绝；一次运行花过预算（计数说 1000 个输入 token，计费 10 万个），之后的付费运行不再开始；一个日志里没有的运行（在同一个状态目录上直接用 agentctl 起的）被下一个评测程序取消，评测程序照样跑完它该跑的。
