# M4 记录：审批

2026-10-20。验收 T4、T5、T6、T14 写成黑盒测试，三种环境都通过（结果见“测试怎么测”）。设计文档第 10 节的全部内容都做了；第 5 节第 7 项和 M2a、M3a 留下的“门铃先直接发信号，到 M4 改走 outbox”也一起做了：批准、核对和追加预算的门铃都走同一个 outbox。

## 做了什么

- **审批表**（迁移 `00008_approvals.sql`）：00001 里的 approvals 表从没写过一行，重建成审批真正要的样子：所属任务和工具、调用的规范化参数、副作用记录的载荷哈希、审批单上下文（blob）、状态（PENDING、APPROVED、REJECTED、EXPIRED、EDITED、SUPERSEDED，带 CHECK）、建立和到期时间、谁在何时决定、决定的幂等键、拒绝理由、修改后的补丁和修改后调用的参数哈希、取代关系、批准后被用掉的时间。一条副作用记录最多一张审批单（`effect_id UNIQUE`）。SQL 要比较的时间（到期、门铃何时再试）用定宽格式写（`ledger.Stamp`，九位小数），按文本排序就是按时间排序；`ledger.Now` 会去掉末尾的 0，不能直接比较。
- **触发**：策略写 `require_approval` 的写工具，第一次调用时渲染并记录载荷（M3 的协议），副作用记录写成 AWAITING_APPROVAL，同一个事务里建审批单，返回 `needs_approval`（带审批单 ID 和到期时间）。工作流照旧把 AgentState 设为 WAITING_APPROVAL，等门铃或 24 小时定时器。只读工具不能要求审批，agentd 启动时就拒绝这样的策略（审批卡的是副作用，读没有副作用）。
- **绑定**：审批单记下副作用记录的载荷哈希。批准之后，网关在一个事务里核对：审批单还是 APPROVED、没被用过、没过期，任务没被取消，副作用记录还在 AWAITING_APPROVAL，而且记录下来的载荷 blob 重新算出的 sha256 等于审批单绑定的那个，然后才改成 PENDING，之后按 M3 的协议领取、发送、恢复。差一个字节就不发：副作用记为 ABANDONED，原因写明两边的哈希，任务得到 `denied`，agentd 记一条 error 日志。执行时发出的就是记录下来、审批过的那份载荷，不重新渲染（文档第 10 节“绑定”，rev 272）。工作流换了参数，就是另一条副作用记录，要另一张审批单，或者被每任务一次的上限拒绝；所以一张审批单只放行它绑定的那一份载荷。
- **人看到的哈希也要对**：每个决定都要带审批人看到的载荷 sha256（`--payload-sha256`），和审批单的对不上就不算数；决定的事务里还要再算一遍记录下来的载荷，载荷在记录之后被改过也不算数。`approvals show` 也先核对，对不上就报错，不把被改过的载荷当成待批的展示出来。
- **过期**：以审批表的 `expires_at` 为准（策略的 `approval_ttl`，默认 24 小时，最长 30 天，只能和 `require_approval` 一起写）。agentd 有一个后台循环，到时间就在一个事务里把审批单改成 EXPIRED（决定人记 agentd，原因“到期前没人决定”）、副作用记录改成 ABANDONED、写一条门铃；启动时先处理 agentd 停着的时候到期的。新审批单建立时唤醒它，没有待批的就每分钟看一次。调用和决定也各自检查到期：过期按拒绝处理，任务得到 `expired` 和原因。批准了的审批管到写生效为止：写还没生效就到期，审批同样作废，此后不再发它的任何请求。工作流的 24 小时定时器只是唤醒，比它短的 TTL 也照样准时过期，因为 agentd 到期时会自己敲门铃。
- **三种决定**：
  - 批准：门铃唤醒任务，它重发同一个调用，按上面的绑定核对后发出。
  - 修改后批准（`agentctl approvals edit --patch-file`）：补丁存成这个任务的 blob，审批单记为 EDITED。任务对原调用的重发得到 `edited` 和新的 `patch_ref`，工作流照设计文档第 7 节的代码重新 `git.apply_check`，再用新补丁调用 `open_draft_pr`。那是一条新的副作用记录，要一张新的审批单；新审批单建立的那个事务里，原审批单改为 SUPERSEDED，原副作用记录改为 ABANDONED，然后才数这个任务的写操作，所以 `max_per_run: 1` 仍然放得下修改后的那一个。只有参数正好是“原调用换上审批人的补丁”的调用才算修改后的调用；工作流拿别的补丁来，原副作用还占着名额，被拒绝。
  - 拒绝：必须写理由（可打印文字，最多 2000 字节），副作用记录同一个事务里改为 ABANDONED，任务得到 `rejected` 和理由。
- **报告里的审批**：`github.comment_commit` 渲染报告时从 agentd 自己的审批表读这个任务的审批，像 PR 编号一样不信工作流传来的东西。围栏外只写 agentd 自己记录的状态（“Approval of github.open_draft_pr: rejected”；批准了却没有发成的，按结局写“approved, not sent”“approved, failed”或“approved, outcome unknown”；最多列 20 张），谁决定的、拒绝理由这些人写的文字放进围栏，链接和 @提及不生效。
- **并发**：决定在一个 SQLite 事务（BEGIN IMMEDIATE）里判定，`UPDATE ... WHERE status = 'PENDING'`，先到的有效决定生效。后到的得到 FAILED_PRECONDITION，消息里写着“已经由谁在何时作了什么决定”。同一个幂等键再发一次同样的决定，返回当初记下的结果，不算冲突；同一个键配别的决定，拒绝。到期也是一种决定：过期之后再批准，得到“already decided: EXPIRED by agentd at …”。
- **审批单内容由 agentd 生成**（`agentctl approvals show`，Control 的新接口 `GetApproval`）：
  - 写操作本身：`open_draft_pr` 的 `Describe` 给出目标仓库、base 分支、新分支名、被审计的完整提交 SHA、补丁全文、改动的文件和改法（修改、新建、删除）、git MCP 服务器在沙箱里跑的 `git apply --check` 结果；还有 GitHub 上此刻的情况：base 分支的头、被审计提交和它比较的结果（落后几个提交、在不在 base 分支的历史里），以及 Execute 写之前要做的两处核对（补丁涉及的文件在被审计提交上、在 base 的头上）此刻的结果。这些都是只读请求，也写明了“提交建在发送时的头上，补丁涉及的文件在头上变了就不推”和“推分支会触发 push、create 的工作流”。
  - 任务的上下文（`tasks.Task.ApprovalContext`，D12：任务配置决定）：安全审计给出提出这个补丁的那次审计的摘要和发现列表（严重度、CWE、文件和行号、标题）；补丁不是哪次审计提出的（审批人改的），就给最近一次的，并写明不是同一次。
  - 将发出的完整载荷和它的 sha256、到期时间、状态和决定记录，以及本任务此刻已花、已预留的钱和上限（展示时现查）。
  - 文字里所有不可打印的字符、以及显示成空白的可打印字符都转义（新的 `safetext.Text` 保留换行和制表符，补丁照原样可读）。上下文按键名排序、缩进打印，agentctl 不认识任何一种任务的字段。agentctl 一次最多收 512 MiB：一个 PR 的载荷可以远大于 gRPC 默认的 4 MiB。
- **门铃 outbox**（`internal/outbox`，新表 `outbox`）：决定、到期、核对、追加预算的事务里各写一条门铃，提交之后唤醒 outbox。outbox 按任务合并，一个信号覆盖它之前写的所有门铃，发给 agentd 启动的那个执行（workflow ID 加 run ID）。Temporal 收下就记 delivered；执行已经结束（NotFound）记 run_ended，不再试；别的失败按 1、2、4…秒退避重试，最长一分钟一次，直到送达。agentd 崩溃留下的门铃，下一个 agentd 启动就发。M2a 的追加预算和 M3a 的核对原来直接发信号，现在都走它，重复的请求不再补发（门铃不会丢了）。
- **入口**：Control socket 上 `ListPending` 列出待批的审批单（已取消任务的不列，过期的不列；不带载荷，载荷在 `GetApproval` 里），新加 `GetApproval`，`ResolveApproval` 做三种决定；命令行 `agentctl approvals list | show | approve | edit | reject --reason`，决定都要 `--payload-sha256`，审批人名字默认是当前用户，`--as` 可以换。
- **开发策略**：`config/dev/policy.yaml` 的 `open_draft_pr` 改成需要审批。开发配置都不配 GitHub，GitHub 工具只 dry-run，不受影响；配了 GitHub 之后，真模型和真实 GitHub 写操作之间总有人看过补丁。配置测试改成断言这一点。

## 我定的几处（文档没细说）

- **dry-run 不要审批**：任务是 dry-run，或者 agentd 没配 GitHub（工具只能 dry-run），需要审批的写操作照旧只渲染、记录成 DRY_RUN，不建审批单。什么都不发，没有东西要批；评测要用 dry-run 跑（第 11 节），不能每次都停下来等人。
- **修改后的调用要再批一次**：审批人改的是补丁，可审批绑定的是完整载荷（PR 标题、正文、分支名、每个文件改后的内容和原来的 blob），这些在工作流重新校验、agentd 重新渲染之前审批人都没见过。所以新审批单是 PENDING，要再批准一次，审批人批的始终是他看过的那份载荷。
- **只收“新的”修改**：修改后的调用如果是这个任务已经有的副作用（补丁和原来一样，或者改回以前用过的补丁），它会得到那条旧副作用的结果，工作流在两张审批单之间来回转。agentd 直接拒绝这样的修改，让审批人改为批准或拒绝。补丁也要能被解析、不超过 256 KiB；是否越界、能否打上，交给工作流的 `git.apply_check` 和 `open_draft_pr` 自己的检查（validate_patch 那两道）。补丁和决定在同一个事务里存成任务的 blob。
- **批准管到写生效为止**：文档第 6 节说“确认审批已批准、未过期”在改成 PENDING 的同一个事务里。我照这个做，并且更进一步（复审时采纳的，见审查一节）：批准之后任务在到期前没有重发调用（比如 Worker 停了一天），或者改成 PENDING 之后写还确知没生效（没被领取；或者交还时查找没查到、工具说什么都没做）就到期了，审批都作废，记为 EXPIRED，原因写明是谁在何时批准的；它发出过请求的，原因还写明那个请求做成的东西可能还在。可能已经生效、在途的写（只有幂等类会这样：恢复查不了它）不受影响，用原来的键照常重发。
- **审批人的名字由 agentctl 给**：Control socket 在 0700 目录里，能连上的就是操作者本人，v0.1 是单用户；agentctl 默认填当前用户名，`--as` 可以写别人。名字要是可打印文字、不超过 100 个字符，`agentd` 保留给 agentd 自己的决定（过期）。
- **冲突用错误表示**：proto 里 `ResolveApprovalResponse` 原注释是“冲突时返回之前的决定”。我改成 FAILED_PRECONDITION 错误，消息里写清之前的决定、谁、何时：agentctl 冲突时以非 0 退出，脚本和人都不会把别人的决定当成自己的。
- **已取消、已结束的任务**：取消之后网关拒绝这个任务的一切调用，审批了也发不出去，所以 `approvals list` 不列已取消任务的审批单，对它的决定直接拒绝；Temporal 里已经结束的任务（`runs get` 是 SUCCEEDED、FAILED、CANCELLED、UNKNOWN）同样拒绝决定。所以做决定时要能连上 Temporal，和 `reconcile resolve` 一样。
- **审批单在建立时生成并存下**，展示时只现查花费：审批单记的是“出审批单时”看到的样子（文档第 10 节），之后 base 分支怎么动，Execute 发送前都会再核对。生成审批单要读 GitHub、起一次 git MCP 服务器，这些读之前先数这个任务的写操作，已经到上限的调用直接拒绝；同一个任务、同一个工具的这几步一次只做一个，被攻破的工作流不能靠一遍遍（或同时）换参数耗掉令牌的 API 配额。
- **策略要审批，就没有不经审批发出的写**：没被领取、确知没生效的 PENDING 副作用，不管是什么时候、在什么策略下记的，只要现在的策略要审批而它没有批准过的审批单，就改回 AWAITING_APPROVAL 补一张审批单（审查发现的第 1 条）。被领取过、可能已经发出的：恢复时不重发，只查；查不到再补审批，查不了（幂等类）交给人核对。
- **门铃按任务合并、按执行发**：一个信号唤醒任务一次就够，工作流醒来后以 agentd 的表为准；信号带上 run ID，发不到同一个 workflow ID 下别的执行。

## 和父会话任务说明不一致的一处

任务说明写的是“执行前 agentd 重新渲染载荷并比对，差一个字节就拒绝执行”。设计文档 rev 272 已经改成“执行时发出的就是记录下来、审批过的那份载荷，不重新渲染”，M3a 的代码也是这样（重新渲染会把已经成功的评论当成载荷变了，见 m3-notes）。我照设计文档做：不重新渲染，执行前核对的是“要发出的那份载荷的哈希等于审批过的哈希”，差一个字节同样拒绝执行（T5 第一个用例）。

## 测试怎么测

- **T4**（`tests/test_t4_approval_restart.py`），两个场景：
  1. 任务停在 WAITING_APPROVAL 时 kill -9 agentd、重启 Temporal 开发服务器（测试框架给它一个数据库文件，`restartable_stack`，原来是内存的，重启就丢）、再起 agentd，Worker 不重启。审批单还在，ID 和载荷哈希不变；模拟 GitHub 没收到任何写请求。审批单的内容逐项核对：载荷的 base 和被审计提交、补丁全文、改动的文件、`git apply --check` 通过、base 的头和“identical、落后 0、在 base 历史里”、两处核对都是 ok、发现列表、已花的钱。批准之后任务跑完，只开出一个 PR，报告里写着这次批准；历史里只有一个信号，outbox 里那条门铃记 delivered。
  2. 审批 8 秒过期，到期时 agentd 正停着：它启动后立刻把审批单记为 EXPIRED（agentd，“到期前没人决定”），任务被门铃唤醒、得到 `expired`、发报告（报告写明过期和原因）、以 SUCCEEDED 结束，没有 PR，副作用记录 ABANDONED。之后再批准，得到“already decided: EXPIRED by agentd”。
- **T5**（`tests/test_t5_payload_binding.py`），四个场景：
  1. 批准时把门铃扣住，停掉 agentd，把账本里记录的载荷改一个字节（`security fix` 改成 `security fiX`），再起 agentd：门铃送达，任务重发，网关拒绝发送，副作用记录 ABANDONED、原因写明两边的哈希，任务得到 `denied` 并发报告，GitHub 没收到任何写请求；`approvals show` 也拒绝展示这份载荷。
  2. 审批人用自己的补丁修改：原审批单 EDITED，工作流对审批人的补丁重新跑了 `git.apply_check`（历史里它排在用新补丁开 PR 的调用之前），出现第二张审批单，取代第一张（SUPERSEDED），新审批单的载荷里是审批人的改法；批准第二张后 PR 开出，GitHub 收到的树里只有审批人的修复、没有模型的；第一条副作用 ABANDONED。
  3. 审批人的补丁改了 `.github/workflows/`：工作流的 `git.apply_check` 拒绝，报告写 `patch rejected`，没有第二张审批单，没开 PR。
  4. 恶意工作流（`tests/rogue_workflows.py` 的 `SwapsThePatch`）：让审批人修改、批准修改后的补丁，然后不用批准的那份，改用模型自己的补丁再调用：得到 `edited`，什么都没发出去；第二张审批单是 APPROVED 但没被用过。
- **T6**（`tests/test_t6_concurrent_decisions.py`）：四个任务同时等审批，每张审批单同时起两个 agentctl，一个以 alice 批准、一个以 bob 拒绝。每张都只有一个成功，另一个以非 0 退出，错误里写着先到的决定、谁、何时；账本里的状态就是先到的那个。各自用原来的幂等键再发一次：先到的那个照样成功，后到的照样冲突。之后任务按先到的决定走：批准的开出一个 PR，拒绝的不开 PR，报告里有 bob 的理由。
- **T14**（`tests/test_t14_doorbell_outbox.py`），两个场景：批准（和追加预算）的门铃扣在 outbox 里，确认它没送出、任务还在睡，kill -9 agentd，再起一个：门铃送达，任务跑完，历史里一个信号，outbox 记 delivered。工作流自己的定时器是 24 小时（预算是 1 小时），测试的等待只有 60 秒，所以唤醒任务的只能是门铃。
- **一半发出去的写过期**（`tests/test_approval_partial_write.py`）：见第五轮第 3 条。
- **审批绕不过去**（`tests/test_approval_gate.py`）：agentd 没配 GitHub 时开 PR 的写被记成 PENDING（只能 dry-run，不要审批），在改记 DRY_RUN 之前被故障挂住；kill -9 之后换一个配了 GitHub 的 agentd：那次写改回等审批，有了审批单，任务停在 WAITING_APPROVAL，GitHub 没收到任何写请求；批准后开出一个 PR。
- **其他黑盒测试的变化**：`test_cancel.py` 等审批时取消，现在还核对审批单不再列出、对它的批准被拒绝；`test_dry_run.py` 加了“dry-run 在需要审批的策略下也不建审批单”。测试框架加了 `approval_policy()`、`restart_temporal()`、扣住门铃的故障（`hold_doorbells_while_exists`）和读模拟 GitHub 评论的辅助函数；模拟 GitHub 的日志记下建树请求里的文件内容，测试才能看出 PR 里是谁的修复。

## 推送前审查（安全审查 + 对抗性审查）发现并修掉的问题

两个审查代理各在自己的 worktree 里做实验，都没改我的文件。下面的问题都核实过、已修，并补了测试：

1. **记录时不需要审批的写，之后不经审批就发出去了**（中，两个审查都发现并实测）。网关每次调用都按当前的策略算要不要审批，可只有记成 AWAITING_APPROVAL 的副作用才去查审批单。两条路会留下没批过的 PENDING：agentd 没配 GitHub 时记下的写（只能 dry-run，不要审批），在改记 DRY_RUN 之前 agentd 停了，再起时配了 GitHub；或者策略从 allow 改成 require_approval（这次的开发策略正是这么改的）之前记下、还没发出（被领取前停了，或者没发出去被交还）。审查代理实测两条都开出了 PR，审批表是空的。改法：没被领取的 PENDING 副作用，策略要审批、又没有已经批准并用过的审批单时，在一个事务里改回 AWAITING_APPROVAL、补一张审批单，调用得到 needs_approval（`gate`）。已经被领取的（请求可能已经发出）交给恢复，不动。黑盒测试 `tests/test_approval_gate.py` 走的是没配 GitHub 那条路，Go 测试覆盖“记下后停掉”和“没发出去被交还”。
2. **改回之前的补丁会让工作流来回转**（中，两个审查都发现）。A1（模型的补丁）改成 P2，得到 A2；再把 A2 改回模型的补丁，修改后的调用就是原来那条副作用，它的审批单已被取代，回答 edited 和 P2，于是 P1、P2 来回，直到循环保护拦下。同理，改成任务以前用过的任何补丁，都会落到那条旧副作用的结果上（被拒、过期，甚至已经开过的 PR）。改法：修改后的调用如果是这个任务已经有的副作用（按工作流 ID、工具和改后的规范化参数算），拒绝这次修改。“和原来一样的修改”是它的特例。
3. **一个大载荷的审批单让整个待办列表收不到**（中，对抗审查实测）。PR 的载荷带着补丁涉及的每个文件改后的全文（最多 20 个、每个 1 MiB，控制字符经 JSON 转义后约 6 倍），agentctl 按 gRPC 默认只收 4 MiB：`ListPending` 整个失败（`approvals list`、`reconcile list` 和 `reconcile show` 都靠它），这张审批单的 `show` 也失败，没人看得到它的哈希，也就没法决定。改法：`ListPending` 里的审批单不再带载荷（`GetApproval` 带）；agentctl 收的上限调到 512 MiB。
4. **并发的调用能绕过“先数名额再生成审批单”**（低）。不同参数的调用各自是一条副作用，单飞合并不了，十个同时来的调用各自生成了审批单（读 GitHub、起 git 工具服务器），之后九个才被事务拒绝。改法：同一个任务、同一个工具，从数名额到生成审批单再到记录，一次一个（进程里的锁，一个数据目录只有一个 agentd；起初是分段锁，复审后改成按任务和工具精确加锁）。
5. **审批单上的发现和补丁可能不是同一次审计的**（低）。审批单取的是最近一次被接受的审计；被攻破的工作流可以审计两次，拿这次的补丁配那次的发现。改法：任务的上下文函数拿到调用的参数，取提出这个 `patch_ref` 的那次审计；没有哪次审计提出过（审批人改的补丁）就取最近的一次，并写明 `patch_from_this_audit: false` 和这个任务一共有几次审计。
6. **看起来是空白的字符**（低）。韩文填充符（U+3164 等）、盲文空格 U+2800、变体选择符这些字符 `unicode.IsPrint` 认作可打印，终端上却什么都不显示；模型写的补丁可以用它当参数名，审批人看到的是空格（Python 接受 `def f(conn, name, ㅤ=None)`）。改法：`safetext` 的三个函数都把它们转义。
7. **报告把没发出去的写说成“批准”**（低，对抗审查）。批准之后载荷被改、或者任务被取消，副作用记为 ABANDONED，审批单还是 APPROVED，报告围栏外写着“approved”。改法：这种情况写“approved, not sent”，原因放进围栏。
8. **批准后过期的审批，重发同一个批准返回成功**（提示）。现在返回“已经决定：EXPIRED”。批准人的名字保留在过期原因里。
9. **被拒的修改留下了补丁**（提示）。补丁原来在决定之前就存成任务的 blob；现在和决定写在同一个事务里，决定不成立就不留。
10. 另外几处顺手的限制：报告围栏外最多列 20 张审批单（GitHub 一条评论最多 65,536 个字符）；`approval_ttl` 最长 30 天（等审批的任务每 24 小时醒一次重发，每次都算一个调用，太长的 TTL 会把循环保护的 100 个调用用完）。

### 复审（两个审查代理复查这些修复）发现并修掉的问题

两个复审的结论基本重合：

1. **修改的拒绝放早了，重发同一个修改反而失败**（中）。上面第 2 条的检查放在决定的事务之前，工作流一做修改后的调用，同一个键重发这个修改（比如 agentctl 超时后重试）就被告知“改为批准或拒绝”，而不是当初记下的 EDITED；第二个审批人晚来、发同样的补丁，得到的也是这句，而不是“已由谁在何时修改”。改法：这项检查挪进事务，排在“同键重发”和“已经决定”两项检查之后。
2. **分段锁把不相干的任务连在一起**（低）。64 段锁，两个任务落在同一段的概率是 1/64，一个任务生成审批单慢，另一个就跟着等；`sync.Mutex` 也不看调用的 context，等的调用可能熬过自己的超时。改法：按（任务、工具）精确加锁，等的时候 context 结束就放弃。
3. **报告把批准后被工具拒绝、或失败的写说成“批准”**（低）。上面第 7 条只管了 ABANDONED；Execute 自己拒绝（GitHub 上的文件和镜像对不上）是 DENIED，GitHub 回 4xx 是 FAILED。改法：批准了却没有发成的写，按副作用的结局写“approved, not sent”“approved, failed”或“approved, outcome unknown”，原因放进围栏。
4. **已被领取的写，经调用的恢复路径不经审批重发**（低）。上面第 1 条只管了没被领取的 PENDING；被已经不在的 agentd 领取过的，调用走恢复，查不到就重发。平时启动时的恢复会先把它交还，再由下一次调用补审批，只有那次恢复没做完时才会走到这里。改法：恢复要重发，必须策略不要求审批，或者审批单已批准、用过、没过期；否则只查，查不到就交还，下一次调用补审批。
5. **取消和补审批撞在一起**（提示）。调用过了 Invoke 的取消检查之后任务才被取消，那次写会被改回等审批，留下一张谁也看不到、要等到期才作废的审批单。改法：改回等审批的那条 UPDATE 也检查任务没被取消，取消了就直接记 ABANDONED。
6. 列表不再读、不再校验每张审批单的载荷（展示和决定时会校验），列一次不必读上百 MiB。

### 第三轮复审

两个审查代理确认上面的修复都成立，又各自发现同一个潜在问题（低，现在没有工具会碰到）：**可能已经发出的写，被当成“没发出”处理**。幂等类的写在恢复时不查就交还（启动时、或者不许重发时），它的请求可能已经落地，可接下来的调用把它当成“什么都没发出”：批准过、已过期的，审批作废、记成没发；当初在不要求审批的策略下领取过的，又挂出一张审批单，审批人拒绝了，记录就说没发，而写其实已经在 GitHub 上了。改法：副作用加一个“可能已经生效”的标记（`maybe_sent`）。工具说一个外人看得到的请求要发出时（`proceed`）置上，而不是领取时：领取本身什么都不发。清掉它要有覆盖此前每一次尝试的证据：查找在时限内没查到（对 lookup 类，查找说了算）；这次尝试什么都没做（工具返回 ErrNotSent 或可重试的拒绝），而它之前没有可能生效的尝试；或者人核对说没执行。所以只有幂等类的写会带着标记被交还（恢复查不了它）。有效期和补审批只管标记清掉的写：标记还在、有审批的，算在途，照常用原来的键重发；标记还在、却从没批过的，交给人核对（UNKNOWN），不重发，也不挂审批单。恢复时要不要重发也按类别：lookup 类先查，没查到再发就是一次新的请求，要在审批的有效期内，而且是在真要再发的那一刻看（查找要等请求的时限过去，这段时间里审批可能到期），过了就交还，下一次调用让审批过期作废；幂等类查不了，有审批就算在途，照常重发。

**审批的有效期管到写发出为止**（对抗审查提出，复审时我采纳了）。原来我照设计文档第 6 节的字面，只在改成 PENDING 的事务里查有效期：之后 agentd 崩溃、或者请求没发出去被交还，下一次尝试可能在过期很久之后才发出（Invoke 没有排队超时，停机多久都可能）。现在没被领取、确知没生效的 PENDING 写（从没领取过，或者工具什么都没做、查找没查到而交还，见第三轮的 `maybe_sent`）要发出时，审批已经过期就作废，按拒绝处理，原因写明“批准过，但到期时写还没生效，agentd 不再发它的任何请求”；人核对后判定“没执行”而改回 PENDING 的写也一样（起初我给它留了例外，提交后的自动安全审查指出：批准之前、或者过期之后的核对记录也会让它绕过过期，就去掉了）。已经被领取、请求可能在途的写不受影响，照常按类别恢复。反过来，到期前一刻批准、门铃晚到，任务醒来时已经过期，也照样作废；默认 TTL 是 24 小时，这只在到期那一刻附近出现。设计文档第 6 节第 1 项和第 10 节“过期”要随之改，改动清单在 PR 说明里，等你批准。

### 第四轮（两个审查代理复查 `maybe_sent`，加上提交后的自动安全审查）

1. **工具什么都没做就交还的写，带着“可能已生效”的标记，过期后照发**（中，提交后的自动安全审查）。上一版在 `proceed` 置标记，工具随后返回 ErrNotSent 或可重试的拒绝时交还、却不清标记（顾虑是 `open_draft_pr` 推了分支之后的 429）。于是这个写被当成在途：过期之后下一次调用照样开 PR。改法：工具说这次尝试什么都没做时，若之前没有可能生效的尝试，交还时清掉标记（这正是工具接口的约定：ErrNotSent 和拒绝表示这次什么都没生效）；幂等类重发时这次什么都没做，之前那次仍可能已落地，就留着标记。lookup 类查过没查到再重发，重发前的尝试都已确知没生效，按“之前没有”算。
2. **查找等请求时限的那段时间里审批到期，恢复照样重发**（低，我自己复查时发现）。恢复先算“能不能重发”，再查找、等请求的时限过去（几分钟），没查到就重发；审批要是在等的时候到期，重发的就是一个过期后的新请求。改法：没查到、真要再发的那一刻再看审批的有效期，过了就交还，下一次调用让它作废。
3. **一半发出去的 PR 被记成“没发出”**（低，对抗审查实测）。`open_draft_pr` 先推分支、再开 PR；推完分支后 agentd 崩溃（或 PR 那一步 429），查找只找 PR，没找到，过期后作废的原因写着“到期时还没发出”，报告也这么写，分支却已经在 GitHub 上、触发过推送的工作流。改法：原因改成“到期时写还没生效”（PR 确实没开），不再说什么都没发出；发出过请求的，再写明“它的一个请求在某时发出过，那个请求做成的东西可能还在”（第五轮加的新列 `last_request_at`，`proceed` 时记下，交还时不清）。分支留在 GitHub 上，和 M3 里取消一次推完分支的写一样，要人去删（见“留到后面”）。我没有按审查代理的建议让标记一直留到人核对：那样 lookup 类的写只要发过一个请求，就再也不受有效期约束，正是第 1 条的问题。
4. **核对说“没执行”的写不一定会重发**（提示，对抗审查）。审批过了期，“没执行”之后的下一次调用让它作废，`agentctl reconcile resolve --help` 和 README 却说会用原来的键重发。改法：两处都写明审批过期（或任务已结束、已取消）时不再发。
5. **旧账本**（提示，安全审查）。00008 给 `maybe_sent` 的默认值是 0；M3 的 agentd 不查就交还过的幂等写（被领取过、现在没人领取）可能已经生效。改法：00008 把这样的写标成 1。M3 没有审批，没有工具是幂等类，所以只是防着以后。
6. 交还时的提示（`errEffectReleased`、日志）不再一律说“请求没生效”：带着标记交还的写，说的是“可能已生效，下一次调用接着处理”。

### 第五轮（两个审查代理复查第四轮）

1. **幂等写一次尝试结果不明，紧接着的重发什么都没做，标记就被清掉**（低，对抗审查；我自己复查时也发现了）。结果不明时恢复当场用原来的键重发，重发返回 ErrNotSent，交还时按“这次尝试开始时的标记”判断，而那份是第一次尝试之前读的，是 0，于是清掉标记；过期后下一次调用就让一个可能已经落地的写作废。改法：结果不明时，按账本里的标记交给恢复：这次尝试发出过请求（`proceed` 记下了），就算可能已生效。起初我一律算作可能已生效，复审时安全审查指出，没发出任何请求就结果不明的尝试也会因此被当成在途，过期后照发（低，没有幂等类工具）；改成看账本。
2. **从没发出过请求的幂等写，过期后照发**（低，对抗审查）。领取它的 agentd 在发请求前就停了，标记是 0、什么都没发出；审批过期之后，启动时的恢复把它交还、下一次调用让它作废，调用路径上的恢复却直接重发。改法：幂等写只有标记在时才算在途；什么都没发出的，重发就是新请求，和 lookup 类一样要在审批有效期内（`resendNew`）。
3. **一半发出去的 PR**（低，安全审查，同第四轮第 3 条）：账本和报告不再只说“没生效”，而是写明它的一个请求发出过、做成的东西可能还在（`last_request_at`）。黑盒测试 `tests/test_approval_partial_write.py`：GitHub 建好分支、回答晚到，agentd 的请求超时、工具说可以重试，重试等到审批过期才来：PR 没开，副作用 ABANDONED，审批 EXPIRED，原因和报告里都有“A request of it went out at”，GitHub 上一个分支、零个 PR。审查代理建议的另一条路（标记一直留到人核对，或者在途的写过期后照发）我没采纳，理由见第四轮第 3 条。
4. 我在定稿代码上把各轮的改坏检查重跑了一遍，发现一处补过修复之后就失去用例的检查：批准了、从没被处理、策略又不再要求审批（重启时改了策略），改成 PENDING 的那个事务里的过期检查。别的路径都会在 `gate` 里再查一次过期，只有这条不经过 `gate`。补了用例：这种写照样作废，不发。

## 留到后面

- **已经结束的任务的审批单**：取消的不列，但 Temporal 里已经结束（失败、被终止）的任务，审批单会一直列到过期；对它的决定会被拒绝（“the run has ended”）。要在列表里也排除，`ListPending` 得逐个问 Temporal。
- **做决定要连得上 Temporal**：为了拒绝对已结束任务的决定，`ResolveApproval` 先问 Temporal 任务的状态，和 `reconcile resolve` 一样；Temporal 不可用时决定报 Unavailable，稍后重试。
- **审批人是自己报的名字**：v0.1 单用户，Control socket 在 0700 目录里。多人共用一台 agentd 时（v0.2 的团队部署），要按连接认人（Unix socket 的对端凭据，或者 mTLS 的证书主体），审计记录里才有可信的“谁”。
- **修改后的补丁 agentd 只做语法检查**：越界、打不打得上，交给工作流的 `git.apply_check` 和 `open_draft_pr` 自己的检查。被攻破的工作流可以跳过 `apply_check`，但跳不过 `open_draft_pr` 在 agentd 里的检查，审批人还会在第二张审批单上看到 `git apply --check` 的结果。
- **改过、但修改后的调用一直没来的审批单**：停在 EDITED，原副作用停在 AWAITING_APPROVAL，永远不会发出，也一直占着这个任务这种写操作的名额。
- **审批疲劳**（第 10 节最后一项）：v0.1 只有开 PR 一种审批，批准率和平均停留时长还没记；以后加第二种审批时一起做。
- **审批单是建立时的快照**：base 分支之后再动，审批单上的“落后几个提交”“头上的核对”不会更新；Execute 发送前会再核对一遍，对不上就不推、交给人。
- **一半发出去的 PR 留下分支**：`open_draft_pr` 推完分支、PR 没开成，之后审批过期（或任务被取消），PR 不再开，分支留在 GitHub 上。审批过期的，账本和报告写明有请求发出过、做成的东西可能还在，但不说是哪个分支；取消的（M3 的路径）什么都不说。要么让 `open_draft_pr` 报告它留下的东西（查找时顺带看分支），写进原因和报告；要么作废时删掉自己推的分支。
- **取消时对“可能已生效”的写**：启动时放弃已取消任务的未发写（`AbandonUnsentEffects`）、调用发现任务已取消、工具什么都没做时任务已取消，这三处把没被领取的副作用记成 ABANDONED（“取消时还没发出”），不看 `maybe_sent`。M3 就是这样，只有幂等类的写会带着标记，现在没有这样的工具；改成带标记的交给人核对，那句话才属实。
- **门铃只要任务还在就一直重试**（最多每分钟一次）：Temporal 长时间不可用时，outbox 里会攒下这段时间的门铃，送达时按任务合并成一个信号。
